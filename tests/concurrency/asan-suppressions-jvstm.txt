# LeakSanitizer suppressions for the JVSTM backend.
#
# JVSTM's CPU runtime has no version reclamation: get_or_create_vbox() allocates
# a VBox per tracked address, and every committed write prepends a fresh
# immutable VBoxBody that nothing ever frees (there is no GC pass in
# backends/tm_impl/jvstm/). The result is unbounded growth measured at ~48 bytes
# per committed write — peak RSS of `bank -t 4` rises 10.9x when the transaction
# count rises 10x (856 KB at 20k, 9.3 MB at 200k), where MVLOG, CSMV and SWISSTM
# stay flat because they do trim. See the JVSTM entry in TODO.md: this is an
# unimplemented feature (the paper's reclamation pass), not a coding slip, so it
# is suppressed rather than gated until a GC exists.
#
# Use with:
#   LSAN_OPTIONS=suppressions=tests/concurrency/asan-suppressions-jvstm.txt
#   ./benchmarks/cpp/bin/test_tx          # BACKEND=JVSTM
#
# Do NOT add entries here for anything else: a new leak in a backend that does
# reclaim should be fixed, not suppressed.
leak:get_or_create_vbox
leak:jvstm::
