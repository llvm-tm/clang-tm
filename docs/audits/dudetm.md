# Audit: DUDETM — TLA+ Spec vs C++ Implementation

## **Score: 1/5 — Model is a high-level design sketch; does not capture the actual implementation.**

The TLA+ spec describes a three-phase persistent TM (Perform → Persist → Reproduce), but the C++ implementation is a **TinySTM WBCTL wrapper with a forked replayer child process**. The model omits the entire STM layer (delegated to TinySTM), uses wrong op-type values, models recovery as a runtime action (C++ does it at init), and has no concept of `fork()`, shared mmap, or signal handling. The abstraction gap is so wide that the model and implementation describe fundamentally different systems.

## Algorithm Summary

DUDETM (Decoupled Durable Transactions) wraps **TinySTM WBCTL** (commit-time locking) with a persistence layer. The STM transaction runs normally via TinySTM; after commit, the write-set is published as a redo batch (COMMIT_BEGIN + OP_WRITE + OP_MALLOC + OP_FREE entries) into a per-thread circular buffer in shared mmap memory. A forked **replayer child process** consumes entries via a k-way merge of all thread logs, flushes them to a file-backed mmap (`clwb` + `sfence` semantics approximated via `msync`), and advances per-log tail pointers. On restart, `init()` checks for existing persistent data and restores symbol ranges from the file.

## Deviations

### 1. No TinySTM WBCTL protocol in the model — **Critical**

**C++**: DUDETM delegates to `tinystm_wbctl.hpp`'s full commit-time locking protocol with lock table (`g_locks_wbctl`), per-lock retry with extend (up to 1000 attempts), sorted-by-address lock acquisition, unconditional read-set validation, version-extension on write, and unlock-with-version.

**TLA+**: `STM_Commit(t)` (lines 157-175) applies the write-set to memory via a function `ws_mem(a)`, increments `stm_clock`, and moves `pc[t]` to `"logging"`. No lock table exists. No validate action exists in the model at all (the comment at line 160 says "For simplicity, model OCC as always succeeding").

**Risk**: **High** — The model cannot verify any correctness property of the WBCTL algorithm (lost-update detection, opacity, deadlock freedom). The model proves trivial log-bounds invariants but says nothing about the STM layer's behavior. The TLC trace has depth 5 (two threads running one begin → write → commit → log cycle) — this is insufficient to detect any concurrency bug.

### 2. Fork/Child-process architecture not modeled — **Critical**

**C++**: `init()` calls `fork()` (line 456). The parent and child share mmap'd regions (`g_logs`, `g_ctrl`, `g_persist_base`) via `MAP_SHARED`. The child runs `replayer_loop()` with its own address space. The parent signals shutdown via `g_ctrl->shutdown` (shared atomic bool).

**TLA+**: The replayer is a concurrent process sharing all variables. No fork, no copy-on-write, no separate address space.

**Risk**: **High** — The model cannot detect any issues related to fork safety (e.g., the replayer reading stale TLS, signal handling in child, mmap MAP_FIXED conflicts). The shared-state model gives a false sense of safety: the real system has a hard memory barrier between parent and child (fork duplicates page tables), and coordination is via shared atomics only.

### 3. Op-type values swapped — **Critical**

**C++** (`dudetm_base.hpp:21-26`): `OP_WRITE=0`, `OP_COMMIT_BEGIN=1`, `OP_MALLOC=2`, `OP_FREE=3`.

**TLA+** (`DUDETM.tla:77-80`): `OP_COMMIT_BEGIN=0`, `OP_WRITE=1`, `OP_MALLOC=2`, `OP_FREE=3`.

**Risk**: **High** — Any trace exported from the C++ runtime and replayed through the TLA+ model would misinterpret COMMIT_BEGIN as WRITE and vice versa. The `LogWriteMatch` invariant would fail (WRITE appears before COMMIT_BEGIN in the model's encoding). The fix is a one-line change in the TLA+ to swap the constants, but this is a serious modeling error.

### 4. Recovery at init vs runtime action — **High**

**C++**: `init()` (dudetm_base.hpp:332-470) checks the persistent file for existing data (magic, version, sym_count), and if valid, restores symbol ranges from the file. This happens BEFORE any transactions run. The forked replayer handles ongoing persistence.

**TLA+**: `RecoverDUDETM` (lines 258-290) is a Next-state action guarded by `~recovered`. It can fire at any interleaving — potentially mid-transaction, after the replayer has consumed some entries but not others. The model folds over `persist_file` to reconstruct `mem`.

**Risk**: **High** — The model's recovery semantics are fundamentally different from the C++ implementation. In C++, recovery is a one-shot init-time event that predates all transactions. In TLA+, it's a concurrent action with arbitrary interleaving. Any property proven by TLC about recovery correctness does not apply to the C++ system.

### 5. No abort action — **High**

**C++**: `abort_tx()` (tinystm_wbctl.hpp:109-133) handles: unlocks held locks, clears read/write sets, increments abort count, random backoff, siglongjmp retry. The runtime's `real_tm_end()` calls `tinystm::commit()` which calls `abort_tx()` on validation failure, which does `siglongjmp` past the commit call.

**TLA+**: There is no abort action. The only way a transaction ends is via `STM_Commit` → `LogBatch`/`LogWriteEntry` → `FinishLogging`, all of which succeed.

**Risk**: **High** — The model assumes all transactions commit. Retry loops, abort-based contention management, and the interaction between aborts and the log state (e.g., clearing `tls_redo_batch` at line 230 of DUDETM_runtime.cpp) are not modeled.

### 6. No memory ordering / fence annotations — **Medium**

**C++**: `publish_batch()` (dudetm_base.hpp:115-116) uses `std::atomic_thread_fence(memory_order_release)` before `head.store(h+count, memory_order_release)`. The replayer uses `head.load(memory_order_acquire)` and `tail.store(..., memory_order_release)`. TinySTM WBCTL uses `atomic_signal_fence(seq_cst)` on reads and acquire/release on lock operations.

**TLA+**: No memory ordering. All variable updates are instantaneous and globally visible. The `reorder` action from the WBCTL spec is not used.

**Risk**: **Medium** — The model cannot detect missing fences, relaxed-atomics bugs, or store-buffer related issues. Given the complexity of the mmap-based shared memory handoff between parent and child processes, this is a significant blind spot.

### 7. Write-set snapshot in `real_tm_end` not modeled — **Medium**

**C++**: `real_tm_end()` (DUDETM_runtime.cpp:235-292) copies the write-set from `current_tx_wbctl` BEFORE calling `tinystm::commit()` (because commit clears it via `tx->reset()`), then builds the batch from the snapshot. It also appends `tls_redo_batch` (MALLOC/FREE entries accumulated during the TX).

**TLA+**: `STM_Commit` moves to `"logging"` state with the write-set still intact. The log batch includes the write-set entries. There's no snapshot-vs-reset ordering issue because the model doesn't clear the write-set.

**Risk**: **Medium** — If a future version of TinySTM changes `commit()` to clear the write-set differently, the snapshot logic in DUDETM's `real_tm_end()` could race. The model wouldn't catch this because it doesn't model the delegation boundary.

### 8. `addr_to_file_off()` binary search — **Low**

**C++**: `addr_to_file_off()` (dudetm_base.hpp:122-151) does binary search across symbol ranges to compute persistent file offsets. The replayer uses this to `memcpy` write values to the correct position in the file mmap.

**TLA+**: Memory is a flat `[Addr → Data]` function. No file offsets, no persistence addressing.

**Risk**: **Low** — The model abstracts away storage entirely. As long as the C++ `addr_to_file_off()` logic is independently tested (it's straightforward binary search), this is a safe abstraction.

### 9. Missing `LogBatch` entry-by-entry vs batch publish — **Low**

**C++**: `publish_batch()` writes all entries atomically (release fence + single head update). The replayer sees a consistent batch.

**TLA+**: `LogBatch` writes a COMMIT_BEGIN, then `LogWriteEntry` writes individual entries. The model allows interleaving between entries (another thread could `ReplayerConsume` between them).

**Risk**: **Low** — The model is more permissive than C++ (allows partial-batch visibility), which is conservative for verification. However, the model's `~IsFull` check per-entry is stricter than C++'s `MAX_PENDING` check (which uses `h - t + count > MAX_PENDING`).

### 10. `MAX_PENDING` vs `IsFull` — **Low**

**C++** (`dudetm_base.hpp:108-110`): Busy-waits until `h - t + count > MAX_PENDING` is false. `MAX_PENDING = RING_LOG_SIZE / 2`, so only half the buffer is used (headroom for replayer).

**TLA+** (`LogWriteEntry`): Checks `~IsFull(t)` which is `(head+1) % LOG_SIZE = tail` — allows full buffer usage (modulo one slot). No headroom.

**Risk**: **Low** — Different capacity models; both prevent overflow. The C++ design is more conservative (half buffer for headroom), which is safer.

| **Hook system** | ⚠️ **Low** | C++ uses `TMRealHooks` registration. Model has direct variable manipulation. Abstracted correctly. |

## **Overall Score: 1/5 — Severe abstraction gaps across fundamental architecture**

This is the lowest-scoring backend in the audit suite. The TLA+ model accurately describes the *conceptual design* from the `Implementation_notes.md` but does not capture any of the actual C++ implementation's key behaviors:

1. The STM layer is TinySTM WBCTL — entirely missing from the model.
2. The replayer is a forked child process — modeled as a shared-memory concurrent process.
3. Recovery is an init-time operation — modeled as a runtime action.
4. Op-type constants are swapped — trace replay would misinterpret data.

The model would need a complete rewrite to match the C++ implementation. The recommended approach would be to compose the existing `tinystm_wbctl.tla` PlusCal spec with a new fork+mmap persistence module, replacing the current `DUDETM.tla`.
