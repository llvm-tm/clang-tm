\chapter{Persistent and Distributed Transactional Memory}
\index{persistent TM}\index{distributed TM}\index{durability}\index{crash recovery}\index{two-phase commit}\index{redo log}\index{Percolator}\index{TiKV}\index{PersistentSGL}\index{DistributedSGL}

Two extensions of the TM contract change the runtime far more than the
language: making commits survive crashes (persistent TM) and making the
same API span multiple machines (distributed TM). Both keep the ordinary
bank invariant, then add a stronger one --- durability, or agreement across
nodes --- and both force the commit path to become explicit about ordering.
The two worked examples below implement and verify each extension.

The running example remains the two-account bank transfer. In volatile TM,
the transfer is correct when it preserves the account floor and conserves the
sum of all balances. In persistent TM, a committed transfer must also survive
a crash. In distributed TM, all replicas or participants must agree on the same
commit decision. These are not cosmetic changes. They move the design pressure
from fast conflict detection to commit ordering, recovery records, stable
metadata, and replay rules.

The companion implementation includes both minimal and production-shaped
instances of these ideas: for persistence, DUDETM~\cite{liu17dudetm}
(decoupled durable transactions: persistence as a background concern),
SPHT~\cite{castro21spht} (group-commit persistent HTM, measured on real
Optane hardware), NV-HTM~\cite{castro18nvhtm}, and a minimal PersistentSGL;
for distribution, DistributedSGL and a TiKV-backed~\cite{peng10percolator}
Percolator two-phase-commit backend, plus the volatile baselines used earlier
in the book. Two naming cautions. First, the repository's \texttt{nvhtm}
backend is a \emph{scaffold}: its TM region is DRAM-backed \texttt{mmap}, so
it provides HTM atomicity plus redo-log instrumentation but \emph{no} crash
recovery (its own notes state this plainly). Second, the repository's
\texttt{romulus} backend is \emph{not} the persistent Romulus of Correia et
al.~\cite{correia18romulus} discussed below --- it is a volatile
version-table OCC that merely borrows the name. The volatile CPU backends are
exercised by the shared test suites (\texttt{test\_tx}: 114 cases,
\texttt{test\_ds}: 207 cases); the persistent and distributed backends carry
partial coverage only (plugin-pipeline builds and manual verification), and
each such limit is flagged where the design is presented. Model checking is
used to pin down the small-state corner cases that ordinary tests rarely hit:
\texttt{PersistentSGL.tla}, \texttt{DUDETM.tla}, \texttt{NVHTM.tla},
\texttt{SPHT.tla}, \texttt{DistributedSGL.tla}, and \texttt{TiKV.tla} all
live in \texttt{docs/proofs} and pass TLC's safety checks.

\section{Worked Example: Durable Bank Commit}
\index{persistent TM}\index{durability}\index{redo log}\index{crash recovery}
\label{sec:durable-bank-example}

Persistent TM asks for the ordinary TM invariant plus a crash invariant. A
committed transfer must not disappear after power loss, and recovery must not
apply it twice. The small example below uses one durable intent record. The
record stores the post-state, so redo is idempotent.

The commit protocol has three externally visible phases. First, the runtime
chooses an outcome while all ordinary TM checks still hold. Second, it forces a
commit intent to durable storage. Third, it installs the data and clears the
intent. A crash before the intent is forced is an abort. A crash after the
intent is forced is a commit that recovery must finish.

\begin{lstlisting}[language=C, caption={A minimal durable two-account transfer with idempotent redo.}]
#include <array>
#include <cstdint>
#include <cstddef>
#include <stdexcept>
#include <fcntl.h>
#include <unistd.h>

static const uint64_t MAGIC = 0x544d5f42414e4b31ULL; /* "TM_BANK1" */

struct Journal {
    uint64_t magic;
    uint32_t from, to;
    int64_t old_from, old_to;
    int64_t new_from, new_to;
    uint64_t sum;
};

struct Image {
    Journal journal;
    std::array<int64_t, 2> balance;
    int64_t floor;
};

static uint64_t checksum(const Journal& j) {
    return j.magic ^ j.from ^ (uint64_t(j.to) << 7) ^
           uint64_t(j.old_from) ^ (uint64_t(j.old_to) << 11) ^
           uint64_t(j.new_from) ^ (uint64_t(j.new_to) << 17);
}

static bool valid(const Journal& j) {
    return j.magic == MAGIC && j.sum == checksum(j);
}

static void write_all(int fd, const void* p, size_t n, off_t off) {
    const char* b = static_cast<const char*>(p);
    while (n != 0) {
        ssize_t k = ::pwrite(fd, b, n, off);
        if (k <= 0) throw std::runtime_error("pwrite failed");
        b += k; n -= size_t(k); off += k;
    }
}

static void read_all(int fd, void* p, size_t n, off_t off) {
    char* b = static_cast<char*>(p);
    while (n != 0) {
        ssize_t k = ::pread(fd, b, n, off);
        if (k <= 0) throw std::runtime_error("pread failed");
        b += k; n -= size_t(k); off += k;
    }
}

class DurableBank {
    int fd_;
    Image img_{};

    void sync() {
        if (::fsync(fd_) != 0) throw std::runtime_error("fsync failed");
    }

    void clear_journal() {
        img_.journal = Journal{};
        write_all(fd_, &img_.journal, sizeof(Journal), 0);
        sync();
    }

    void flush_image() {
        write_all(fd_, &img_, sizeof(Image), 0);
        sync();
    }

    void recover() {
        if (!valid(img_.journal)) return;
        const Journal& j = img_.journal;
        if (j.from >= 2 || j.to >= 2) throw std::runtime_error("bad journal");
        img_.balance[j.from] = j.new_from;  /* idempotent redo */
        img_.balance[j.to] = j.new_to;
        write_all(fd_, &img_.balance, sizeof(img_.balance),
                  offsetof(Image, balance));
        sync();
        clear_journal();
    }

public:
    explicit DurableBank(const char* path) {
        fd_ = ::open(path, O_RDWR | O_CREAT, 0644);
        if (fd_ < 0) throw std::runtime_error("open failed");

        off_t n = ::lseek(fd_, 0, SEEK_END);
        if (n < off_t(sizeof(Image))) {
            img_.balance = {1000, 1000};
            img_.floor = 0;
            flush_image();
        } else {
            read_all(fd_, &img_, sizeof(Image), 0);
            recover();
        }
    }

    ~DurableBank() {
        if (fd_ >= 0) ::close(fd_);
    }

    bool transfer(uint32_t from, uint32_t to, int64_t amount) {
        if (from >= 2 || to >= 2 || from == to || amount < 0) return false;
        if (img_.balance[from] - amount < img_.floor) return false;

        Journal j{};
        j.magic = MAGIC;
        j.from = from; j.to = to;
        j.old_from = img_.balance[from];
        j.old_to = img_.balance[to];
        j.new_from = j.old_from - amount;
        j.new_to = j.old_to + amount;
        j.sum = checksum(j);

        img_.journal = j;
        write_all(fd_, &img_.journal, sizeof(Journal), 0);
        sync();                         /* durable commit intent */

        img_.balance[from] = j.new_from;
        img_.balance[to] = j.new_to;
        write_all(fd_, &img_.balance, sizeof(img_.balance),
                  offsetof(Image, balance));
        sync();                         /* durable data */

        clear_journal();                /* recovery no longer needed */
        return true;
    }

    int64_t total() const {
        return img_.balance[0] + img_.balance[1];
    }
};

int main() {
    DurableBank b("bank.img");
    b.transfer(0, 1, 5);
    return b.total() == 2000 ? 0 : 2;
}
\end{lstlisting}

\begin{itemize}
    \item The durable intent record is not a full database log. It is the minimum needed to make one committed transfer recoverable.
    \item The post-state makes recovery idempotent: replaying the same journal record writes the same balances.
    \item The account floor is checked before the durable commit point. Recovery must not re-run policy code; it must complete the already chosen outcome.
    \item The money-conservation invariant is checked after restart by the same observation used in volatile tests: the total balance remains unchanged.
\end{itemize}

The example is deliberately conservative. It uses \texttt{fsync} as the storage
ordering primitive and a single image rather than a segmented log. A real
persistent TM backend may use cache-line write-back, epoch barriers, nonvolatile
allocation protocols, or copy-on-write roots. The same correctness rule remains:
once the commit point is durable, recovery must be able to discover the decision
and complete the update without consulting volatile state.

\section{Worked Example: Model Checking Distributed Commit}
\index{distributed TM}\index{two-phase commit}\index{TLA+}\index{money conservation}
\label{sec:distributed-commit-example}

Distributed TM turns validation into a protocol. A coordinator may decide only
after participants vote, and the data update must remain atomic from the
client's point of view. This TLA+ model is intentionally small: two accounts,
one transfer, one prepare phase, and one commit decision. (The full-scale
version checked in the repository is
\texttt{docs/proofs/\allowbreak DistributedSGL.tla};
read this mini-model as its teaching skeleton.) A naming caution: the
repository's \texttt{calvin} backend borrows its name from, but is not, the
deterministic distributed database of Thomson et al.~\cite{thomson12calvin};
it is a two-phase OCC shared-memory backend.

\begin{lstlisting}[caption={A TLA+ model of one distributed bank transfer with prepare/commit.}]
--------------------------- MODULE MiniDistributedBank ---------------------------
EXTENDS Naturals, TLC

Accounts == 1..2
From == 1
To == 2
Amount == 3
Floor == 0
InitBal == [a \in Accounts |-> 10]

VARIABLES bal, phase, vote, decision

vars == <<bal, phase, vote, decision>>

Init ==
    /\ bal = InitBal
    /\ phase = "idle"
    /\ vote = [r \in Accounts |-> "none"]
    /\ decision = "none"

Begin ==
    /\ phase = "idle"
    /\ phase' = "prepare"
    /\ UNCHANGED <<bal, vote, decision>>

Prepare(r) ==
    /\ phase = "prepare"
    /\ vote[r] = "none"
    /\ vote' =
        [vote EXCEPT ![r] =
            IF r = From
            THEN IF bal[From] - Amount >= Floor THEN "yes" ELSE "no"
            ELSE "yes"]
    /\ UNCHANGED <<bal, phase, decision>>

AllVoted ==
    \A r \in Accounts: vote[r] \in {"yes", "no"}

DecideCommit ==
    /\ phase = "prepare"
    /\ \A r \in Accounts: vote[r] = "yes"
    /\ phase' = "commit"
    /\ decision' = "commit"
    /\ UNCHANGED <<bal, vote>>

DecideAbort ==
    /\ phase = "prepare"
    /\ AllVoted
    /\ \E r \in Accounts: vote[r] = "no"
    /\ phase' = "done"
    /\ decision' = "abort"
    /\ UNCHANGED <<bal, vote>>

ApplyCommit ==
    /\ phase = "commit"
    /\ bal' = [bal EXCEPT ![From] = @ - Amount,
                          ![To] = @ + Amount]
    /\ phase' = "done"
    /\ UNCHANGED <<vote, decision>>

Next ==
    \/ Begin
    \/ \E r \in Accounts: Prepare(r)
    \/ DecideCommit
    \/ DecideAbort
    \/ ApplyCommit

Spec == Init /\ [][Next]_vars

TypeOK ==
    /\ phase \in {"idle", "prepare", "commit", "done"}
    /\ decision \in {"none", "commit", "abort"}
    /\ \A a \in Accounts: bal[a] \in Nat
    /\ \A r \in Accounts: vote[r] \in {"none", "yes", "no"}

MoneyConserved ==
    bal[1] + bal[2] = InitBal[1] + InitBal[2]

FloorsHold ==
    \A a \in Accounts: bal[a] >= Floor

=============================================================================
\end{lstlisting}

\begin{itemize}
    \item The model separates decision from application. This exposes the window in which a real coordinator must recover enough state to finish.
    \item The invariant is the same as the sequential bank example: balances stay above the floor and the total amount of money is conserved.
    \item The prepare votes are local, but the commit is global. This is the essential cost of exporting a TM abstraction over a distributed store.
    \item The model is small enough for exhaustive checking, but already contains the main distributed failure boundary: a decision without a completed data update.
\end{itemize}

The model also shows why distributed TM is not merely TL2 with sockets. A local
STM can usually retry when validation fails. A distributed transaction may have
already locked keys, recorded a primary decision, or exposed a timestamp to
another node. Abort, retry, and recovery become protocol states rather than
local control-flow choices.

\section{The Companion's Persistent Backends}
\label{sec:persistent-backends}
\index{DUDETM}\index{SPHT}\index{group commit}\index{redo log!decoupled}\index{per-thread commit log}

Table~\ref{tab:persistent-distributed-taxonomy} sorts designs by their commit
obligation; this section walks the two research-grade persistent backends the
companion actually implements, because they occupy opposite ends of the
spectrum in Figure~\ref{fig:persistent-distributed-commit-order}: DUDETM makes
durability \emph{trail} visibility, while SPHT batches durability into epochs
without ever delaying visibility past a hardware commit.

\paragraph{DUDETM: durability as a background concern.}
DUDETM~\cite{liu17dudetm} splits the durable transaction into three phases.
\emph{Perform}: the STM transaction runs exactly as any volatile backend runs
it --- read-set, write-set, validation, publish --- and the TM commit makes the
writes atomically visible with no persistence barrier anywhere in the path.
\emph{Persist}: each write was meanwhile appended as a redo entry
$(addr, size, value)$ to a non-volatile log; after the TM commits, a background
flusher drains the log to NVM (\texttt{clwb} + fence), overlapped with the
thread's next transaction. \emph{Reproduce}: after a crash, recovery scans the
log, replays every \emph{complete} transaction's writes idempotently, and
truncates. The design's whole point is the inversion: the visibility commit
point stays where volatile TM put it, and the durability point trails behind
it, so forward progress never waits on I/O. The cost is a recovery window ---
state that is visible-but-not-yet-durable must be reconstructible purely from
the log, which is why log completeness markers are load-bearing. The checked
model \texttt{docs/proofs/DUDETM.tla} (PlusCal) encodes exactly this split;
TLC verifies \texttt{LogBounds} (the per-thread ring log never overruns its
tail) and \texttt{PersistFileValid} (every persisted entry is well-typed ---
the recovery machinery may assume structure even for entries it has not
replayed yet).

\paragraph{SPHT: group commit on a hardware fast path.}
SPHT~\cite{castro21spht} keeps restricted transactions on RTM but gives every
thread a \emph{per-thread commit log} (PCL): an append-only NVM region into
which transactions append $(addr, size, value)$ entries as they execute,
inside the hardware transaction. Durability enters at \emph{epoch boundaries}:
the PCL accumulates several durably-committed transactions' entries until a
watermark fires (log roughly three-quarters full, or an epoch timer), then one
cache-line write-back sweep plus a single fence publishes the entire epoch.
One sync amortizes many transactions; recovery assigns one worker per PCL and
replays them in parallel. When RTM aborts persistently, the thread falls back
to a global-lock path --- and the fallback must be engineered as carefully as
the fast path: the companion's own history includes a bug class where a naive
fallback leaked the mutex across the retry loop's \texttt{siglongjmp}, a
concrete instance of the frame-hazard pitfalls Chapter~13 catalogs. The
checked model \texttt{docs/proofs/SPHT.tla} (PlusCal) carries the dual-path
state machine and crash/recovery; TLC verifies \texttt{TSXSafety},
\texttt{LockExclusion}, \texttt{TSXvsSGLSafety},
\texttt{DurableSeqMonotonic}, and \texttt{PCLBounds}.

\section{Worked Example: PersistentSGL Commit Ordering}

A single global lock is the simplest place to add durability because it removes
interleavings from the commit path. PersistentSGL is not scalable, but it is a
useful reference design: if the lock is held, the runtime can force the journal,
force the data, and clear the journal without another transaction observing a
half-installed update.

The listing below compresses that rule into a small C++ program. It is not a
replacement for the earlier durable image; it isolates the ordering discipline
that a persistent SGL backend enforces. (The repository's own
\texttt{PersistentSGL} takes the degenerate form of this design: no intent
record at all, but a write-through \emph{dual write} --- every committed store
is applied to memory and to a persistent file in the same critical section,
which is exactly what its checked model \texttt{PersistentSGL.tla} encodes.
The intent-record form shown here is the generalization a real undo/redo
backend would use.)

\begin{lstlisting}[language=C++, caption={A small PersistentSGL-style commit path for the bank invariant.}]
#include <array>
#include <cstdint>
#include <mutex>
#include <stdexcept>

struct Bank {
    std::array<int64_t, 2> balance{1000, 1000};
    int64_t floor = 0;
};

struct Intent {
    bool valid = false;
    uint32_t from = 0;
    uint32_t to = 0;
    int64_t new_from = 0;
    int64_t new_to = 0;
};

class PersistentSGLBank {
    std::mutex global_;
    Bank bank_;
    Intent intent_;

    void persist_intent() {
        if (!intent_.valid) throw std::runtime_error("empty intent");
        /* Real backend: write-back intent cache lines, then persist barrier. */
    }

    void persist_data() {
        /* Real backend: write-back modified balances, then persist barrier. */
    }

    void persist_clear() {
        /* Real backend: persist the invalid journal state. */
    }

public:
    bool transfer(uint32_t from, uint32_t to, int64_t amount) {
        std::lock_guard<std::mutex> guard(global_);

        if (from >= 2 || to >= 2 || from == to || amount < 0) return false;
        if (bank_.balance[from] - amount < bank_.floor) return false;

        intent_.valid = true;
        intent_.from = from;
        intent_.to = to;
        intent_.new_from = bank_.balance[from] - amount;
        intent_.new_to = bank_.balance[to] + amount;
        persist_intent();              /* durable commit point */

        bank_.balance[from] = intent_.new_from;
        bank_.balance[to] = intent_.new_to;
        persist_data();

        intent_.valid = false;
        persist_clear();
        return true;
    }

    void recover() {
        std::lock_guard<std::mutex> guard(global_);
        if (!intent_.valid) return;
        bank_.balance[intent_.from] = intent_.new_from;
        bank_.balance[intent_.to] = intent_.new_to;
        persist_data();
        intent_.valid = false;
        persist_clear();
    }

    int64_t total() const {
        return bank_.balance[0] + bank_.balance[1];
    }
};
\end{lstlisting}

\begin{itemize}
    \item The global lock is a correctness simplifier: it serializes volatile execution and durable publication.
    \item The durable commit point is the forced intent, not the later balance write.
    \item Recovery performs no validation and no user policy. It only completes a decision already made durable.
    \item The design is a baseline. More concurrent persistent algorithms must preserve the same ordering while allowing multiple transactions to prepare or publish.
\end{itemize}

\section{Worked Example: Percolator-Style Primary Commit}
\label{sec:percolator-commit-example}
\index{TiKV!key mapping}\index{address-to-key mapping}

TiKV-style distributed TM follows the Percolator shape~\cite{peng10percolator}:
prewrite locks the write set, the primary key records the commit decision, and
secondary keys are resolved afterward. This splits agreement into a recoverable
primary decision and idempotent cleanup of secondaries. The companion ships
both a runnable backend --- the Rust \texttt{tikv} runtime, which drives a real
TiKV cluster's optimistic transactions through the same TM hook API as every
volatile backend in this book --- and a checked PlusCal model,
\texttt{docs/proofs/TiKV.tla}. The small TLA+ model below abstracts keys as the
two bank accounts.

\paragraph{Mapping TM addresses to keys.}
The first design question in a distributed TM is deceptively simple: what is a
distributed \emph{address}? Two processes cannot agree on virtual pointers ---
\texttt{mmap} places each process's TM region wherever the OS pleases --- so
the backend maps each TM address to a key by its \emph{offset from the region
base}, rendered as fixed-width hex:

\begin{lstlisting}[caption={The address-to-key mapping of the companion's TiKV backend: region offsets, not pointers, so independent processes agree on keys.}]
fn addr_key(addr: *const u8) -> Vec<u8> {
    let start = addrspace::tm_region_start();
    let offset = (addr as usize).wrapping_sub(start);
    format!("tm:{offset:016x}").into_bytes()
}
\end{lstlisting}

This one function carries the whole portability argument of Chapter~2's DSM
lineage: TreadMarks moved shared memory across machines with per-page diffs;
here the same idea shrinks to a naming convention. The rest of the backend is
deliberately boring. Reads consult the local write-set, then the local
read-set cache, then issue a lazy TiKV \texttt{get}; writes buffer in a local
write-set; commit flushes the buffered writes atomically through TiKV's
optimistic two-phase commit (Percolator prewrite, then commit with the primary
key first). Contention surfaces not as a validation failure but as a gRPC-era
error from a conflicting commit; the backend rolls its transaction back and
signals an abort, and the ordinary retry loop re-executes --- the distributed
analogue of the abort/retry edge in Figure~\ref{fig:transactional-state-machine}.
Throughput is correspondingly lower than shared-memory backends (the network
replaces the cache line), but the invariant discipline is identical: money is
conserved across every committed transfer, now under a protocol whose commit
point lives on a different machine than the data.

    /\ phase = "primaryCommitted"
    /\ primaryDecision = "commit"
    /\ bal' = [bal EXCEPT ![Primary] = @ - Amount,
                          ![Secondary] = @ + Amount]
    /\ lock' = [k \in Keys |-> FALSE]
    /\ phase' = "done"
    /\ UNCHANGED primaryDecision

    /\ primaryDecision = "none"
    /\ primaryDecision' = "abort"
    /\ lock' = [k \in Keys |-> FALSE]
    /\ phase' = "done"
    /\ UNCHANGED bal

    \/ CommitSecondaries

Spec == Init /\ [][Next]_vars

    bal[1] + bal[2] = InitBal[1] + InitBal[2]

TypeOK ==
    /\ phase \in {"begin", "primaryCommitted", "done"}
    /\ primaryDecision \in {"none", "commit", "abort"}

\begin{itemize}
    \item The primary record is the distributed commit point.
    \item Secondary cleanup is allowed to lag because the primary decision can be re-read.
    \item The account floor is checked before prewrite succeeds on the debit key.
    \item The model captures the same obligation as the durable log: once commit is discoverable, later recovery must finish the data update.
\end{itemize}

\section{Summary}
\begin{itemize}
    \item Persistent TM adds a crash invariant to the ordinary money-conservation invariant; the durable worked example shows the minimum journal needed.
    \item The companion's persistent backends span a spectrum of \emph{where durability enters the commit path}: inside the lock (PersistentSGL), after visibility in a background flusher (DUDETM), batched at epoch boundaries (SPHT), and not at all yet (the NV-HTM scaffold). Each is pinned by a checked TLA+ model whose invariants name the obligation they discharge (Table~\ref{tab:durability-entry-points}).
    \item Distributed TM turns validation into a protocol; the model-checking example pins the failure boundary at ``a decision without a completed data update,'' and the TiKV backend shows the same API spanning machines once addresses become region offsets.
    \item Both extensions keep the same TM API --- only the commit path and its ordering obligations change.
\end{itemize}

Persistent and distributed TM are therefore best understood as commit-path
extensions. The speculative body of the transaction still reads, writes,
validates, and aborts. The difference is that commit becomes an externally
recoverable fact. PersistentSGL makes that fact a durable journal record.
Percolator-style distributed TM makes it a primary-key decision. In both cases,
the implementation must answer the same recovery question: after a crash or
partition, which transactions are committed, which are aborted, and which
updates remain to be completed?

\section{Exercises}
\begin{enumerate}
    \item \emph{[implementation]} Extend the durable bank example in \S\ref{sec:durable-bank-example} to four accounts and two concurrent worker threads. Keep one global durable commit lock, then record the throughput change relative to an in-memory SGL version. Do not claim durability until the journal and data writes have both been forced to storage.
    \item \emph{[verification]} Modify the TLA+ model in \S\ref{sec:distributed-commit-example} so that the coordinator may crash after deciding commit but before applying the update. Add a recovery action and check that \texttt{MoneyConserved} and \texttt{FloorsHold} still hold.
    \item \emph{[implementation]} Replace the single intent record in \S\ref{sec:durable-bank-example} with a bounded redo-log array. Add sequence numbers, reject torn records during recovery, and keep redo idempotent.
    \item \emph{[verification]} Extend the Percolator-style model so that secondary cleanup may be skipped nondeterministically. Add a recovery action that consults the primary decision and prove that committed transfers eventually reach \texttt{done} under weak fairness.
    \item \emph{[theory]} Compare PersistentSGL, Romulus, and TiKV-style two-phase commit as instances of the same abstract rule: a commit decision must become recoverable before its effects are required to be visible.
    \item \emph{[verification]} The SPHT model's \texttt{TSXvsSGLSafety} invariant states $\forall t:\ \texttt{sgl} \neq 0 \Rightarrow \lnot\texttt{tsx\_mode}[t]$ --- when any thread occupies the global-lock fallback, no thread may be in a hardware transaction. Explain why group commit needs this \emph{system-wide} exclusion rather than a per-thread one: what goes wrong if the lock holder excludes only its own TSX mode while another thread keeps executing an RTM transaction? Then modify the model's SGL-entry guard to permit exactly that overlap and report which checked invariant fails first.
    \item \emph{[implementation]} Add a second background flusher thread to your Exercise~3 redo-log bank so that persistence trails visibility exactly as DUDETM prescribes: the committing thread never blocks on I/O. Demonstrate a crash window (kill the process between visibility and persistence) and show that recovery reconstructs the visible-but-undurable state from the log.
    \item \emph{[literature]} Read Peng and Dabek's Percolator paper
          \cite{peng10percolator}, which this chapter's TiKV-style model
          abbreviates.  Map its per-row locks and commit timestamps onto
          the TLA+ model of \S\ref{sec:distributed-commit-example}, and
          identify one guarantee of the paper (e.g.\ write-write
          conflict resolution, the two-phase protocol under replication)
          that the book's abstract model does not represent.
\end{enumerate}
