\chapter[Transaction API Design]{Transaction API Design – Software Engineering Perspectives}
\index{transaction API design}\index{classic synchronous API}\index{language-integrated transactions}\index{transactional futures}\index{object-oriented transactional interfaces}

A transactional-memory backend is only useful if programmers can call it correctly. The algorithm may be TL2, NOrec, SGL, TSC-TM, TinySTM, SwissTM, JVSTM, MVLog, or a distributed Percolator-style coordinator, but the application sees a smaller surface: begin, read, write, commit, abort, retry, and sometimes a higher-level wrapper around them. API design is therefore not decoration. It determines where instrumentation happens, who owns retry, which side effects are safe, and how much of the runtime contract is visible in ordinary source code.

This chapter studies that contract from a software-engineering perspective. We keep the two-account bank transfer as the running example: a transaction debits one account, credits another, respects a floor, and preserves total money on the successful path. The examples deliberately use a small API because the companion implementations expose the same synchronous primitives across many backends. More elaborate interfaces are built by moving responsibility among the programmer, the compiler, the library, and the executor.

\section{Classic Synchronous API}

The classic transactional-memory API is a small set of blocking calls:

\begin{center}
\texttt{tm\_begin()}, \texttt{tm\_read()}, \texttt{tm\_write()}, \texttt{tm\_commit()}, \texttt{tm\_abort()}.
\end{center}

In the companion codebase this appears in the common denominator exposed by the Part~IV runtimes. An application enters a transaction, performs instrumented loads and stores, and asks the runtime to commit. If the runtime detects a conflict, the transaction aborts and the application retries. The underlying backend decides how conflict detection and validation work: SGL serializes through one lock; TL2 uses versioned ownership records; NOrec validates against a global sequence; TSC-TM uses timestamp-counter ordering; persistent and distributed variants add durability or coordination. The source-level protocol remains the same.

The minimal API hides a transaction descriptor. Each participating thread needs thread-local state: a read set, a write set, a nesting depth or status flag, a retry target, and backend-specific metadata. This is why practical systems often require thread-entry instrumentation. A thread must be initialized before its first transaction and cleaned up at exit. With an executor or task runtime, that requirement moves from ``thread starts once'' to ``worker is prepared before running transactional closures.''

Although the core is byte-oriented, programmers rarely want to write byte loops. Typed wrappers such as \texttt{tm\_read\_i4}, \texttt{tm\_write\_i4}, \texttt{tm\_read\_u8}, or \texttt{tm\_write\_ptr} convert typed operations into a uniform core operation over an address and size. The typed wrapper is not merely syntactic sugar: it fixes alignment, copying, and aliasing conventions at the API boundary. A word-based STM can still implement it by mapping an address to metadata; a byte-based redo log can copy the requested bytes directly.

The awkward part is retry. Many C implementations use \texttt{sigsetjmp}/\texttt{siglongjmp}, or an equivalent non-local control transfer, so that an abort can jump back to the most recent transaction start. This is efficient and keeps application code compact, but it creates a frame-lifetime hazard. If a transaction body stores pointers to stack objects, or relies on C++ destructors to run on every abort path, a non-local jump may invalidate those assumptions. Part~VI studies these hazards in detail. At the API level the lesson is already visible: a small primitive set makes the runtime portable, but it exposes responsibility for replay-safe code.

The set of primitives is deliberately small. Nested transactions, retry policies, allocation protocols, logging conventions, and futures can all be built on top. The smaller the primitive contract, the easier it is for many backends to implement it consistently. The cost is that higher-level safety properties must be enforced by wrappers, coding discipline, compiler integration, or verification.

\section{Worked Example: The Transfer, on the Classic API}
\index{TMD API}\index{tm\_begin}\index{tm\_end}\index{retry loop}
\label{sec:api-example}

Chapter~1's running example, expressed with the synchronous API and an
explicit retry loop:

\begin{lstlisting}[language=C, caption={transfer on the synchronous API.}]
int transfer(int *a, int *b, int n) {
    int attempts = 0;
    for (;;) {
        tm_begin();
        attempts++;
        int ba = tm_read_i4(a);
        int bb = tm_read_i4(b);
        if (ba - n < 0 || bb + n < 0) { tm_end(); return 0; }
        tm_write_i4(a, ba - n);
        tm_write_i4(b, bb + n);
        if (tm_end() == TM_COMMITTED) return attempts;  /* done */
        /* aborted: loop and retry */
    }
}
\end{lstlisting}

The code has the shape of an ordinary sequential transfer, but every shared access is routed through the transaction. The two reads define the snapshot used by the decision. The two writes are tentative until \texttt{tm\_end}. If validation fails, neither write becomes part of the abstract history, and the loop re-executes with a fresh snapshot.

The early return deserves attention. The example calls \texttt{tm\_end()} before returning failure, which treats the read-only decision as a transaction. Some APIs provide an explicit \texttt{tm\_abort()} or \texttt{tm\_cancel()} for application-level cancellation. Either convention is valid if the runtime specifies it clearly. What is not valid is leaving the active state by ordinary return while the runtime still believes a descriptor is live.

For a successful transfer of amount \texttt{n}, the local invariant is:

$$
a' + b' = (a - n) + (b + n) = a + b
$$

The floor condition is a precondition for installing the write set. If \texttt{a - n < 0}, the transaction commits no debit. If concurrent transactions race on the same accounts, the backend may abort one of them, but no interleaving observes only the debit or only the credit.

Compare with Chapter~1's lock-based version: no lock ordering, no unlock on every early-return path, and the two writes are atomic by construction. The \texttt{sigsetjmp}/\texttt{siglongjmp} machinery hides in \texttt{tm\_begin} and \texttt{tm\_end} --- the frame-lifetime hazard of Part~VI. Every backend in Part~IV implements exactly these five functions, so this source compiles unchanged across all of them. Exercise~3 asks for the \texttt{\_\_transaction\_atomic} equivalent; note the retry loop disappears --- the compiler generates it.

\section{Worked Example: A Lambda Wrapper}
\index{transactional lambda}\index{C++ wrapper}\index{retry loop}

A thin C++ wrapper can remove duplicated retry loops while preserving the same
backend contract. The body is still responsible for using instrumented loads and
stores.

\begin{lstlisting}[language=C++, caption={a C++ retry wrapper over the classic API.}]
extern "C" {
enum { TM_ABORTED = 0, TM_COMMITTED = 1 };

void tm_begin(void);
int  tm_end(void);
int  tm_read_i4(const int *addr);
void tm_write_i4(int *addr, int value);
}

template <class Body>
auto atomic_retry(Body body) -> decltype(body()) {
    for (;;) {
        tm_begin();

        auto result = body();

        if (tm_end() == TM_COMMITTED)
            return result;

        /* aborted: discard result and execute body again */
    }
}

int transfer_with_floor(int *from, int *to, int amount, int from_floor) {
    return atomic_retry([=]() -> int {
        if (amount <= 0)
            return 0;

        int bf = tm_read_i4(from);
        int bt = tm_read_i4(to);

        if (bf - amount < from_floor)
            return 0;

        tm_write_i4(from, bf - amount);
        tm_write_i4(to,   bt + amount);
        return 1;
    });
}
\end{lstlisting}

The money-conservation step for the successful path is local to the closure:

$$
\mathit{from}' + \mathit{to}' =
(\mathit{from} - \mathit{amount}) + (\mathit{to} + \mathit{amount})
=
\mathit{from} + \mathit{to}
$$

The wrapper changes the surface area of the API without changing the backend ABI. The body is a value. The retry policy is centralized. Tests can wrap many operations with the same helper. This is often the first engineering step in a research implementation: keep the C ABI stable, then build safer idioms above it in C++.

The wrapper also marks a boundary that cannot be crossed magically. It does not instrument ordinary loads and stores. If the body dereferences \texttt{*from} directly, the runtime does not know that \texttt{from} belongs in the read set. Similarly, if the closure prints a message, pushes to a non-transactional vector, releases memory, or sends a network request, that side effect may happen repeatedly under abort. A closure-based API improves structure, not semantics.

The wrapper centralises retry policy; the transfer code only describes the atomic update. The closure must be replay-safe: printing, freeing memory, or sending messages inside the body would repeat on abort. This is not language integration. Ordinary loads and stores are still ordinary loads and stores; the wrapper cannot instrument them. And destructors are not a complete substitute for the API: if a backend restarts with \texttt{siglongjmp}, C++ stack unwinding does not run.

\section{Language‑Integrated Keywords}

Language-integrated transactions move the API boundary into the compiler. GCC's \texttt{\_\_transaction\_\allowbreak atomic} is the canonical C/C++ example: the programmer writes a block, and the compiler inserts transaction begin and commit operations, instruments memory accesses, and enforces restrictions on calls from inside the block. The programmer no longer writes a retry loop, and common mistakes such as forgetting \texttt{tm\_end()} disappear.

The appeal is clear. The transaction is syntactically scoped. The compiler can distinguish transactional and non-transactional code. It can instrument ordinary-looking loads and stores, reject unsafe calls, and coordinate with exception handling. In a successful implementation the programmer sees something close to the ideal notation: execute this block atomically.

The cost is also clear. Keywords require compiler, runtime, and ABI support. The implementation must define what happens when a block throws an exception, calls a function that performs I/O, allocates memory, or touches inline assembly. It must decide how cancellation differs from conflict abort. It must preserve opacity: even a transaction that later aborts should not observe inconsistent intermediate states that allow undefined behavior before validation catches up.

An explicit API is easier to port across backends because it is just function calls. A keyword API is easier to use correctly because the compiler controls the shape of the transaction. This is the recurring API trade-off: portability and transparency on one side, static checking and syntactic safety on the other.

\section{Asynchronous and Future‑Based APIs}

A synchronous transaction is tied to the caller's stack. The caller enters the transaction, runs it, and leaves with either a result or an abort. An asynchronous API changes this shape: the caller submits a transaction as work, receives a handle, and later waits for the result. The transaction becomes a unit scheduled by an executor rather than a lexical region on the submitting thread.

This shift is attractive for systems that already have work queues. Worker threads can consume transaction closures, run the same classic API internally, and resolve futures after commit. The executor can choose scheduling order, limit concurrency, group similar operations, or batch validation attempts. None of that requires changing the bank-transfer body if the closure obeys the same rule as before: shared memory is accessed only through transactional operations.

The price is lifetime complexity. A future may outlive the stack frame that submitted it. Capturing pointers to local variables is therefore unsafe unless the API proves that the future finishes before the frame exits. Thread-entry initialization also changes. With a synchronous API, the application can initialize transaction state when a user thread starts. With an executor, the worker owns transaction stack state; per-task setup must ensure that no stale descriptor is reused across logically separate transactions.

Future composition preserves the composability argument from Chapter~1. An atomic closure is a value: it can be stored, submitted, combined with other futures, and awaited at a dependency point. But this composability does not make side effects transactional. A closure that sends a message before commit can still send it twice if the transaction aborts and retries.

\section{Worked Example: Futures for Batched Transfers}
\index{transactional future}\index{executor}\index{batching}

A future-based API moves the retry loop into the worker. The caller receives a
handle and later observes the committed result.

\begin{lstlisting}[language=C++, caption={submitting bank transfers as transactional futures.}]
#include <future>
#include <utility>
#include <vector>

extern "C" {
enum { TM_ABORTED = 0, TM_COMMITTED = 1 };

void tm_begin(void);
int  tm_end(void);
int  tm_read_i4(const int *addr);
void tm_write_i4(int *addr, int value);
}

/* Concrete helper for transactions returning int. */
template <class Body>
std::future<int> submit_tx_int(Body body) {
    return std::async(std::launch::async,
        [body = std::move(body)]() mutable -> int {
            for (;;) {
                tm_begin();

                int result = body();

                if (tm_end() == TM_COMMITTED)
                    return result;

                /* aborted: retry on this worker */
            }
        });
}

std::future<int> submit_transfer(int *from, int *to,
                                 int amount, int from_floor) {
    return submit_tx_int([=]() -> int {
        if (amount <= 0)
            return 0;

        int bf = tm_read_i4(from);
        int bt = tm_read_i4(to);

        if (bf - amount < from_floor)
            return 0;

        tm_write_i4(from, bf - amount);
        tm_write_i4(to,   bt + amount);
        return 1;
    });
}

int submit_batch_and_count(int *a, int *b, int *c) {
    std::vector<std::future<int>> fs;

    fs.push_back(submit_transfer(a, b, 10, 0));
    fs.push_back(submit_transfer(b, c,  7, 0));
    fs.push_back(submit_transfer(c, a,  3, 0));

    int committed_successes = 0;
    for (auto &f : fs)
        committed_successes += f.get();

    return committed_successes;
}
\end{lstlisting}

The three submitted transfers may execute in any order. If all three commit successfully, the total across \texttt{a}, \texttt{b}, and \texttt{c} is unchanged because each individual transaction preserves its two-account sum. If one returns \texttt{0} because of a floor check, it performs no write and therefore also preserves the global sum. Conflicts affect progress, not the abstract invariant.

A production executor would normally avoid creating one operating-system thread per \texttt{std::async}. The listing uses \texttt{std::async} because it is compact and standard. A fixed worker pool would keep per-worker transaction descriptors hot, reduce allocation overhead, and make batching decisions explicit.

The caller no longer owns transaction stack state; the worker does. Futures make composition explicit: submit many transactions, then join at the dependency point. A real executor can batch validation or scheduling decisions; the source-level API does not require the caller to know which backend is underneath. The closure must capture stable addresses: capturing pointers to caller stack variables is unsafe if the future may outlive the stack frame.

\section{Object‑Oriented and Polymorphic Interfaces}

Object-oriented APIs hide instrumentation inside types. Instead of calling \texttt{tm\_read\_i4(\&x)}, the programmer may write through a wrapper such as \texttt{TM<int>}. The wrapper overloads operations, records reads and writes with the runtime, and prevents some accidental raw access. Template-based STMs, including systems in the RSTM family, use this style to make transactions look like ordinary generic C++ code.

The benefit is type safety at the use site. A \texttt{TM<T>} value can expose only operations that are meaningful inside a transaction. It can choose whether reads return copies, proxies, or transactional references. It can encode ownership rules in constructors and destructors. A transaction-object or visitor pattern goes further: application objects provide methods that register their own fields with the runtime, allowing the transaction to operate at object granularity.

The central trade-off is granularity. Per-object locking and validation are simple, but they can be coarse. Two transactions that update different fields of the same object may conflict unnecessarily. Word-level STM reclaims fine granularity by indexing metadata by address, but then the wrapper must map object operations back to word or byte ranges. This tension appears repeatedly in real systems: the safer interface is often the coarser one, and the faster fine-grained interface is easier to misuse.

Polymorphism adds another cost. Virtual dispatch inside a transaction can obscure which memory locations are touched. If a virtual method performs non-transactional I/O, the runtime cannot roll it back. A good object-oriented API therefore needs a visible distinction between transactional methods, irrevocable methods, and methods forbidden inside a transaction.

\section{Summary}

API design directly affects usability, safety, and performance. The classic synchronous API is small, portable, and close to the runtime, but it relies on programmers or wrappers to place boundaries and instrument accesses correctly. Language keywords shift responsibility to the compiler, reducing common mistakes at the cost of toolchain complexity. Lambda and object wrappers improve structure while preserving a conventional backend ABI, but they cannot make ordinary side effects transactional. Future-based interfaces turn transactions into scheduled work, opening the door to batching and executor-level policies while introducing lifetime and replay hazards.

The API is the contract the rest of the book's runtimes implement. The same transfer source can run over simple SGL, optimistic STMs such as NOrec and TL2, timestamped designs such as TSC-TM, persistent variants, and distributed coordinators when the implementation supplies the required primitives. The programmer-facing question remains constant: where is the transaction boundary, who instruments memory, who retries, and what is allowed to become visible before commit?

\section{Exercises}
\begin{enumerate}
    \item A programmer argues that \texttt{tm\_write} should return a status code indicating whether the write caused an immediate abort. Explain why this violates opacity and propose an alternative.
    \item Sketch an asynchronous API where multiple transactions are submitted to a work queue and later awaited. Discuss how batching might reduce validation overhead.
    \item Compare using \texttt{tm\_begin}\slash{}\texttt{tm\_end} versus \texttt{\_\_transaction\_\allowbreak atomic}. Which is less error-prone and why?
    \item \emph{[implementation]} Extend Listing~\ref{sec:api-example}'s transfer into a reusable \texttt{atomic\_retry} helper for transactions returning \texttt{int}. Add a test that forces at least one abort and checks that the final account sum is unchanged.
    \item \emph{[verification]} Write a small PlusCal or TLA+ model of the state machine in Figure~\ref{fig:api-state-machine}. Check that no execution reaches \emph{Committed} after a failed validation edge.
    \item \emph{[theory]} Compare explicit calls, compiler keywords, and future-based closures under opacity. Which API makes it easiest to prevent non-transactional side effects from becoming visible before commit?
    \item \emph{[implementation]} Implement a \texttt{TM<int>} wrapper with \texttt{load()} and \texttt{store()} methods backed by \texttt{tm\_read\_i4} and \texttt{tm\_write\_i4}. Show one example where exposing a raw \texttt{int *} would bypass instrumentation.
    \item \emph{[verification]} Model a future-based API with states \emph{submitted}, \emph{running}, \emph{committed}, and \emph{failed}. State an invariant that a future never returns a value produced by an aborted attempt.
    \item \emph{[theory]} For the bank-transfer example, classify printing a receipt, appending to an audit log, and updating a transactional counter as replay-safe or replay-unsafe. Explain what API support would make each safe.
    \item \emph{[open]} Transactional semantics can live in the \emph{language} (compiler keywords), the \emph{library} (explicit hooks, closures), or the \emph{hardware} (HTM).  Argue for the layer you think should own opacity.  State the cost your choice imposes on the other two layers, and give the strongest argument against the layer you reject.
\end{enumerate}
