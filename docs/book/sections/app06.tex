\chapter{Development Environment Setup}
\label{chap:dev-setup}

This appendix is the concrete setup behind every \emph{[implementation]}
exercise.  The preface points here for the toolchain; this chapter makes
that promise good.  Everything below is tested against the companion
repository, so a working setup is: run the build, run the tests, run one
TLA+ check, and only then start an exercise.

\section{Minimum Toolchain}

\begin{itemize}
    \item \textbf{A C++20 compiler}: \texttt{g++} or \texttt{clang++}.
          The runtime backends and benchmarks build with
          \texttt{-std=c++20}; the LLVM instrumentation plugin requires
          LLVM~22 and its \texttt{clang}. (Note: LLVM~22 removed Arm TME
          support after the architecture withdrew it --- Chapter~16.)
    \item \textbf{LLVM 22} (for Part~V exercises): \texttt{llvm-config-22},
          \texttt{opt-22}, and the \texttt{clang-22} driver used by the
          \texttt{plugin/clang-tm} wrapper script.
    \item \textbf{\texttt{make}} and \textbf{CMake} (the plugin builds
          through CMake; the benchmarks through the top-level Makefile).
    \item \textbf{Java} and the \texttt{tla2tools.jar} checker (Part~III,
          Appendix~\ref{chap:pluscal-quick-ref}).  Install once with
          \texttt{make -C docs/proofs download-jar}.
    \item \emph{Optional:} \texttt{rr} (record-and-replay, Chapter~12),
          the gem5 fork (Chapter~16 --- see below), Docker (cross-builds
          and Linux CI on macOS), and a CUDA/ROCm toolchain (Chapter~17).
\end{itemize}

\section{Building the Companion}

From the repository root:

\begin{verbatim}
make                        # builds the plugin, plugin benchmarks, and
                            # benchmarks/cpp (explicit-API) binaries
make -C tests run           # backend (backends/tm_impl) unit tests
make -C benchmarks/cpp run-test-tx   # explicit-API tests, built+run below
make -C plugin run                   # plugin pipeline tests (18)
\end{verbatim}

The \texttt{benchmarks/cpp} Makefile exposes the per-benchmark and per-test
targets used by exercises:

\begin{verbatim}
make -C benchmarks/cpp run-bank          # two-account bank + fuzz/bank
make -C benchmarks/cpp run-fuzz-counter  # fuzz-counter with retry stats
make -C benchmarks/cpp run-test-tx       # 114 transaction tests
make -C benchmarks/cpp run-test-ds       # 207 data-structure tests
make -C benchmarks/cpp run-stamp         # STAMP benchmarks
\end{verbatim}

A backend is selected with the \texttt{BACKEND} variable. In
\texttt{benchmarks/cpp} the values are \textbf{uppercase}
(\texttt{TINYSTM} is the default; \texttt{NOREC}, \texttt{TL2},
\texttt{SGL}, \texttt{JVSTM}, \texttt{ROMULUS}, \texttt{TSXSGL}, and the
others named in \texttt{benchmarks/cpp/Makefile} are valid):

\begin{verbatim}
make -C benchmarks/cpp BACKEND=NOREC run-test-tx
\end{verbatim}

(The top-level Makefile's own \texttt{BACKEND} passthrough historically
used lowercase; when in doubt, match the case of the \texttt{ifeq} blocks
in the Makefile you are driving.)

\paragraph{gem5 (Chapter~16).} Upstream gem5 has no x86 TSX support; use
the companion fork (the \textsc{TM-SIM} repository, gem5 v25.1 plus the
in-tree TSX commit). Build and smoke-test:

\begin{verbatim}
scons build/X86_TSX/gem5.opt --with-ruby -j$(nproc)
tsx-comparison/scripts/run-bank-gem5.sh TSXSGL 1 64 500
\end{verbatim}

Benchmarks for gem5 are built as static x86-64 binaries with the ROI
markers of Chapter~16 --- on any host, including macOS, via Docker
(\texttt{linux/amd64} Alpine image, musl toolchain):

\begin{verbatim}
docker run --rm --platform linux/amd64 -v $PWD:/w -w /w/benchmarks/cpp \
  alpine:3.20 sh -c "apk add --no-cache g++ make >/dev/null && \
                     make BACKEND=TSXSGL GEM5=1"
\end{verbatim}

The full simulation workflow (checkpointing, ROI discipline, known gaps)
is in the fork's \texttt{IMPROVEMENT\_PLAN.md}.

\section{Model-Checking Workflow}

Chapter~6 (\S\ref{sec:verify-workflow}) defines the workflow; the
\texttt{docs/proofs/Makefile} automates it:

\begin{verbatim}
make -C docs/proofs download-jar        # one-time: fetches tla2tools.jar
make -C docs/proofs check               # TLC safety check, all backends
make -C docs/proofs check-one BACKEND=TL2
make -C docs/proofs verify-liveness     # fairness-based properties
\end{verbatim}

For a \emph{[verification]} exercise, drop your model in
\texttt{docs/proofs/} with a matching \texttt{.cfg} (see
Appendix~\ref{chap:pluscal-quick-ref}), run \texttt{check-one
BACKEND=YourModel}, then delete it before committing so the default
\texttt{check} target stays green.

\section{GPU Toolchains (Chapter 17)}

The GPU backends require dedicated hardware.  Under CUDA, compile kernels
with \texttt{nvcc} and target your \texttt{sm\_XX}.  Under ROCm, use
\texttt{hipcc --offload-arch=gfxXXXX} for kernels and compile host-side TM
hooks with \texttt{g++} defining \texttt{TM\_GPU\_USE\_HIP} and
\texttt{\_\_HIP\_PLATFORM\_AMD\_\_} (see
\texttt{backends/tm\_impl/gpu\_stm/}).  The GPU results are device-specific
by design (Table~\ref{tab:gpu-tm}); a CPU fallback
(\texttt{pr\_stm\_cpu.cpp}) exists for the simulation exercises.

\section{Common Failure Modes and Their Fixes}

These are the failures that recur when building and running the companion,
each with the fix that worked in this repository's history:

\begin{itemize}
    \item \textbf{DATA/TEXT symbol collisions.}  If an instrumented binary
          crashes jumping into garbage at the first TM call, the runtime was
          compiled without \texttt{-DLLVM\_TM\_PLUGIN}, so \texttt{tm\_init}
          and friends are TEXT functions while the plugin emits indirect
          calls through DATA pointers.  Fix: pass \texttt{-DLLVM\_TM\_PLUGIN}
          when building the runtime (the \texttt{plugin/clang-tm} wrapper
          does this automatically).  The same class of bug appears when a
          benchmark declares \texttt{tm\_malloc} as a function instead of a
          function-pointer variable.
    \item \textbf{Region-address conflicts.}  The TM region allocator
          \texttt{mmap}s a fixed address.  If a process stack or heap
          lands inside that range, the mapping replaces it and the process
          crashes (SIGSEGV).  Fix: map the region at the reserved base
          address and translate addresses, as the simulator does.
    \item \textbf{Missing LLVM target flags.}  The plugin needs the LLVM
          version's target and codegen flags.  Use the repository's
          \texttt{llvm-tool-helper.mk} and \texttt{clang-tm} rather than a
          hand-rolled build, so the flags stay in one place.
    \item \textbf{Untracked TM globals.}  If a static
          \texttt{TM} global is silently bypassed (lost updates), the
          instrumented binary is missing the \texttt{tm\_register\_global}
          calls that the queue-init pass emits; rebuild the plugin and
          recompile the benchmark.
    \item \textbf{Stale binaries.}  After a runtime change, rebuild the
          backend objects and the benchmark together; mixing an old
          instrumented binary with a new runtime produces the DATA/TEXT
          class of failure above.
\end{itemize}

The smoke test entry point is \texttt{smoke\_test.sh} at the repository
root; run it after any change to confirm the ten tested backends still pass
\texttt{test\_tx} (114/114) and \texttt{test\_ds} (207/207).
