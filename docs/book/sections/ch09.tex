\chapter{Speculative Designs: NOrec and Beyond}
\index{NOrec}\index{TL2}\index{TinySTM}\index{JVSTM}\index{MVLog}\index{value-based validation}\index{global-clock STM}\index{multiversion STM}

Speculative transactional memory replaces coarse serialization with optimistic execution. A transaction reads shared memory, records enough evidence to justify those reads, buffers or protects its writes, and later tries to make the whole execution appear atomic. The reward is concurrency. The price is aborts, metadata traffic, validation, and proof obligations.

This chapter studies the speculative in-memory families implemented in the companion repository: NOrec and NOrec-BF, TL2 and TSC-TM, TinySTM variants, JVSTM, and MVLog. The running bank-transfer example remains the test case: a transfer must preserve total money and must not take an account below its floor. Each design is judged by the same question: how does it prevent a transaction from committing an inconsistent snapshot?

\section{NOrec: Value‑Based Validation}

NOrec is the smallest useful optimistic STM in the repository. It has one global sequence clock, one commit lock, a buffered write-set, and a read-set containing addresses and the values observed at those addresses. There are no ownership records attached to individual memory locations. That absence is the name: \emph{NO ownership RECords}.

The algorithm is value-based. A transaction starts by sampling the global clock. A read first consults the transaction's own write-set; if the address has already been written speculatively, the buffered value is returned. Otherwise the read performs the read-validate discipline: capture the clock, read the value, re-check the clock, and validate the old read-set before admitting the new read. If the clock changed, some writer committed during the read, so the transaction retries or validates.

At commit time, the transaction acquires the single commit lock, re-reads every address in the read-set, compares each value with the recorded value, writes back the buffered writes, and advances the global clock. The clock advance is the linearization point for update transactions. A read-only transaction may linearize at a stable clock sample after validation.

The central invariant is simple: every committed transaction must have read values that all coexisted at one logical time. NOrec enforces this without per-location metadata by re-reading values. Clock-only validation is not enough. The companion implementation fixed a real bug class of this form: an ``invisible-it-committed'' execution in which a concurrent commit occurred between a transaction's last read and its commit, but the stale snapshot was not detected because values were not revalidated.

The cost model follows directly. NOrec has the smallest metadata footprint among the in-memory STMs considered here, but validation cost grows with the read-set size. The Bloom-filter variant, NOrec-BF, improves read-mostly workloads by avoiding some expensive bookkeeping and validation work when the filter proves an address is irrelevant to the current conflict check. In the repository's M1 Pro bank/fuzz measurements, NOrec-BF reaches about 829K transactions per second on a read-mostly workload, compared with about 553K for baseline NOrec. That is not a new algorithmic law; it is the expected signature of removing work from the read path.

\section{Worked Example: The NOrec Read Path}
\index{NOrec}\index{read-validate}\index{read-only transaction}\index{commit order}\index{validation}\index{read-set}
\label{sec:norec-example}

The read-validate discipline in code, mirroring \S\ref{sec:tso-example}'s
capture$\rightarrow$read$\rightarrow$recheck:

\begin{lstlisting}[language=C, caption={NOrec read: capture clock, read, re-check clock.}]
int32_t tm_read_i4(const void *addr) {
    for (;;) {
        uint64_t t1 = atomic_load(&g_clock);       /* capture   */
        int32_t v  = *(const int32_t*)addr;        /* read      */
        uint64_t t2 = atomic_load(&g_clock);       /* re-check  */
        if (t1 == t2) return v;                    /* consistent */
        /* a commit raced us: retry */
    }
}
\end{lstlisting}

Two clock reads bracket the data read; any interleaved commit changes the clock and forces a retry. This is the read-validate pattern the preceding discussion names --- the same one Part~II's store-buffer example revealed in hardware. Note there is no lock and no CAS: the read path is a plain load plus two acquires. That is the entire NOrec point. Exercise~1 of this chapter invites you to drop the second clock read and watch the invariant tests of Part~III fail.

The listing is deliberately minimal. A production NOrec read also checks the transaction's write-set before loading from memory and records the loaded value in the read-set after validation. The essence, however, is the two clock reads around the data read. They prevent a reader from accepting a value that was observed while a writer was publishing.

\section{Worked Example: NOrec Bank Transfer}
\index{NOrec}\index{bank transfer}\index{money conservation}\index{account floor}\index{value-based validation}
\label{sec:norec-bank-transfer-example}

The running bank example is deliberately small: transfer money between two
accounts, preserve total money, and reject transfers that would take the
source account below its floor.  In NOrec, transaction-local writes are buffered
until commit; reads first consult the write-set, then perform the
capture$\rightarrow$read$\rightarrow$recheck protocol.

\begin{lstlisting}[language=C, caption={A compilable C++17 NOrec-style bank transfer with value revalidation.}]
#include <atomic>
#include <cstdint>
#include <mutex>
#include <unordered_map>
#include <vector>

struct ReadEntry {
    const int64_t *addr;
    int64_t value;
};

struct WriteEntry {
    int64_t *addr;
    int64_t value;
};

struct Tx {
    uint64_t start_clock = 0;
    std::vector<ReadEntry> read_set;
    std::vector<WriteEntry> write_set;
};

static std::atomic<uint64_t> g_clock{0};
static std::mutex g_commit_lock;

static bool validate(const Tx &tx) {
    for (const ReadEntry &r : tx.read_set) {
        if (*r.addr != r.value) return false;
    }
    return true;
}

static bool find_write(const Tx &tx, const int64_t *addr, int64_t &out) {
    for (auto it = tx.write_set.rbegin(); it != tx.write_set.rend(); ++it) {
        if (it->addr == addr) {
            out = it->value;
            return true;
        }
    }
    return false;
}

static int64_t tx_read(Tx &tx, int64_t *addr) {
    int64_t buffered = 0;
    if (find_write(tx, addr, buffered)) return buffered;

    for (;;) {
        uint64_t c1 = g_clock.load(std::memory_order_acquire);
        int64_t v = *addr;
        uint64_t c2 = g_clock.load(std::memory_order_acquire);

        if (c1 == c2 && validate(tx)) {
            tx.read_set.push_back(ReadEntry{addr, v});
            return v;
        }

        tx.read_set.clear();
        tx.start_clock = g_clock.load(std::memory_order_acquire);
    }
}

static void tx_write(Tx &tx, int64_t *addr, int64_t value) {
    for (WriteEntry &w : tx.write_set) {
        if (w.addr == addr) {
            w.value = value;
            return;
        }
    }
    tx.write_set.push_back(WriteEntry{addr, value});
}

static bool tx_commit(Tx &tx) {
    std::lock_guard<std::mutex> guard(g_commit_lock);

    if (!validate(tx)) return false;

    for (const WriteEntry &w : tx.write_set) {
        *w.addr = w.value;
    }

    g_clock.fetch_add(1, std::memory_order_release);
    return true;
}

static bool transfer(int64_t accounts[2],
                     int64_t floor[2],
                     int from,
                     int to,
                     int64_t amount) {
    Tx tx;
    tx.start_clock = g_clock.load(std::memory_order_acquire);

    int64_t src = tx_read(tx, &accounts[from]);
    int64_t dst = tx_read(tx, &accounts[to]);

    if (src - amount < floor[from]) return false;

    tx_write(tx, &accounts[from], src - amount);
    tx_write(tx, &accounts[to], dst + amount);

    return tx_commit(tx);
}

int main() {
    int64_t accounts[2] = {100, 100};
    int64_t floor[2] = {0, 0};

    bool ok = transfer(accounts, floor, 0, 1, 25);

    if (!ok) return 1;
    if (accounts[0] + accounts[1] != 200) return 2;
    if (accounts[0] < floor[0] || accounts[1] < floor[1]) return 3;

    return 0;
}
\end{lstlisting}

The money-conservation invariant is checked after commit: the sum of committed account balances remains unchanged. The floor check is speculative; it is safe only because commit revalidates the values that justified it. The read path validates the old read-set before admitting a new read; otherwise a transaction can assemble a snapshot from different commit times. NOrec has no per-account ownership record; the commit lock and global sequence clock serialize publication.

\section{Worked Example: TL2 Read Barrier}

TL2 moves part of the validation burden from values to metadata. Each transactional location has a versioned lock word. A read samples the lock word, reads the payload, then samples the lock word again. The two samples must agree, the location must not be locked by a writer, and the version must not be newer than the transaction's start timestamp.

\begin{lstlisting}[language=C, caption={A compilable C++17 TL2-style read barrier for one integer location.}]
#include <atomic>
#include <cstdint>

struct VersionedInt {
    std::atomic<uint64_t> meta;  // low bit = locked, high bits = version
    int64_t value;
};

static constexpr uint64_t LOCKED = 1;

struct ReadRecord {
    VersionedInt *obj;
    uint64_t observed_meta;
    int64_t observed_value;
};

static bool is_locked(uint64_t meta) {
    return (meta & LOCKED) != 0;
}

static uint64_t version(uint64_t meta) {
    return meta >> 1;
}

static bool tl2_read(VersionedInt *obj,
                     uint64_t start_time,
                     ReadRecord &out) {
    for (;;) {
        uint64_t m1 = obj->meta.load(std::memory_order_acquire);
        if (is_locked(m1) || version(m1) > start_time) return false;

        int64_t v = obj->value;

        uint64_t m2 = obj->meta.load(std::memory_order_acquire);
        if (m1 == m2 && !is_locked(m2)) {
            out = ReadRecord{obj, m2, v};
            return true;
        }
    }
}

int main() {
    VersionedInt account{{2}, 100}; // version 1, unlocked
    ReadRecord r{};
    return tl2_read(&account, 1, r) && r.observed_value == 100 ? 0 : 1;
}
\end{lstlisting}

TL2 reads are invisible: the reader does not write to shared metadata. The metadata double-check prevents a read from crossing a writer's lock/unlock interval. The start timestamp defines the snapshot; versions newer than that timestamp force abort.

\section{TL2: The Textbook Global-Clock STM}

TL2 is the standard global-clock optimistic STM. A transaction reads the global version clock at begin time. That value is its snapshot time. Each transactional location has version metadata; each transaction has a read-set and a buffered write-set. Reads are invisible, but they are not unchecked: the read barrier records the observed version and later validation ensures the version did not change.

The commit protocol is lock-then-validate. The writer acquires ownership of every location in its write-set, validates the read-set against recorded versions, obtains a fresh commit timestamp, writes back the buffered values, installs the new versions, and releases the locks. The commit timestamp is the serialization point.

The validation rule is the opacity rule in executable form: every read-set entry must still have the recorded version, and that version must be no later than the transaction's snapshot. This is why invisible reads are safe. The reader does not announce itself, but it later proves that no writer changed what it observed.

The repository's TL2 and TSC-TM backends show the expected signature on the M1 Pro bank/fuzz workload: both are around 2.05M transactions per second, with TL2 measured at about 2.06M and TSC-TM at about 2.05M. The important lesson is not the exact number; it is that a tight global-clock OCC design can be far faster than value-only NOrec when metadata checks are cheap and contention is moderate.

\section{TinySTM Design Variants}

TinySTM is not one algorithm but a configurable family. The two main axes are version management and conflict timing. Version management decides where speculative writes live before commit. Write-back mode keeps new values in the transaction's private write-set until commit. Write-through mode installs new values in memory immediately and records undo information for abort. Conflict timing decides whether a transaction acquires ownership eagerly, at write time, or lazily, at commit time.

The repository exposes the important TinySTM styles: WBCTL, WT, and WBETL. In WBCTL, writes are buffered and locks are taken at commit time. Abort is cheap: discard the write-set. In WT, writes go through to memory, so abort must restore old values from an undo log. WT can detect write conflicts early, which helps under some high-contention patterns, but it makes rollback heavier and exposes more metadata traffic.

The observable distinction is where data lives. In write-back, shared memory remains unchanged until commit. In write-through, shared memory may contain speculative state protected by locks and undo records. Both can be correct; they discharge different obligations. Write-back must ensure write-set forwarding for reads-after-writes. Write-through must ensure that no other transaction treats speculative memory as committed.

TinySTM also illustrates cache-level engineering. Versioned write-set entries can avoid repeated metadata reads. Read-set bypass can avoid redundant validation when a read is satisfied from the write-set. These optimizations pay when transaction-local reuse is high; they add overhead when transactions touch many locations once.

\section{Multiversion STMs: JVSTM and MVLog}

Multiversion STMs avoid many read-only aborts by retaining history. A reader does not need to prove that the present still matches the past; it reads the past directly.

JVSTM stores each transactional variable in a VBox, a versioned box containing a history of bodies. Each body records a version and a value. A transaction with read-version walks the VBox history and returns the newest body whose version is no greater than that read-version. Read-only transactions never abort because their snapshot is materialized by the version histories. Writers still validate: at commit, a global clock increments under a lock, and writers append new VBox bodies after checking that the heads they depended on have not changed.

MVLog uses a different representation. It negotiates a commit slot at begin time with a single atomic increment, maintains an ever-growing log of committed write-sets, and tracks the newest writer per address. Its no-false-negative Bloom filter lets reads skip log work when the address is provably clean. The cost is history management. Memory grows with transaction count unless old versions and log entries are reclaimed. Epochs, hazard pointers, or equivalent schemes become part of the algorithm rather than an implementation afterthought.

This is also why multiversion ideas dominate many GPU TM designs. Read-only transactions do not abort, commit slots are cheap atomics, and validation can be expressed as bulk log or version checks. The repository's GPU designs, including CSMV and GUST, use related ideas at warp and block granularity, with GUST using an AtomicINC commit-log design and CCT/MRV validation.

\section{Worked Example: MVLog Snapshot Read}

The following small program is not the repository MVLog backend. It is a compact model of the same idea: a reader chooses a snapshot version and then reads the newest committed version not newer than that snapshot.

\begin{lstlisting}[language=C, caption={A compilable C++17 multiversion account read.}]
#include <cstdint>
#include <vector>

struct VersionedValue {
    uint64_t version;
    int64_t value;
};

struct VBox {
    // Newest entry first.
    std::vector<VersionedValue> history;
};

static bool read_at(const VBox &box, uint64_t snapshot, int64_t &out) {
    for (const VersionedValue &entry : box.history) {
        if (entry.version <= snapshot) {
            out = entry.value;
            return true;
        }
    }
    return false;
}

static void append_commit(VBox &box, uint64_t version, int64_t value) {
    box.history.insert(box.history.begin(), VersionedValue{version, value});
}

int main() {
    VBox account{{VersionedValue{2, 90}, VersionedValue{1, 100}}};

    int64_t old_snapshot = 0;
    if (!read_at(account, 1, old_snapshot)) return 1;
    if (old_snapshot != 100) return 2;

    append_commit(account, 3, 80);

    int64_t stable_snapshot = 0;
    if (!read_at(account, 2, stable_snapshot)) return 3;
    return stable_snapshot == 90 ? 0 : 4;
}
\end{lstlisting}

The reader's snapshot version, not the current head, determines the value returned. Appending a new version does not invalidate an old read-only transaction. Reclamation is the hard part: the body at version 1 cannot be freed while any reader may still hold snapshot 1.

\section{Comparing the Family}
\index{comparison}\index{version management}\index{conflict detection}

The speculative STM design space is small enough to fit in one matrix. The axes are conflict detection, version management, metadata placement, read visibility, and the linearization point. A runtime is a point in this space.

NOrec is the simplicity endpoint: one clock, one commit lock, value re-reading, no ownership records. TL2 adds per-location version metadata and becomes the textbook OCC baseline. TinySTM exposes the engineering trade-off between write-back and write-through. JVSTM and MVLog spend memory to make read-only snapshots stable. The recurring invariant is unchanged: a transaction must not commit a snapshot that never existed.

\section{Worked Example: The TL2 Commit Path}
\index{TL2}\index{commit protocol}\index{commit lock}\index{global clock}\index{OCC}\index{validation}\index{version management}
\label{sec:tl2-example}

The five-phase commit that Chapter~6's model and Part~III's invariants check:

\begin{lstlisting}[language=C, caption={TL2 commit: lock, validate, write back, publish.}]
bool tm_end(void) {
    if (!commit_lock.try_lock()) return retry();        /* 1. serialise */
    for (each r in read_set)                            /* 2. validate */
        if (version_of(r.addr) != r.observed_version)
            { commit_lock.unlock(); return retry(); }
    uint64_t ts = global_clock.fetch_add(1) + 1;        /* 3. new version */
    for (each w in write_set) {                         /* 4. write back */
        *(w.addr) = w.value;
        store_version(w.addr, ts);
    }
    commit_lock.unlock();                               /* 5. publish   */
    return true;
}
\end{lstlisting}

Step 2 is the expensive one: the read-set is validated against per-location version metadata, not a global clock. Step 4 writes back \emph{under} the commit lock, then advances the clock so no concurrent reader can observe a half-published write-set. The stored-value trap is step 4 interacting with step 2: without the read-validate pattern of \S\ref{sec:norec-example}, a stale read-set can validate against an old version while the write-back overwrites a newer commit. The same five steps appear in the PlusCal model of Part~III, and in the GPU backends of Part~VII at warp granularity.

\section{Worked Example: Account-Floor PlusCal Model}
\index{PlusCal}\index{TLA+}\index{model checking}\index{account floor}\index{money conservation}
\label{sec:pluscal-bank-floor-example}

The model below is intentionally small enough for TLC.  Two processes repeatedly
try to transfer one unit in opposite directions.  The commit action is atomic:
it checks the floor against the current state and then updates both accounts.
This is the serial specification that NOrec, TL2, TinySTM, JVSTM, and MVLog
must refine.

\begin{lstlisting}[language={}, caption={PlusCal/TLA+ model of two-account transfer with conservation and floor invariants.}]
---- MODULE BankTransferFloor ----
EXTENDS Naturals, TLC

CONSTANT Init0, Init1, Floor0, Floor1

ASSUME Init0 >= Floor0 /\ Init1 >= Floor1

(*
--algorithm Bank
variables bal = [0 |-> Init0, 1 |-> Init1];

define
  TotalOK == bal[0] + bal[1] = Init0 + Init1
  FloorsOK == bal[0] >= Floor0 /\ bal[1] >= Floor1
end define;

process (P \in {0, 1})
variables from = P, to = 1 - P, amount = 1;
begin
Loop:
  while TRUE do
    if bal[from] - amount >=
       IF from = 0 THEN Floor0 ELSE Floor1 then
      bal[from] := bal[from] - amount;
      bal[to] := bal[to] + amount;
    end if;
  end while;
end process;
end algorithm;
*)

==== 
\end{lstlisting}

A minimal TLC configuration is:

\begin{lstlisting}[language={}, caption={TLC configuration for the PlusCal account-floor model.}]
SPECIFICATION Spec
CONSTANTS
  Init0 = 2
  Init1 = 2
  Floor0 = 0
  Floor1 = 0
INVARIANTS
  TotalOK
  FloorsOK
\end{lstlisting}

The invariant \texttt{TotalOK} is the money-conservation property: transfers move value; they do not create or destroy it. The invariant \texttt{FloorsOK} is the safety property enforced by the transactional read of the source account followed by validation. To model a broken STM, split the guarded update into separate read, validate, debit, and credit actions, then remove the final validation; TLC should find an execution where the guard was true for a stale source value. This model is a serial specification, not an implementation model. The implementation models add clocks, read-sets, write-sets, locks, or version histories.

\section{A Complete NOrec in Rust}
\index{Rust}\index{sequence lock}\index{commit lock}\index{NOrec!complete implementation}\index{opacity!local justification}
\label{sec:norec-rust-complete}

The worked examples of this chapter showed fragments: a read path in
\S\ref{sec:norec-example}, a transfer in
\S\ref{sec:norec-bank-transfer-example}. This section assembles the whole
algorithm --- begin, read, write, commit, and the retry loop around them ---
into one compilable program, and explains every line that matters. The
language is Rust, and the choice is didactic rather than cosmetic: in
\emph{safe} Rust there are no casts between integers and pointers, so the
implementation cannot quietly rely on undefined behavior. Every design
decision must be made explicitly, which is exactly the discipline an STM
author needs. The repository ships a full-featured Rust NOrec with these
same bones (\rep{explicit\_api/rust/workspace/runtime/norec}); the version
below strips it to roughly two hundred lines of standard-library-only code,
verified with the compiler and the bank test that follows.

Four choices define the design, and each is the smallest honest version of
a choice NOrec makes \cite{dalessandro10norec}:

\begin{itemize}
    \item One global sequence clock, with the commit lock encoded in its
          low bit --- even means ``version $v$,'' odd means ``version $v$
          under commit.''
    \item Writes buffered in a per-transaction write-set, visible only at
          commit.
    \item Reads recorded as $(slot, value)$ pairs and validated against
          the \emph{begin} snapshot version.
    \item Any detected staleness aborts the whole transaction; the retry
          loop re-executes it from scratch.
\end{itemize}

Listing~\ref{lst:norec-rust-state} is the state. Cells live in a region:
one machine word each, addressed by slot index, guarded by nothing but the
clock. The \texttt{Word} trait admits any fixed-size \texttt{Copy} type;
the two implementations shown cover the accounts of this chapter, and more
are added mechanically. Note what the type system contributes: a
\texttt{TmCell<T>} is just an index plus a phantom type, so threads share
the region through an \texttt{Arc} and cells by copy, and no unsafe block
appears anywhere in the file.

\begin{lstlisting}[language=Rust, caption={State: a word-trait, the shared region, typed cell handles, and the per-thread transaction log.}, label={lst:norec-rust-state}]
use std::collections::HashMap;
use std::marker::PhantomData;
use std::sync::atomic::{AtomicU64, Ordering as O};
use std::sync::{Arc, atomic::AtomicBool};
use std::thread;

pub trait Word: Copy {
    fn pack(self) -> u64;
    fn unpack(raw: u64) -> Self;
}
impl Word for u64 {
    fn pack(self) -> u64 { self }
    fn unpack(raw: u64) -> u64 { raw }
}
impl Word for i64 {
    fn pack(self) -> u64 { self as u64 }
    fn unpack(raw: u64) -> i64 { raw as i64 }
}

pub struct Region {
    clock: AtomicU64,      // even = version v; odd = v, commit lock held
    mem: Vec<AtomicU64>,   // the TM heap: one machine word per cell
}

#[derive(Clone, Copy)]
pub struct TmCell<T> {
    slot: usize,
    _pd: PhantomData<T>,
}

/// Zero-sized signal: this attempt made no sense; retry.
pub struct Abort;

/// Per-thread transaction state, created fresh by `transaction`.
pub struct Tx<'r> {
    region: &'r Region,
    rv: u64,                  // snapshot version taken at begin
    ws: HashMap<usize, u64>,  // write-set: slot -> buffered value
    rs: Vec<(usize, u64)>,    // read-set: slot -> value observed
}

impl Region {
    pub fn new() -> Self {
        Region { clock: AtomicU64::new(0), mem: Vec::new() }
    }

    /// Allocate a cell. Call only during single-threaded setup:
    /// the heap does not grow once threads share the region.
    pub fn alloc<T: Word>(&mut self, init: T) -> TmCell<T> {
        self.mem.push(AtomicU64::new(init.pack()));
        TmCell { slot: self.mem.len() - 1, _pd: PhantomData }
    }
\end{lstlisting}

Allocation takes \texttt{\&mut self} on purpose. Growing the heap while
other threads hold slots would require the same kind of careful protocol
the companion's region allocators implement; here the rule is simply that
all allocation happens before the region is frozen into an \texttt{Arc},
and the signature enforces it.

Listing~\ref{lst:norec-rust-begin} adds the driver and \texttt{begin}.
The retry loop has exactly three exits per attempt: the body returns a
value, the body signals \texttt{Abort}, or \texttt{commit} fails. All
three land in the same place --- clear the logs, sample the clock, run
again. This is the explicit-API shape of Chapter~8's \texttt{tm\_begin}
and \texttt{tm\_end}, collapsed into one closure. Sampling the clock in
\texttt{begin} waits out any in-flight commit; the wait is bounded because
the commit lock is held only for the write-back of one transaction's
write-set, never across arbitrary user code.

\begin{lstlisting}[language=Rust, caption={The retry loop and begin: sample an unlocked clock, clear the logs, run, commit or retry.}, label={lst:norec-rust-begin}]
    /// Run `body` as an atomic action, retrying until it commits.
    pub fn transaction<R>(
        &self,
        body: impl Fn(&mut Tx<'_>) -> Result<R, Abort>,
    ) -> R {
        let mut tx =
            Tx { region: self, rv: 0, ws: HashMap::new(), rs: Vec::new() };
        loop {
            tx.begin();                     // sample clock, clear logs
            match body(&mut tx) {
                Ok(value) => match tx.commit() {
                    Ok(()) => return value, // committed
                    Err(Abort) => {}        // lost the race: retry
                },
                Err(Abort) => {}            // invalid snapshot: retry
            }
        }
    }
}

impl<'r> Tx<'r> {
    fn begin(&mut self) {
        self.ws.clear();
        self.rs.clear();
        // Sample the clock; wait out any in-flight commit (bit0 set).
        self.rv = loop {
            let s = self.region.clock.load(O::Acquire);
            if s & 1 == 0 { break s; }
        };
    }
\end{lstlisting}

Listing~\ref{lst:norec-rust-readwrite} is the heart. A read first serves
itself from the write-set (read-own-writes), then performs the
capture$\rightarrow$read$\rightarrow$recheck discipline of
\S\ref{sec:norec-example} with one addition: the captured value must equal
\texttt{rv}, the version sampled at \emph{begin}. That single comparison
is what validates the entire prior read-set. Because every commit moves
the global clock, a stable clock proves that no commit has interleaved
since the snapshot was taken, so every earlier recorded read still
coexists with the value about to be admitted. This is precisely the
chapter's earlier sentence --- ``validate the old read-set before
admitting the new read'' --- reduced, under a single global clock, to one
integer comparison. It is also the mechanism that lifts the design above
plain serializability toward the local-justification form of opacity
defined in \S\ref{sec:histories-legality-opacity}: a live transaction's
reads are always justified by the memory state at version \texttt{rv}.

\begin{lstlisting}[language=Rust, caption={Read and write: serve from the write-set first; otherwise capture--read--recheck against the begin version.}, label={lst:norec-rust-readwrite}]
    /// Transactional read: write-set first, then capture-read-recheck
    /// against the *begin* version. Every successful read re-validates
    /// the entire snapshot implicitly: any commit since begin would
    /// have moved the clock away from `rv`.
    pub fn read<T: Word>(&mut self, cell: &TmCell<T>) -> Result<T, Abort> {
        let slot = cell.slot;
        if let Some(&v) = self.ws.get(&slot) {
            return Ok(T::unpack(v));       // read own buffered write
        }
        let s1 = self.region.clock.load(O::Acquire);   // capture
        if s1 != self.rv {
            return Err(Abort);             // snapshot is stale already
        }
        let raw = self.region.mem[slot].load(O::Relaxed);  // read data
        let s2 = self.region.clock.load(O::Acquire);   // re-check
        if s1 != s2 {
            return Err(Abort);             // a commit raced the read
        }
        self.rs.push((slot, raw));
        Ok(T::unpack(raw))
    }

    /// Transactional write: buffer only; visible at commit time.
    pub fn write<T: Word>(&mut self, cell: &TmCell<T>, value: T) {
        self.ws.insert(cell.slot, value.pack());
    }
\end{lstlisting}

One simplification deserves honesty: the real NOrec lets a transaction
\emph{extend} its snapshot --- on detecting a moved clock it re-validates
its old read-set under the newer version and continues. This
implementation instead aborts whenever the clock leaves \texttt{rv},
which is strictly more conservative and easier to prove correct; the
extension policy is Exercise~13.

Listing~\ref{lst:norec-rust-commit} is the commit protocol. A writer
acquires the single commit lock by flipping bit~0 of the clock with a
CAS; the loser aborts immediately, making the design weakly progressive
in the ladder of \S\ref{sec:progress-ladder}. Under the lock, memory is
frozen --- every writer in the system needs this same lock --- so comparing
each recorded read against current memory is meaningful. On mismatch the
transaction stores \texttt{rv} back: the same version, lock cleared,
nothing published, because it changed nothing. On success it writes the
buffered values and publishes with \texttt{rv + 2}. The bump by two (not
one) keeps versions even forever; odd numbers exist only transiently
while a writer holds the lock.

\begin{lstlisting}[language=Rust, caption={Commit: acquire the lock bit, re-validate reads against frozen memory, write back, publish with a Release clock bump.}, label={lst:norec-rust-commit}]
    // ---------- 4. Commit protocol ----------

    fn commit(&mut self) -> Result<(), Abort> {
        if self.ws.is_empty() {
            return Ok(());  // read-only: reads validated continuously
        }
        let rv = self.rv;
        // Acquire the single commit lock by setting bit0 of the clock.
        if self.region.clock
            .compare_exchange(rv, rv | 1, O::Acquire, O::Relaxed)
            .is_err()
        {
            return Err(Abort);             // another writer went first
        }
        // Lock held: no other writer can touch memory now, so value
        // comparisons against our recorded reads are meaningful.
        for &(slot, observed) in &self.rs {
            if self.region.mem[slot].load(O::Relaxed) != observed {
                self.region.clock.store(rv, O::Release); // unlock, no bump
                return Err(Abort);
            }
        }
        // Publish: write back, then bump the clock (unlock + new version).
        for (&slot, &v) in &self.ws {
            self.region.mem[slot].store(v, O::Relaxed);
        }
        self.region.clock.store(rv + 2, O::Release);
        Ok(())
    }
\end{lstlisting}

The memory orderings are load-bearing, and they are the portable answer to
the puzzle of \S\ref{sec:tso-example}. Every data access is
\texttt{Relaxed}; all synchronization is carried by the single clock
variable. A writer's data stores precede its \texttt{Release} store of the
new version; a reader whose \texttt{Acquire} load observes that version is
guaranteed to see every write published with it. That Release/Acquire pair
is the generalization of the store-buffer story from Part~II to weakly
ordered machines: on x86 the relaxed accesses would compile to plain
moves, while on ARM the pairing emits the barriers the litmus tests of
Chapter~3 demanded. The commit-time validation loads are sound under
\texttt{Relaxed} for the same reason --- they execute after the
\texttt{Acquire} CAS, so no previously committed state can be invisible
to them.

A read-only transaction commits trivially: its reads were validated
continuously, so there is nothing to do, and it linearizes at its last
successful read. An update transaction linearizes at the clock bump ---
the moment its writes become visible to every subsequent snapshot.

Listing~\ref{lst:norec-rust-demo} runs the chapter's example end to end:
eight mover threads transfer 10 units between accounts $A$ and $B$
honoring the floor rule, while a checker thread continuously executes
read-only transactions asserting conservation \emph{mid-flight}. Note the
distinction in the mover body: a floor violation returns
\texttt{Ok(false)} --- a committed business outcome, exactly as in
Listing~\ref{lst:rust-bank} --- whereas \texttt{Abort} is reserved for the
STM's own invalid-snapshot signal.

\begin{lstlisting}[language=Rust, caption={The bank demo: movers honor the floor; a checker thread asserts conservation inside concurrent read-only transactions.}, label={lst:norec-rust-demo}]
const THREADS: usize = 8;
const ITERS: usize = 25_000;
const START: i64 = 1_000_000;

fn main() {
    let mut region = Region::new();
    let a = region.alloc(START);
    let b = region.alloc(START);
    let region = Arc::new(region);

    let done = Arc::new(AtomicBool::new(false));

    // Mover threads: transfer 10 between A and B, honouring a floor 10.
    let mut handles = Vec::new();
    for t in 0..THREADS {
        let region = Arc::clone(&region);
        let done = Arc::clone(&done);
        handles.push(thread::spawn(move || {
            let (src, dst) = if t % 2 == 0 { (a, b) } else { (b, a) };
            let (mut moved, mut rejected) = (0u64, 0u64);
            while !done.load(O::Relaxed) && moved < ITERS as u64 {
                let ok = region.transaction(|tx| {
                    let s = tx.read(&src)?;
                    let d = tx.read(&dst)?;
                    if s < 10 { return Ok(false); } // floor: real outcome
                    tx.write(&src, s - 10);
                    tx.write(&dst, d + 10);
                    Ok(true)
                });
                if ok { moved += 1 } else { rejected += 1 }
            }
            (moved, rejected)
        }));
    }

    // Checker thread: every committed snapshot must conserve money.
    let region2 = Arc::clone(&region);
    let done2 = Arc::clone(&done);
    let checker = thread::spawn(move || {
        let mut checks = 0u64;
        while !done2.load(O::Relaxed) {
            let total = region2.transaction(|tx| {
                Ok(tx.read(&a)? + tx.read(&b)?)
            });
            assert_eq!(total, 2 * START, "invariant violated");
            checks += 1;
        }
        checks
    });

    for h in handles { h.join().unwrap(); }
    done.store(true, O::Relaxed);
    let checks = checker.join().unwrap();

    let total = region.transaction(|tx| Ok(tx.read(&a)? + tx.read(&b)?));
    println!("final total = {}", total);
    println!("snapshot checks passed: {}", checks);
    assert_eq!(total, 2 * START);
}
\end{lstlisting}

Typical output on the development machine (Apple M1 Pro, rustc 1.96):

\begin{quote}
\small\ttfamily
final total = 2000000\\
snapshot checks passed: 229337
\end{quote}

Money is conserved at the end, and --- the stronger property --- every one
of the hundreds of thousands of concurrent read-only snapshots observed a
consistent world. That is opacity demonstrated empirically: the checker
thread shares no locks with the movers, yet it never observes half of a
transfer.

Three caveats bound the claim. First, correctness assumes all accesses to
cells go through transactions; a plain write to \texttt{mem} would be
invisible to validation, exactly as in every backend of Part~VII.
Second, the design has no starvation guarantee. Under sustained write
contention, readers can lose the race repeatedly --- the retry loop is
unbounded and unfair --- which is why production backends pair speculation
with fallback locks and why the progress ladder of
\S\ref{sec:progress-ladder} ranks guarantees the way it does. Third, the
fixed-snapshot policy aborts where the paper's forward-extension policy
would proceed, trading throughput for proof simplicity; measuring that
trade is Exercise~12.

\section{Summary}

Speculation unlocks concurrency but introduces aborts. Different version-management policies trade off simplicity for performance. The design space is small: clocks, locks, logs, and history --- every real STM is a combination of these. NOrec shows the value-only endpoint, TL2 the metadata-based baseline, TinySTM the write-back versus write-through engineering choice, and JVSTM and MVLog the multiversion alternative that buys read-only stability at the price of reclamation. Section~\ref{sec:norec-rust-complete} closes the loop by assembling the NOrec endpoint into a complete, compilable implementation.

\S\ref{sec:norec-bank-transfer-example}, instrument the abort

graded against \S\ref{sec:norec-example}, \S\ref{sec:tl2-example}, and
