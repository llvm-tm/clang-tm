\chapter{Formal Design with PlusCal and TLA+}
\index{TLA+}\index{PlusCal}\index{TLC}\index{model checking}\index{invariant}\index{opacity}\index{transactional memory!formal verification}

Transactional memory is a concurrency protocol before it is a library.  The
implementation contains atomics, locks, fences, compiler boundaries, cache
effects, persistence calls, RPCs, and sometimes GPU kernels.  The protocol
underneath is smaller: a set of shared variables, a set of transactions, and a
rule for deciding which executions are legal.  TLA+ and PlusCal give us a way
to write that smaller protocol as an executable state machine.

This chapter uses PlusCal as a design notation for TM algorithms.  We model the
running two-account bank transfer, check the account-floor and
money-conservation invariants, then move from a single global lock to NOrec-style
optimistic validation.  The aim is not to prove that the C++, Rust, or GPU code
has no defect.  The aim is to make the concurrency argument explicit, finite,
and hostile enough that TLC can search for the interleavings humans routinely
miss.

\section{Why TLA+ and PlusCal (and Not a Proof Assistant)?}
\label{sec:why-tla}

A reader with a formal-methods background will reasonably ask why this book
standardizes on TLA+/PlusCal and the TLC model checker instead of a proof
assistant such as Lean, Coq, or Isabelle, or another model checker such as
Alloy or SPIN.  The choice is deliberate, and it is worth making the argument
explicitly, because it explains both what the book's models \emph{are} and what
they are \emph{not}.

\paragraph{The job to be done.}  Every verification artifact in this book
answers the same engineering question: \emph{does this specific protocol
design, at this level of abstraction, admit a bad interleaving?}  TM protocols
are small, closed, finite-state systems once the data values are abstracted:
two or three threads, a handful of addresses, a global clock, a lock word, a
commit log.  What makes them hard is not mathematical depth but
\emph{interleaving explosion} --- the bugs live in the schedules, not in the
arithmetic.  That is exactly the profile at which explicit-state model checking
excels: push a button, and TLC either exhausts the state space or returns a
concrete counterexample trace that can be read off state by state and replayed
against the C++ implementation.

\paragraph{What the alternatives would buy and cost.}

\begin{itemize}
\item \textbf{Lean~4 / Coq / Isabelle (interactive theorem provers).}
  A proof assistant gives a \emph{parametric} theorem --- ``opaque for any
  number of threads and addresses'' --- rather than a finite-instance check.
  The price is steep: the proof is written by hand as tactics or structured
  scripts, typically person-months for a single realistic TM protocol, and the
  artifact reads as proof syntax rather than as the algorithm.  That trade
  inverts this book's goal: Part~IV and Part~VII iterate over \emph{many}
  backend designs (20+ in the companion repository), each of which needs a
  checkable model in hours, not months, and the model must stay close enough to
  the code that a reader can move between them.  When a parametric theorem is
  genuinely wanted --- say, that value-based validation implies opacity for
  \emph{any} workload, not just the checked instance --- a proof assistant is
  the right tool, and the literature's published opacity proofs
  (e.g.\ Guerraoui and Kapalka's~\cite{guerraoui08correctness}) were done
  paper-style for the same reason.  We flag that as a research exercise rather
  than pretend TLC subsumes it.
\item \textbf{Alloy.}  Alloy's relational logic is excellent for data-shape
  invariants (``this graph is always a tree''), but its idioms fit protocol
  \emph{steps} awkwardly and its analyzer is bounded-satisfiability rather than
  temporal; liveness properties such as ``a transaction that keeps retrying
  eventually commits'' are outside its comfort zone.
\item \textbf{SPIN (Promela).}  SPIN is the closest relative: an
  explicit-state LTL model checker with an algorithm-like input language.  It
  would serve.  TLA+ wins on three practical points: the PlusCal surface syntax
  is closer to the pseudo-code used elsewhere in the book; the specification is
  ordinary math (sets, functions, records) rather than a C-like DSL, so the
  models double as precise definitions; and the TLA+ ecosystem (TLC, the
  PlusCal translator, TLATeX pretty-printing) is a single mature toolchain that
  the companion repository drives with one \texttt{Makefile}
  (\texttt{docs/proofs}).
\end{itemize}

\paragraph{What TLC does \emph{not} give us.}  Three honest limitations recur
throughout the book.  First, \emph{finiteness}: TLC checks the instance it is
given --- two threads, three addresses, a bounded log --- so ``TLC pass'' is
evidence, not a theorem; the liveness false-negatives noted in
Part~VII are the price of bounding unbounded counters.  Second,
\emph{abstraction}: the models abstract away the \texttt{sigsetjmp} retry
machinery, cache geometry, and compiler effects, so they cannot catch bugs
that live below the abstraction line (Chapter~13's DATA/TEXT symbol collision
is a real example).  Third, \emph{extraction}: nothing guarantees the C++ code
implements the model; the repository manages that risk by keeping model and
runtime side by side and by tracing each chapter's runtime to its model file
(Table~\ref{tab:traceability}).  A proof assistant would address only the first
of these, at a cost this book is not willing to pay per backend.

\section{TLA+ and PlusCal in a Nutshell}

TLA+ is a language for state machines.  A specification names variables, gives
their initial values, and defines the actions that move the system from one
state to the next.  TLC then enumerates reachable states and checks whether the
declared invariants and temporal properties hold.

PlusCal is an algorithm language embedded in TLA+.  It looks closer to
pseudo-code: it has processes, labels, assignment, conditionals, loops,
\texttt{either/or}, \texttt{await}, and \texttt{assert}.  The PlusCal translator
turns that algorithm into ordinary TLA+ actions.  This matters in a textbook:
the pseudo-code can be the checked artifact, not a paraphrase of it.

A TM model normally has three layers of state: \textbf{application state}, the
heap being protected, such as the two account balances in the bank example;
\textbf{transaction state}, the read sets, write sets, local snapshots, abort
flags, and program counters; and \textbf{metadata}, the locks, sequence clocks,
versioned ownership records, commit logs, persistence epochs, or distributed
write intents.

Safety and liveness must be stated separately.  A safety property says that a
bad state never occurs: two owners do not hold the same lock, a committed
transaction does not expose a mixed snapshot, total money is conserved.  A
liveness property says that a good state eventually occurs: under appropriate
fairness assumptions, a transaction that can commit is not postponed forever.
Most TM bugs in this book are safety bugs.  Starvation and retry policies are
liveness questions.

The main benefit is design pressure.  Writing the model forces empty cases into
view.  What happens if a reader observes the old value of account~1 and the new
value of account~2?  What happens if the sequence clock changes between read and
commit?  What if a GPU warp sees a commit-log entry but not the corresponding
validation-table update?  These are not implementation details yet.  They are
states, and a state-machine model must either allow them or rule them out.

\section{Specifying and Checking Simple TM Algorithms}

A useful TM specification is finite and abstract.  It does not contain the
allocator, the benchmark harness, the cache hierarchy, or the whole language
runtime.  It contains exactly the state needed to falsify the advertised
property.

For a single-global-lock TM, the state is almost embarrassingly small: one lock
bit, a heap, and per-transaction local state.  Every transaction waits for the
lock, runs alone, writes back, and releases the lock.  The specification is
valuable not because SGL is subtle, but because it is the serial reference
against which optimistic designs are compared.

NOrec is only slightly larger in code but much richer in behavior.  The model
contains a global sequence clock, a commit lock, application values, and each
transaction's remembered read values.  A reader records a snapshot.  If the
clock is unchanged, the read set is accepted quickly.  If the clock changed, the
reader must compare the values it observed against memory.  A writer must
recheck before publishing.  Removing that final recheck is precisely the kind of
``obviously harmless'' edit that TLC is good at rejecting.

The companion repository contains checked models for every backend discussed in
the implementation chapters: SGL, TSX-SGL, SPHT, NOrec, NOrec-BF, TL2, TSC-TM,
TinySTM variants, SwissTM, DUDETM, NV-HTM, XTM, Romulus, LeftRight, JVSTM,
MVLog, PersistentSGL, DistributedSGL, TiKV/Percolator-style two-phase commit,
and the GPU designs PR-STM, CSMV, GPUTX, GAccO, GPU-JVSTM, and GUST.  The
runtime test suites report \texttt{test\_tx} 114/114 and \texttt{test\_ds}
207/207 passing; the models are a separate line of evidence, checking the
protocol abstraction rather than the concrete benchmark binary.

The invariants that matter recur throughout the book: opacity or a reduced-order
approximation of opacity; lock exclusion and ownership consistency; monotonic
commit clocks; version/lock agreement for TL2-like orecs; the guarantee that no
committed transaction can be invalidated by a later validation; no missed
conflict in commit-log GPU designs; and atomic visibility for distributed
two-phase commit.

TLC should be treated as an adversarial scheduler.  If a read-validate bug, a
snapshot-threshold bug, or a missed commit-log conflict exists in the finite
model, the checker will usually find a short trace.  That trace is often more
useful than a crash: it names the exact sequence of abstract actions that led to
the bad state.

The state machine is serial by construction.  At most one process can pass
\texttt{begin\_tx}; all application reads and writes occur while the lock is
held; the lock is released only after write-back.  The model therefore gives a
baseline refinement target: any optimistic backend that claims to implement the
same transaction should expose only histories equivalent to some SGL ordering.

Every invariant of this chapter is trivially true here --- the lock serialises
everything --- which is exactly why SGL is the reference design every optimistic
backend is checked against.  The companion repository's \texttt{SGL.tla} is this
model plus the opacity invariant, and it passes TLC.  Exercise~1 asks you to add
read-set validation to this model; the point is that even this ``obviously
correct'' design needs the check spelled out.  Contrast with the optimistic
designs of Part~IV: the moment the lock disappears, the invariants become
non-trivial and TLC earns its keep.

\section{Bug‑Injection and Counterexample Analysis}

A model that only passes is not yet persuasive.  We also want to know that the
invariant is sharp enough to fail when the protocol is damaged.  Bug-injection
does this deliberately: remove the validation guard, remove the commit-time
recheck, remove the ownership test, or allow a clock to move backwards.  TLC
should produce an invariant violation.  If it does not, either the mutation did
not matter or the invariant is too weak.

For optimistic TM, the most common injected bug is omitted read-set validation.
A transaction reads account~1, another transaction commits a transfer, and the
first transaction then reads account~2.  Without validation, the first
transaction may observe a snapshot that never existed in any serial execution.
The bank total may still be 20 in memory, but the transaction's local view is
not opaque.

A TLC counterexample is a schedule.  Read it from the initial state to the bad
state, not from the assertion failure backward.  The important questions are:
which process moved, which label executed, which shared variable changed, and
which earlier read became stale?  In the implementation, the same shape of bug
might appear as a rare fuzz failure.  In the model, it appears as a replayable
trace.

Mutation testing for models is practical and cheap.  For each backend family,
keep a small list of expected-failing edits: remove a read-set validation;
remove a lock-acquire guard; allow write-back without ownership; skip a
persistence or visibility step in the abstract protocol; omit the GPU
commit-log conflict-table update; or let one participant in distributed
two-phase commit publish without the commit decision.

The goal is not to simulate every low-level failure.  The goal is to test that
the abstraction can distinguish the correct protocol from nearby incorrect
ones.

\section{Worked Example: A TLC Configuration for BankSGL}

The PlusCal file is not the whole checked artifact.  TLC also needs a
configuration naming the specification, invariants, and any temporal properties.
For the finite bank model, the configuration is deliberately small.

\begin{lstlisting}[caption={A minimal TLC configuration for the SGL bank model.}]
SPECIFICATION Spec

INVARIANT
  TypeOK
  MoneyConserved
  FloorsHold

CHECK_DEADLOCK TRUE
\end{lstlisting}

The corresponding TLA+ definitions can live below the translated algorithm:

\begin{lstlisting}[caption={Invariant definitions for the checked bank model.}]
TypeOK ==
  /\ lock \in BOOLEAN
  /\ bal \in [Accounts -> Nat]
  /\ committed \in [1..2 -> BOOLEAN]

MoneyConserved == Total(bal) = 20

FloorsHold == \A a \in Accounts : bal[a] >= 0
\end{lstlisting}

The configuration is part of the proof artifact; without it, the word
``checked'' is underspecified.  \texttt{TypeOK} catches modelling errors that
may otherwise obscure the protocol failure.  Application invariants should be
named directly: here they are \texttt{MoneyConserved} and \texttt{FloorsHold}.

\section{Worked Example: A Stale Snapshot Mutation}

Here is the smallest useful NOrec mutation: commit after a changed clock without
checking the values again.  The code below is intentionally wrong.  It is a
model-testing tool, not a runtime design.

\begin{lstlisting}[caption={A deliberately broken NOrec-style commit action.}]
BrokenCommit ==
  /\ ok
  /\ ~commitLock
  /\ commitLock' = TRUE
  /\ IF r1 >= amount THEN
        /\ bal' = [bal EXCEPT ![1] = @ - amount,
                              ![2] = @ + amount]
        /\ clock' = clock + 1
     ELSE
        /\ bal' = bal
        /\ clock' = clock
\end{lstlisting}

The missing condition is the final value recheck:

\begin{lstlisting}[caption={The commit guard that the broken action omitted.}]
CommitRecheck ==
  /\ clock = snap
  /\ r1 = bal[1]
  /\ r2 = bal[2]
\end{lstlisting}

Timestamp equality alone is not the NOrec protocol; value validation is
the safety mechanism after interference.  The bad trace usually has only two
transactions: one reads, the other commits, then the first commits using stale
local values.  A useful model makes the wrong edit small enough to review in one
screen.

\section{Worked Example: Bank Transfer Under a Single Global Lock}
\index{bank transfer}\index{single global lock}\index{PlusCal}

The running bank example is a two-account transfer.  The model is intentionally
small: two accounts, two transactions, one unit transferred from account~1 to
account~2.  The interesting part is not the arithmetic; it is that the floor
and conservation checks are written at the same point where the runtime would
return success to the caller.

\begin{lstlisting}[caption={A complete PlusCal model of the bank transfer under SGL.}]
---- MODULE BankSGL ----
EXTENDS Naturals, TLC

Accounts == 1..2
Initial == [a \in Accounts |-> 10]
Total(b) == b[1] + b[2]

(*--algorithm BankSGL
variables
  lock = FALSE,
  bal = Initial,
  committed = [t \in 1..2 |-> FALSE];

process Tx \in 1..2
variables
  from = 1,
  to = 2,
  amount = 1,
  seen = 0;
begin
BeginTx:
  await lock = FALSE;
  lock := TRUE;

Read:
  seen := bal[from];

WriteBack:
  if seen >= amount then
    bal[from] := bal[from] - amount;
    bal[to] := bal[to] + amount;
    committed[self] := TRUE;
  end if;

Check:
  assert Total(bal) = 20;
  assert bal[1] >= 0 /\ bal[2] >= 0;

Commit:
  lock := FALSE;
end process;
end algorithm; *)
====
\end{lstlisting}

The assertions are local, but their meaning is global.  If either process can
return after losing money or driving an account below its floor, the model is
wrong.  Because the transfer is protected by a single lock, the only reachable
successful histories are serial: transaction~1 before transaction~2, or
transaction~2 before transaction~1.

The invariant is checked after write-back, not only at initialization.  The
lock makes the state space small enough that TLC explores all interleavings of
both transactions.  The model does not claim performance.  It claims that every
checked execution preserves the account floors and total money.  SGL is a
useful reference because every optimistic backend should refine the same
externally visible transfer behavior.

\section{Worked Example: NOrec-Style Validation for the Bank}
\index{NOrec}\index{validation}\index{opacity}\index{read set}

NOrec replaces ownership metadata with a global sequence clock and value-based
validation.  A reader records a snapshot and the values it observed.  If the
clock changes before commit, the read values must still match memory; otherwise
the transaction aborts.  The following model is deliberately finite and omits
allocation, privatization, and signal recovery.  It is the core validation
discipline.

\begin{lstlisting}[caption={A finite PlusCal model of NOrec-style value validation.}]
---- MODULE BankNOrecValue ----
EXTENDS Naturals, TLC

Accounts == 1..2
Initial == [a \in Accounts |-> 10]
Total(b) == b[1] + b[2]

(*--algorithm BankNOrecValue
variables
  commitLock = FALSE,
  clock = 0,
  bal = Initial;

process Tx \in 1..2
variables
  snap = 0,
  r1 = 0,
  r2 = 0,
  amount = 1,
  ok = FALSE;
begin
BeginTx:
  snap := clock;

Read1:
  r1 := bal[1];

Read2:
  r2 := bal[2];

Validate:
  if clock = snap then
    ok := TRUE;
  else
    ok := (r1 = bal[1] /\ r2 = bal[2]);
  end if;

Commit:
  if ok /\ r1 >= amount then
    await commitLock = FALSE;
    commitLock := TRUE;

    if clock = snap /\ r1 = bal[1] /\ r2 = bal[2] then
      bal[1] := bal[1] - amount;
      bal[2] := bal[2] + amount;
      clock := clock + 1;
    end if;

    assert Total(bal) = 20;
    assert bal[1] >= 0 /\ bal[2] >= 0;

    commitLock := FALSE;
  end if;
end process;
end algorithm; *)
====
\end{lstlisting}

This is not a full NOrec implementation.  It abstracts away memory barriers,
signal handling, allocation, Bloom-filter acceleration, and the concrete
write-set representation.  It keeps the safety core: a transaction may not
commit using a stale observation of the heap.

The first validation is a fast path: if the clock did not change, the read set
is still valid.  The second validation is the commit-time defense; removing it
is a standard bug-injection test.  Value validation compares the values read,
not only the timestamp, which is the point that distinguishes NOrec from a naive
global-clock scheme.  The model is small, but it captures the critical opacity
question: no transaction may commit after observing a mixed snapshot.

\section{The Complete Verification Workflow}
\label{sec:verify-workflow}
What ``we checked this with TLC'' means, end to end, so the claim is
reproducible rather than rhetorical:

\begin{enumerate}
    \item \textbf{Specify} the algorithm in PlusCal (a \texttt{--algorithm} block), with the correctness condition encoded as invariants (e.g.\ opacity via \texttt{InvNoMissedConflict}).
    \item \textbf{Add temporal properties} where liveness matters (a committed-transaction progress property under weak fairness).
    \item \textbf{Configure TLC}: a \texttt{.cfg} listing the model constants, the invariant, the optional \texttt{PROPERTY}, and a state bound so the checker terminates.
    \item \textbf{Run} \texttt{tlc} and read the state-count line --- \emph{how much} of the state space was explored matters as much as the absence of errors.
    \item \textbf{Inject a bug} (Section ``Bug-Injection'') and confirm the checker finds it: a test of a model that never fails is a test of the model's triviality.
    \item \textbf{Document the limits}: bounded state spaces and abstraction gaps (no call stack, no jmp-buffer lifetime) are what the model cannot see.
\end{enumerate}

The performance numbers reported elsewhere in the book are deliberately absent
from these models.  For example, the M1 Pro fuzz/bank measurements distinguish
NOrec-BF, NOrec, TL2, TSC-TM, and MVLog as engineering artifacts.  TLC checks a
different claim: whether the abstract protocol admits a forbidden history in a
bounded state space.  The two claims should reinforce each other, not replace
each other.

The workflow is the connective tissue between Part~III (formalism) and Part~IV
(runtimes): a backend ``is verified'' only in the sense of steps 1--6 above.

checks is the figure a reader sees.  Figure~\ref{fig:norec-validation-sm} is the

\section{Summary}

Model checking provides formal guarantees about TM algorithm correctness.  Even
simple TM designs can harbour subtle bugs that TLC exposes.  The model is not
the implementation; it is the executable argument that the implementation's
concurrency protocol has the advertised shape.  The useful models are small,
finite, and hostile: they should make wrong interleavings easy for TLC to find.

    \item The NOrec model can fail if it uses only timestamp validation without value‑based validation. Insert this bug and show the TLC output that reveals it.
    \item Specify a TM that uses eager locking and use TLC to find a deadlock scenario.
    \item \emph{[implementation]} Add a tiny C++ harness that runs the bank transfer under the repository's SGL and NOrec backends with two worker threads. Check the same two runtime assertions used in the models: total money is conserved and no account falls below its floor.
    \item \emph{[verification]} Mutate the protocol of Figure~\ref{fig:norec-validation-sm} by removing the commit-time recheck from \texttt{BankNOrecValue}. State the invariant that fails and summarize the shortest TLC counterexample trace.
    \item \emph{[theory]} Explain why lock exclusion alone is insufficient for opacity in an optimistic STM. Give a two-transaction history with a stale read, then identify which validation edge in Figure~\ref{fig:norec-validation-sm} must reject it.
    \item \emph{[implementation]} Run the repository's NOrec model
          (\texttt{docs/proofs/NOrec.tla}) with
          \texttt{make -C docs/proofs check-one BACKEND=NOrec} and record
          the state count.  Delete the commit-time recheck, rerun, and
          confirm TLC now finds the injected-bug counterexample.
    \item \emph{[verification]} Extend \texttt{BankSGL} to three accounts
          and a second transfer direction.  State
          \texttt{MoneyConserved} over all three balances and check
          \texttt{FloorsHold} for each account.
    \item \emph{[theory]} Explain why ``TLC passed'' on a finite model does
          not transfer to the C++ implementation automatically.  Name two
          abstraction gaps --- the call stack and \texttt{jmp\_buf}
          lifetimes (\S\ref{sec:jmpbuf-example}), and unbounded state such
          as the commit clock or the allocator --- that the model omits and
          the implementation still owns.
    \item \emph{[literature]} Read Lamport's \emph{The Temporal Logic of
          Actions} \cite{lamport94tla} and the first chapters of
          \emph{Specifying Systems} \cite{lamport02specifying}.  Identify
          which TLA+ features this chapter's models actually use
          (labeled actions, conjunction, \texttt{UNCHANGED}), which
          features the chapter deliberately avoids, and give one reason
          (state-space cost, readability) for avoiding them.
\end{enumerate}

\textbf{How to check your work.} The \emph{[verification]} exercises are
checked with TLC: put your model and configuration in
\texttt{docs/proofs/} and run
\texttt{make -C docs/proofs check-one BACKEND=YourModel} (commands in
Appendix~\ref{chap:pluscal-quick-ref}); for the bug-injection exercises,
confirm the checker fails on the damaged model before you restore it.  The
\emph{[implementation]} exercise is verified against the companion:
\texttt{make -C benchmarks/cpp BACKEND=sgl run-bank} and
\texttt{BACKEND=norec} run the same two-account transfer the models check.
The \emph{[theory]} exercises are graded against
\S\ref{sec:pluscal-example} and the workflow of \S\ref{sec:verify-workflow}.
The \emph{[literature]} exercise is graded on the accuracy of your feature
inventory and the plausibility of your stated reason for omitting the
features you name.
