\chapter{Programming Languages and Memory Semantics for TM}
\index{memory model}\index{atomic}\index{volatile}\index{compiler barrier}\index{ABI}\index{Rust}\index{borrow checker}\index{Send}\index{Sync}\index{UnsafeCell}\index{transaction-safe}\index{\_\_transaction\_atomic}\index{lost atomicity}

Transactional memory is only as strong as the language that surrounds it.
The programmer writes an atomic block over ordinary variables; the compiler
decides which of those variables are transactional; the runtime decides how
their accesses are tracked. Between the source text and the runtime sits a
memory model --- a contract about which reorderings the compiler and hardware
may perform --- and a set of ABI hazards that break silently when violated.

This chapter examines the language side of that boundary: \texttt{volatile},
inline assembly, atomics, the C/C++ memory model, and how Rust's ownership
rules both help and complicate TM. The running bank transfer appears
throughout as the case any of these mechanisms can break: a lost-update that a
different memory model would have prevented.

\section[C/C++ Memory Model and ABI Hazards]{C/C++ Memory Model and ABI Hazards: \texttt{volatile}, Inline Assembly, and Atomics}

A language-integrated TM is a boundary. The compiler decides which memory
operations are instrumented; the runtime decides which atomics and fences
implement the protocol. This section introduces the parts of C and C++ that
live on either side of that boundary.

\texttt{volatile} is the weakest tool. In C and C++, a volatile access is not
optimized away and is not reordered with respect to other volatile accesses in
the same thread, but volatile says nothing about ordering visible to other
threads. A volatile store can still sit in a store buffer and become visible to
other cores after later non-volatile operations. The compiler is prevented
from reordering the source-level access, but the hardware is not.

C11 and C++11 atomics are the real interface. The memory orderings form a
lattice: \texttt{memory\_order\_relaxed} gives atomicity with no ordering
guarantee; \texttt{memory\_order\_acquire} prevents subsequent reads from moving
before the atomic load; \texttt{memory\_order\_release} prevents prior writes
from moving after the atomic store; \texttt{memory\_order\_seq\_cst} provides a
single total order over all sequentially consistent atomic operations.
Acquire/release is usually sufficient for a TM runtime, and seq\_cst is often
more than needed.

The per-operation cost model matters. A software TM's read path does not need a
full hardware fence on x86 because the machine already preserves load-load
ordering. The backend can therefore emit a compiler fence,
\texttt{std::atomic\_\allowbreak signal\_fence}\allowbreak\texttt{(std::memory\_\allowbreak order\_seq\_cst)}, which prevents
the compiler from reordering the read around the barrier but costs zero CPU
cycles on the read path. The write/commit path, by contrast, needs a real
release fence so that the entire write-set becomes visible atomically. This
asymmetry is exactly the optimization made in the repository's Rust
\texttt{wbctl}, \texttt{wbetl}, and \texttt{wt} backends: acquire/release on
the commit path, compiler-only fences on the read path.

The TM read path is not a new idea. Lock-free readers and writers have used the
same atomics for decades. A lock-free reader loads with acquire, a writer
stores with release. A TM read is a lock-free read plus membership in a
transaction's read-set. The atomics are the same; the workload differs because
the TM runtime must also maintain metadata and validate the entire read-set at
commit.

ABI hazards are the practical edge. When instrumented and non-instrumented
code are mixed in one binary, the calling convention can silently corrupt
state. The classic trap in this repository was a DATA-vs-TEXT symbol
collision: the runtime exposed \texttt{tm\_sigsetjmp} as a function pointer in
a data symbol, while the compiler emitted a direct call to the symbol's
address. The generated code jumped to the pointer variable, not to the
function. The pitfalls chapter returns to this failure. The rule is simple:
every runtime hook that the compiler may call must be a real function symbol,
not a data symbol containing a pointer.

Figure~\ref{fig:language-tm-boundary} shows the intended boundary. The source
language marks an atomic block; the compiler pass decides, address by address,
whether an access is private or shared; the ABI hands shared accesses to the
runtime as ordinary function calls; and the runtime owns all atomics, fences,
and protocol state.

\section{Language Integration Case Studies}

The first two case studies in this section sit at opposite ends of the
integration spectrum. Rust integrates by \emph{ruling things out}: the
borrow checker removes data races before the program runs, and the TM
layer supplies only the multi-location atomicity that the type system
cannot prove. Annotation-based integration (GCC's
\texttt{\_\_transaction\_atomic}, this book's \texttt{[[tm::shared]]}
plugin) integrates by \emph{rewriting}: the compiler instruments the
accesses an annotation marks and hands them to the runtime. Reading the
two side by side makes the trade-off concrete: what each mechanism proves
at compile time, what it leaves to the runtime, and what breaks when the
contract is violated. The remaining subsections widen the lens: Haskell
and Clojure as worked contrasts --- languages that redesigned shared
state so that TM becomes the natural, indeed only, way to mutate it ---
then Scala and Python as library-level adoptions, and finally the
negative space: why JavaScript, PHP, and Kotlin never grew one.

\subsection{Rust: The Borrow Checker and TM}

Rust's borrow checker eliminates data races at compile time. A data race in
Rust is undefined behavior, and the type system refuses to compile code that
permits one. This is a stronger guarantee than C++ atomics can give: C++ can
prevent data races only if the programmer uses the right atomic operations
everywhere. Rust prevents whole classes of races by construction.

What remains unprotected is atomicity across multiple memory locations.
Ownership prevents two threads from mutably borrowing the same object, and
\texttt{Send}/\texttt{Sync} classify which values may cross thread boundaries.
But ownership does not prevent a thread from reading an account balance,
checking a floor, and then writing both balances in a way that another thread
observes as a partial update. That is lost atomicity, not a data race, and it
is exactly the property TM adds on top of the language.

\texttt{UnsafeCell} is the escape hatch. Interior mutability via
\texttt{UnsafeCell} or safe wrappers like \texttt{RefCell} lets a shared
reference provide mutable access through a runtime check. The type system can
prove that no data race occurs, but it cannot prove that a multi-step
transaction is atomic. An STM that instruments all loads and stores still
cannot protect against a data race involving \texttt{RefCell} without
additional runtime checks, because the instrumentation sees the memory access
but not the higher-level lock or borrow discipline.

The C++ and Rust stories are different in kind, not just degree. C++ gives the
programmer control over every memory order; Rust removes many hazards by
construction. A TM layer must therefore integrate with each differently: one
C++ ABI, one Rust trait boundary. The repository's Rust backends reuse the
same runtime core but wrap it in a trait that exposes a safe transactional
cell, leaving the unsafe interior to the runtime.

The companion's Rust API makes the split visible in three lines of client
code. A \texttt{TmCell<T>} owns a value that ordinary code cannot touch
(its contents are behind \texttt{UnsafeCell}); a \texttt{transaction}
closure receives a transaction handle whose \texttt{read}/\texttt{write}
methods are the only way in; and the runtime---selected at link time from
the same backend zoo as the C++ side---owns every fence and retry.
Listing~\ref{lst:rust-bank} is the bank transfer of this chapter's C++
examples, in safe Rust: no \texttt{unsafe} block appears anywhere in the
client, yet both balances update as one atomic unit or not at all.

\lstinputlisting[language=Rust, caption={The bank transfer in safe Rust
with the companion \texttt{tm} crate: atomicity without a single
\texttt{unsafe} block in client code.}, label={lst:rust-bank},
firstline=6, lastline=31]{listings/rust_bank_transfer.rs}

What the borrow checker proved here: no thread can read or write
\texttt{a} or \texttt{b} outside \texttt{transaction} (the cells' interiors
are inaccessible), and the cells may be shared across threads only because
\texttt{TmCell} is \texttt{Sync}. What it did \emph{not} prove: that the
two writes commit together. That is the runtime's obligation, and it is
discharged by the same OCC protocols as the C++ backends of Part~IV.

One design consequence deserves its own paragraph, because it is where Rust's
safety and TM's abort semantics collide. The C++ backends abort with
\texttt{sigsetjmp}/\texttt{siglongjmp} (\S\ref{sec:crash-without-opacity}
uses exactly that machinery): the jump unwinds the stack by force, running
no destructors. In C++ that is already a hazard we manage by convention; in
Rust it would be unsound by definition, because the language guarantees
\texttt{Drop} runs. So the companion's Rust runtime aborts differently: a
contention abort is a panic carrying a private \texttt{TmxAbort} payload,
unwound through the transaction body and caught by the
\texttt{catch\_unwind} inside \texttt{transaction()}; every local's
\texttt{Drop} runs on the way out, and a real user panic is re-raised rather
than swallowed as an abort. That single mechanism choice explains the shape
of the API: the transaction is a closure, not a begin/commit pair, because
an API that returns across frames needs an unwindable stack to be safe.
Appendix~\ref{chap:rust-mistakes} collects the further traps that live where
\texttt{unsafe} code, \texttt{Drop}, and TM aborts overlap.

\subsection{Language-Integrated Annotations for TM}

GCC's \texttt{\_\_transaction\_atomic} is the canonical example of a
language-integrated TM. The compiler instruments every load and store inside
the block, inserts begin and commit calls, and handles exceptions. The
programmer writes an atomic block and the compiler does the rest. GCC also
supports \texttt{transaction\_\allowbreak safe} and \texttt{transaction\_\allowbreak pure} function
attributes. A \texttt{transaction\_\allowbreak safe} function is instrumented when called
inside a transaction; a \texttt{transaction\_\allowbreak pure} function is not.

The C++ TM Technical Specification was an attempt to standardize this model.
It proposed \texttt{transaction\_safe} functions, atomic blocks, and a
transactional memory runtime interface. The committee ultimately dropped the
TS because the implementation burden was high, the performance on existing
hardware was unpredictable, and no vendor was willing to commit to the full
specification. The lesson is that language integration is a spectrum: the more
the compiler enforces, the more the language must promise.

This book's instrumentation plugin sits at the lighter end of that spectrum.
A \texttt{[[tm::\allowbreak shared]]} annotation marks a global as shared, and the
\texttt{LLVM\_\allowbreak TM\_\allowbreak ADDR\_CHECK} pass decides, address by address, whether an
access must be rewritten to a TM runtime call. The plugin does not promise
exception safety or nested-block handling. It promises only that shared
accesses inside an \texttt{atomic} block reach the runtime. The less the
compiler enforces, the more the runtime must prove.

\subsection{Haskell: The Pure Escape Hatch}
\index{Haskell}\index{GHC!STM monad}\index{retry}

Haskell has no mutable heap to instrument, and that absence turns the
integration question inside out. The language's concurrency story began with
Concurrent Haskell's message-passing processes \cite{peytonjones96concurrent};
its shared-mutable-state story landed later, as the \texttt{STM} monad in the
GHC runtime \cite{ghcstm} --- and it is the purest implementation of
transactional memory that exists, in the sense that transactional code has
nowhere else to touch.

\begin{lstlisting}[language=Haskell, caption={Bank transfer and blocking
audit in GHC's STM. \texttt{retry} aborts the transaction and registers the
read set as the wait set: \texttt{atomically (report a b)} suspends until some
transaction writes \texttt{a} or \texttt{b}.}, label={lst:haskell-stm}]
transfer :: TVar Int -> TVar Int -> Int -> STM ()
transfer from to amt = do
  f <- readTVar from
  if f < amt then retry
             else do writeTVar from (f - amt)
                     t <- readTVar to
                     writeTVar to (t + amt)

report :: TVar Int -> TVar Int -> STM (Int, Int)
report a b = do
  x <- readTVar a;  y <- readTVar b
  check (x >= 0 && y >= 0)   -- check c  ==  if c then return () else retry
  return (x, y)

main = atomically (transfer checking savings 10)
\end{lstlisting}

Three properties fall out of the type system rather than the runtime, and
they are exactly the guarantees Chapter~7 says a TM must buy for itself.

\begin{itemize}
\item \textbf{The observer boundary is language-enforced.} All shared mutable
state lives in \texttt{TVar}s, and the only way to read one is inside
\texttt{STM}, which only \texttt{atomically} can run. There is therefore no
privatization gap: no ordinary code path can observe uncommitted writes,
because uncommitted writes exist only in a transaction's local structure and
the language cannot express a load of that structure. The crash class of
\S\ref{sec:crash-without-opacity} is not ``prevented by the runtime'' in
Haskell; it is \emph{inexpressible}. The \texttt{unsafePerformIO} escape
hatch --- a pointer into the raw heap --- is precisely where GHC's own
documentation warns that STM guarantees evaporate: the boundary we drew for
databases in Figure~\ref{fig:db-tx-landscape} is, once again, the whole game.
\item \textbf{Blocking is transactional.} \texttt{retry} (Listing
\ref{lst:haskell-stm}) aborts, remembers the read set, and re-runs when any
read location is written. Waiting needs no locks, no condition variables, and
no lock-order discipline --- deadlocks from lock holding are structurally
impossible, and the wait-for set is the read set, which the runtime already
tracks. This is the mechanism Chapter~13 uses for GPU warp suspensions and
Chapter~15's retry model treats as validation failure with external
wake-up.
\item \textbf{Composition is substitution.} \texttt{STM} is a monad:
transactions compose by ordinary function application, and
\texttt{orElse} offers transactional disjunction --- try one, on
\texttt{retry} fall back with all state restored. Nesting that Chapter~2
flattened by hand comes for free because a composed \texttt{STM} block either
runs as one atomic unit or is discarded whole.
\end{itemize}

Implementation-wise, GHC's runtime is an optimistic multi-version STM that a
reader of Part~IV will recognize \cite{ghcstm}: each transaction keeps private
\emph{multi-version tokens} per \texttt{TVar}, reads need no locks, commit
takes a single global lock and bumps a commit clock, and abort simply
discards tokens. It resembles NOrec with per-location versioning --- same
promise (opaque serializability), similar cost structure (global serialization
point at commit). Haskell thus gives the book's cleanest existence proof that
strong semantics and a simple runtime coexist --- and it was obtained by
removing the shared heap, a move unavailable to C.

\subsection{Clojure: References, not Cells}
\index{Clojure}\index{ref (Clojure)}\index{io (Clojure)}

Clojure reaches the same summit from the other side: instead of removing the
mutable heap, it removes mutable \emph{values}. The language's reference type
\texttt{ref} points at an immutable value; transactions coordinate the
swapping of refs between immutable values \cite{clojurestm}. A half-built map
is not a thing that exists --- a value is built privately, then a ref points
at it at commit.

\begin{lstlisting}[caption={Transfer, blocking read, and the \texttt{io!}
discipline in Clojure.}, label={lst:clojure-stm}]
(def checking (ref 100))
(def savings  (ref 200))

(defn transfer [from to amt]
  (dosync                            ; transaction body
    (when (>= @from amt)             ; snapshot read
      (alter from - amt)
      (alter to   + amt))))

(defn balance-report [a b]
  (sync (refset-of a)                ; block until 'a' changes; no tx needed
    (println @a @b)))

(defn notify! [msg]
  (io! (println msg)))               ; io! THROWS if called inside dosync
\end{lstlisting}

The ladder of Chapter~7 places Clojure precisely: reads come from a
consistent snapshot; \texttt{alter} validates on write-write conflicts
(first updater wins); reads never abort a commit. That is snapshot isolation
--- write skew is admitted, and the language's own documentation says so ---
which is tolerable in Clojure for the reason \S\ref{sec:iso-not-in-tm} gives
for databases: observers never hold a pointer into the middle of a value, so
an anomaly yields a stale decision about an immutable thing, not a dangling
reference to a torn one. The design carries three lessons for the rest of
this book.

\begin{itemize}
\item \textbf{Values as snapshots.} Because refs swap between immutable
values, a reader's view is always internally consistent by construction ---
the mechanism behind Figure~\ref{fig:db-tx-landscape} in a language without
a server. Chapter~14's multi-version backends do the same trick per object;
Clojure does it globally by fiat of the type system (all values are
immutable; mutation is reassignment).
\item \textbf{Privatization by convention, enforced.} \texttt{io!}
(Listing~\ref{lst:clojure-stm}) declares ``this side effect must not run
speculatively'': executing it inside a transaction throws immediately, and
outside one it runs normally. Compare Chapter~2's privatization hazard --- a
C program \emph{hopes} it published safely; a Clojure program's publish
points announce themselves. The \texttt{!} naming convention on side-effecting
functions makes the transactional boundary a visible part of the API surface.
\item \textbf{Validation relaxation as a knob.} \texttt{commute} marks an
update as commutative (metadata counters, set inserts), exempting it from
the WW first-winner rule and reducing aborts at the price of weaker read
guarantees --- an explicit, programmer-facing dial between the rungs of
Figure~\ref{fig:iso-ladder}, in a language whose default is near its top.
\end{itemize}

\subsection{Scala and Python: Library STM Where the VM Removed the Excuse}
\index{Scala}\index{Python}\index{pySTM}

Two more languages host transactional memories as libraries, and their
histories explain exactly when STM gets adopted rather than designed in.
Scala's \texttt{scala.concurrent.stm} puts shared state in \texttt{Ref}
cells with an \texttt{atomic \{ \}} block; reads validate lazily, and
\texttt{orRetry} provides the blocking idiom of Listing
\ref{lst:haskell-stm} inside an imperative host. It never became Scala's
default concurrency story --- the ecosystem went to message passing
(actors) --- but its \emph{transformer} API, which passes the current value
through a function rather than computing new values from separately-read
ones, remains the cleanest expression of commutative updates anywhere.

Python's case is a controlled experiment. CPython's global interpreter lock
makes cross-thread mutation of plain objects ``accidentally'' sequenced, so
STM answers no question there; Jython and IronPython run threads natively,
have no GIL, and carry no built-in lock --- and exactly those dialects grew
\texttt{pySTM} \cite{pystm}: decorators marking transactional classes,
\texttt{with transaction():} blocks, optimistic validation with the usual
retry semantics. STM appeared precisely where shared mutable state first
became real. It is the same lesson Haskell and Clojure teach from the
opposite direction: transactional memory is the shared-mutable-state
technology, and a language adopts it at exactly the rate that it commits to
sharing mutable state.

\subsection{The Negative Space: JavaScript, PHP, and Kotlin}
\index{JavaScript}\index{PHP}\index{Kotlin}\index{STM!absent from languages}

No mainstream JavaScript, PHP, or Kotlin runtime offers transactional memory,
and the absence is not lag --- it is diagnosis. STM answers three questions
that must all be present: threads share memory; values are mutable in place;
the programmer needs multi-location atomicity as a primitive. JavaScript and
PHP answer away the first: their concurrency models are event loops and
message passing (Web Workers post messages; SharedArrayBuffer exists for
atomics, but the ecosystems standardized on passing snapshots, not sharing
mutation). Kotlin answers away the third for the same reason Clojure does,
in reverse: coroutines and channels give structured confinement, so the
need to share mutated state across threads is designed out at the
programming-model level, and the JVM's stdlib carries no STM to import.
The languages that grew STM (Haskell, Clojure, Java briefly via libraries
and the C++ TS attempt) share one property: they kept mutable shared state
and needed a discipline for it. The ones that never grew it removed the
state, the sharing, or the need. A book about STM should be able to say what
it is \emph{not} for, and these three are the answer.

\section{Worked Example: Atomic Operations for a Counter}
\label{sec:atomics-example}

A shared counter is the smallest TM-relevant program. The three
synchronisation styles on the same three lines of logic show exactly what the
language boundary buys.

\begin{lstlisting}[language=C, caption={A shared counter three ways: lock,
atomic, and transactional.}, label={lst:counter-three-ways}]
#include <pthread.h>
#include <stdatomic.h>
#include <stdio.h>

static pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;
static int counter_lock = 0;
static _Atomic int counter_atomic = 0;
static int counter_tm = 0;

void increment_lock(void) {
    pthread_mutex_lock(&lock);
    counter_lock++;
    pthread_mutex_unlock(&lock);
}

void increment_atomic(void) {
    atomic_fetch_add_explicit(&counter_atomic, 1, memory_order_relaxed);
}

void increment_tm(void) {
    __transaction_atomic {
        counter_tm++;
    }
}

int main(void) {
    for (int i = 0; i < 1000; ++i) {
        increment_lock();
        increment_atomic();
        increment_tm();
    }
    printf("lock=%d atomic=%d tm=%d\n",
           counter_lock, atomic_load(&counter_atomic), counter_tm);
    return 0;
}
\end{lstlisting}

The atomic version exposes which ordering to use per operation:
\texttt{memory\_order\_relaxed} says that atomicity is enough and no ordering
is required. The TM version hides the whole protocol. The runtime still needs
the right atomics internally, but it puts them behind one API, as Part~IV
shows. Composability reappears here: two counters in one \texttt{atomic} block
compose, because the transaction names both accesses and the runtime
serializes the pair. Two separate \texttt{atomic\_fetch\_add} calls do not
compose: each is atomic by itself, but the pair is not.

Rust states the same three-way choice with the borrow checker standing
guard over each door. In Listing~\ref{lst:counter-rust} the mutex wrapper
makes the critical section unmissable, the atomic makes the ordering an
explicit argument at each call, and the TM path is the only one that can
touch \emph{two} cells in one indivisible step---try extending the first
two styles to increment a second counter together with the first and the
lost-update window opens immediately, while the transaction closure keeps
the pair atomic by construction.

\begin{lstlisting}[language=Rust, caption={The shared counter three ways
in Rust: lock, atomic, and transaction (companion \texttt{tm} crate).},
label={lst:counter-rust}]
use std::sync::{Arc, Mutex};
use std::sync::atomic::{AtomicI32, Ordering::Relaxed};
use tm::{TmCell, transaction, tm_init, tm_exit, tm_init_thread,
         tm_exit_thread};

fn main() {
    tm_init();
    let lock = Arc::new(Mutex::new(0_i32));   // way 1: lock
    let atomic = AtomicI32::new(0);            // way 2: atomic
    let cell = Arc::new(TmCell::new(0_i32));   // way 3: transaction

    let mut handles = Vec::new();
    for _ in 0..4 {
        let (lock, cell) = (lock.clone(), cell.clone());
        handles.push(std::thread::spawn(move || {
            tm_init_thread();
            for _ in 0..1000 {
                *lock.lock().unwrap() += 1;
                atomic.fetch_add(1, Relaxed);
                transaction(|tx| {
                    let v = tx.read(&cell);
                    tx.write(&cell, v + 1);
                });
            }
            tm_exit_thread();
        }));
    }
    for h in handles { h.join().unwrap(); }

    assert_eq!(*lock.lock().unwrap(), 4000);
    assert_eq!(atomic.load(Relaxed), 4000);
    let total = transaction(|tx| tx.read(&cell));
    assert_eq!(total, 4000);
    tm_exit();
}
\end{lstlisting}

\section{Worked Example: ABI-Safe Bank Transfer}
\label{sec:abi-safe-bank-transfer}

The following example is deliberately an SGL-style TM. Its purpose is not
performance but the language boundary. The runtime exports functions, not
data symbols containing function pointers. Instrumented code calls those
functions and lets the runtime choose atomics and fences internally.

\begin{lstlisting}[language=C++, caption={A compilable C++ TM facade for the
bank-transfer invariant.}, label={lst:abi-safe-bank}]
#include <array>
#include <atomic>
#include <cassert>
#include <cstddef>

struct Account { int balance; };

static std::array<Account, 2> bank = { Account{100}, Account{100} };
static std::atomic_flag g_lock = ATOMIC_FLAG_INIT;

extern "C" void tm_begin() {
    while (g_lock.test_and_set(std::memory_order_acquire)) {
        // spin
    }
}

extern "C" void tm_commit() {
    g_lock.clear(std::memory_order_release);
}

extern "C" int tm_read_i32(const int *addr) {
    std::atomic_signal_fence(std::memory_order_seq_cst);
    return *addr;
}

extern "C" void tm_write_i32(int *addr, int value) {
    std::atomic_signal_fence(std::memory_order_seq_cst);
    *addr = value;
}

class TxGuard {
public:
    TxGuard() { tm_begin(); }
    ~TxGuard() { tm_commit(); }
};

bool transfer(int from, int to, int amount, int floor) {
    TxGuard guard;
    int bal_from = tm_read_i32(&bank[from].balance);
    int bal_to = tm_read_i32(&bank[to].balance);
    if (bal_from - amount < floor || bal_to < floor) {
        return false;
    }
    tm_write_i32(&bank[from].balance, bal_from - amount);
    tm_write_i32(&bank[to].balance, bal_to + amount);
    return true;
}

int total_money() {
    TxGuard guard;
    int total = 0;
    for (const auto &acct : bank) {
        total += tm_read_i32(&acct.balance);
    }
    return total;
}

int main() {
    assert(transfer(0, 1, 10, 0));
    assert(transfer(1, 0, 5, 0));
    assert(total_money() == 200);
    assert(bank[0].balance == 95);
    assert(bank[1].balance == 105);
    return 0;
}
\end{lstlisting}

The acquire on \texttt{tm\_begin} and release on \texttt{tm\_commit} publish
the critical section. The per-access fences only constrain the compiler: they
prevent the compiler from hoisting the load or sinking the store across the
runtime call, but they do not issue CPU barriers. The source-level transaction
is compositional: the floor check and both writes are one unit. The ABI
contract is visible: instrumented code calls \texttt{tm\_read\_i32} and
\texttt{tm\_write\_i32}; non-instrumented code must not bypass shared state.
This is the semantic baseline implemented by SGL and TSX-SGL before more
selective protocols such as NOrec, TL2, and TSC-TM reduce contention.

\section{Worked Example: Model Checking Lost Atomicity}
\label{sec:tla-bank-language-contract}

Language support for TM should preserve the same invariant as the runtime: the
transfer either commits as one state transition or has no effect. The
following TLA+ model captures that contract without mentioning cache lines,
fences, or calling conventions.

\begin{lstlisting}[language={}, caption={A TLC-checkable TLA+ model of an
atomic bank transfer with money-conservation and floor invariants.},
label={lst:bank-tm-atomicity}]
---- MODULE BankTMAtomicity ----
EXTENDS Naturals, TLC

CONSTANTS A0, A1, Floor, Amount

VARIABLES bal, pc
vars == <<bal, pc>>

Init ==
/\ bal = [i \in {0,1} |-> IF i = 0 THEN A0 ELSE A1]
/\ pc = "idle"

CanTransfer ==
/\ pc = "idle"
/\ bal[0] >= Floor + Amount

Begin ==
/\ CanTransfer
/\ pc' = "active"
/\ bal' = bal

Commit ==
/\ pc = "active"
/\ bal' = [bal EXCEPT ![0] = bal[0] - Amount,
![1] = bal[1] + Amount]
/\ pc' = "idle"

Abort ==
/\ pc = "active"
/\ bal' = bal
/\ pc' = "idle"

Idle ==
/\ pc = "idle"
/\ bal' = bal
/\ pc' = "idle"

Next ==
\/ Begin
\/ Commit
\/ Abort
\/ Idle

InvMoney ==
bal[0] + bal[1] = A0 + A1

InvFloor ==
/\ bal[0] >= Floor
/\ bal[1] >= Floor

Spec == Init /\ [][Next]_vars

THEOREM Spec => []InvMoney /\ []InvFloor
====
\end{lstlisting}

A minimal configuration sets \texttt{A0 = 10}, \texttt{A1 = 10},
\texttt{Floor = 0}, and \texttt{Amount = 3}. The model treats the transaction
body as one commit transition; this is the property language integration must
preserve. \texttt{InvMoney} catches partial instrumentation: if the debit and
credit are exposed as two separate visible actions, the conservation invariant
fails on the intermediate state. \texttt{InvFloor} catches a misplaced check:
the account floor must be tested in the same atomic unit as the debit. The
model abstracts away C++ and Rust details; those details re-enter at the ABI
and trait boundaries.

\section{Summary}

Different languages offer different levels of memory-ordering control. C and
C++ hand the programmer the full set of atomics and ordering choices. Rust
removes data races at compile time but does not restore multi-location
atomicity. A type system that prevents data races still cannot enforce
atomicity across multiple memory locations without TM support; the Rust
listings of this chapter (Listings~\ref{lst:rust-bank}
and~\ref{lst:counter-rust}) show where the language's guarantees end and
the runtime's begin. The survey subsections add the contrast case: Haskell
and Clojure reach opacity-like safety by \emph{redesigning shared state} ---
no raw heap, or immutable values behind refs --- making the crash class of
\S\ref{sec:crash-without-opacity} inexpressible rather than merely prevented,
while Scala and Python show library STM appearing exactly where shared mutable
state becomes real, and JavaScript, PHP, and Kotlin show what its absence
means: the questions were designed away first.

The key takeaway for the rest of the book is that the language integration is
a boundary. The compiler decides what is instrumented; the runtime decides how
the protocol is implemented. Each language integration re-balances the proof
obligation between them. GCC enforces a lot; this book's plugin enforces only
the address-space rule; the runtime must prove the rest. Chapter~5 moves into
the formal foundations that let us state those proofs precisely.

\section{Exercises}

\begin{enumerate}
\item \emph{[theory]} In C, a compiler hoists a read of \texttt{x} out of
an \texttt{atomic} block because it thinks \texttt{x} is thread-local.
Explain how \texttt{volatile} or an \texttt{asm} barrier can prevent
this, and what the runtime cost is.

\item \emph{[theory]} A Rust program uses \texttt{RefCell}. Explain why an
STM that instruments all loads and stores still cannot protect against
a data race without additional runtime checks.

\item \emph{[implementation]} Compare the programming effort required to
add a thread-safe counter using locks, atomics, and a TM in C++ and
Rust. Start from the C++ version in Listing~\ref{lst:counter-three-ways}
and the Rust version in Listing~\ref{lst:counter-rust}, then extend
both so that a second counter is incremented in the \emph{same}
indivisible step as the first. Which of the six combinations composes
without further machinery, and why?

\item \emph{[implementation]} Extend the ABI-safe bank-transfer example of
Listing~\ref{lst:abi-safe-bank} with a second shared object,
\texttt{transfer\_count}. Update it inside the same transaction as the
two account balances. Then write a non-transactional version using
three separate atomics and identify an interleaving that preserves each
individual atomic operation but violates the intended compound
invariant.

\item \emph{[verification]} Modify the TLA+ model in
Listing~\ref{lst:bank-tm-atomicity} by splitting \texttt{Commit} into
two transitions, one debit and one credit. Run TLC on the finite model
and record the shortest counterexample to \texttt{InvMoney}. Explain
which source-level compiler or ABI mistake the split transition
represents.

\item \emph{[theory]} Compare a C++ TM API based on explicit
\texttt{std::memory\_order} parameters with a Rust API based on a
\texttt{TxCell<T>} wrapper. For each API, state what the type system
proves, what the runtime must still validate, and where unsafe escape
hatches can break atomicity.

\item \emph{[verification]} Add an \texttt{Abort} action to the TLA+ model
that can happen from \texttt{active} and leaves the balances unchanged.
Check that \texttt{InvMoney} and \texttt{InvFloor} still hold. Explain
why the model has no partial state during \texttt{Commit}.

\item \emph{[literature]} Read Blundell, Lewis, and Martin's
\emph{Subtleties of Transactional Memory Atomicity Semantics}
\cite{blundell06subtleties}.  The chapter's \emph{[theory]} exercises
distinguish weak from strong atomicity; the paper refines that
distinction into several concrete atomicity properties.  Choose one
property from the paper, restate it in this chapter's terminology, and
give one program that the property protects that plain opacity of the
\texttt{atomic} block does not.

\item \emph{[theory]} Haskell and Clojure both make the crash class of
Section~\ref{sec:crash-without-opacity} inexpressible, by opposite means:
Haskell removes the mutable heap, Clojure removes mutable values. For each
language, name the feature that plays the role of the database's protocol
boundary, and explain why neither mechanism can be retrofitted onto a C
program by runtime cooperation alone. Then identify the one escape hatch in
each language (one per language) through which the crash class re-enters, and
what it costs the programmer.
\end{enumerate}

\textbf{How to check your work.} The \emph{[implementation]} exercises are
verified with the companion: extend Listing~\ref{lst:abi-safe-bank} with
\texttt{transfer\_count} and compare the C++ and Rust counter wrappers of
Exercise~3.  The \emph{[verification]} exercises are checked with TLC against
Listing~\ref{lst:bank-tm-atomicity} (\texttt{InvMoney}, \texttt{InvFloor}; see
Appendix~\ref{chap:pluscal-quick-ref}).  The \emph{[theory]} exercises are
graded against \S\ref{sec:atomics-example}.  The final \emph{[theory]}
exercise is graded against \S\ref{sec:iso-not-in-tm}: the boundary analysis
there is the model answer.  The \emph{[literature]}
exercise is graded on the accuracy of your restatement: the chosen
property must be a real one from the paper, and your counterexample must
be one the property (and not plain block opacity) protects.
