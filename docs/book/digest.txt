FRONT: Preface
============================================================
Assumed background.
  * Computer architecture: caches, cache coherence, out-of-order execution (one semester).
  * Operating systems / concurrency: threads, locks, semaphores, atomics.
  * Compilers: a first course; the essential material is recapped in Part III.
  * Discrete mathematics and basic probability for the modeling parts (Parts IV and V).
How to read this book.
  * Parts I-II motivate TM and ground it in real hardware; readers with a strong OS/architecture background may skim them.
  * Parts V and VII (formal verification and runtime designs) are the conceptual core.
  * Part III (compilers) and Part IV (mathematics) are self-contained detours; their notation is reused later.
  * A one-semester course could cover Parts I, VII, VIII, and V; a full course adds III, IV, IX, and X.
  * A single running example - a two-account transfer() - threads through the book: it appears as locked code in Chapter 1, as an API call in Chapter 10, and as the test case for every runtime in Chapter 12.
The companion codebase.
  * This book is written against a working repository: 20+ STM backends, an LLVM instrumentation plugin, TLA+/PlusCal models, the STAMP benchmarks, and GPU backends.
  * Exercises are tagged [implementation] (write code), [verification] (write a TLA+ model), or [theory] (prove or derive) so instructors can mix them.
  * Every runtime design in Part VII exists as buildable code and as a model-checked TLA+ specification.
Getting the code running.
  * The full toolchain instructions live in the Development Environment Setup chapter at the back; the minimum you need for most chapters is: make in the repository root (builds the backends and benchmarks), a recent clang/g++ with C++17, and java plus the tla2tools.jar for the model-checking exercises.
  * Exercise tracks: the tags let you follow one coherent path end-to-end. The implementer track (all [implementation]) builds a runtime of each family; the verifier track (all [verification]) builds a PlusCal/TLA+ model for each design; the theory track (all [theory]) carries the opacity and performance arguments across chapters. Each track's exercises are cumulative - later ones reuse the artifacts of earlier ones.

CHAPTER: The Locking Crisis
============================================================

== The Cost of Mixing Synchronization with Logic ==
  * Real-world examples: deadlocks, priority inversion, lost wake-ups.
  * The tangling problem: concurrency control is scattered across the application.
  * Readability, maintainability, and composability suffer.
  * Three failure modes worth distinguishing: deadlock (no progress), livelock/starvation (no fairness), and data races (incorrectness).
  * Locking contracts are invisible: the compiler, the type system, and the reader cannot see which lock guards which variable.
  * Error-prone patterns: check-then-act, test-and-set loops, nested locking, lock order inversion between modules.
  * Heisenbugs: concurrency bugs reproduce only under specific interleavings, making them the costliest class of bugs in industry.
  * Hidden costs beyond correctness: lock contention reduces parallelism, and coarse locking trades away scalability (Amdahl's law, revisited in Part VII).

== Composability – The "Innocent Change" Problem ==
  * A small modification in one module breaks the locking protocol of another.
  * Lock-based code is not composable; the whole call chain must obey the same locking order.
  * The appeal of a declarative atomic block.
  * Classic worked example: a thread-safe List and a thread-safe Map; transferring an element between them requires locking both with a consistent global order.
  * The "innocent change": adding one more field to a record silently inserts a second lock into a previously single-lock code path.
  * Two independently correct modules can be combined into a deadlocking program - no amount of local reasoning prevents it.
  * Nesting should be free: atomic blocks inside atomic blocks should compose by flattening rather than by a new locking protocol.
  * TM removes the lock-order obligation: conflicts are detected at runtime on the accessed data, not by programmer-chosen lock order.

CHAPTER: Transactions: From Databases to Shared Memory
============================================================

== ACID and Serializability ==
  * Database transactions: Atomicity, Consistency, Isolation, Durability.
  * Serializability as the gold standard for isolation.
  * Why serializability is not directly transferable to in-memory concurrent programming.
  * Database mechanisms we will reuse: version clocks, read/write sets, validation, write-ahead logging.
  * The database-to-STM mapping: databases use disk-based logging and two-phase locking (2PL); STM replaces both with in-memory metadata and optimistic validation.
  * Isolation levels (read committed, repeatable read, serializable) as a spectrum; TM typically targets the strongest end (opacity).
  * In-memory difference: no durable media, no disk costs - the cost centre shifts from I/O to coherence traffic and validation.

== Data Hazards and Memory Models ==
  * Write-after-read, read-after-write, write-after-write hazards.
  * Sequential consistency vs. relaxed memory models (TSO, RMO).
  * How memory models affect the visibility of transactional writes.
  * The three classical hazard classes (RAW, WAR, WAW) and how each maps to a transactional conflict.
  * A transaction is really a sequence of hazards against other threads; concurrency control must resolve them consistently.
  * Why relaxed models (TSO on x86, weak on ARM/GPUs) force TM implementations to insert fences; revisited from a compiler and runtime perspective in Parts II, VII, and X.
  * The happens-before relation as the formal backbone for reasoning about visibility of committed writes.

== TM Semantics: Opacity, Sandboxing, Privatization ==
  * Opacity: even aborted transactions must see a consistent view.
  * The privatization anomaly: why serializability fails when transactions publish objects.
  * Sandboxing: why speculative writes must not leak outside a transaction.
  * Serializability vs. opacity: a history can be serializable while an aborted reader still observes an inconsistent partial state - opacity closes that gap.
  * Opacity also subsumes weak vs. strong atomicity debates via a single formal condition.
  * Privatization: handing an object from a transactional context to a non-transactional one must publish a consistent version; naive STMs corrupt it.
  * Sandboxing: instrumentation, not hardware, must guarantee that accesses outside a transaction are never redirected to speculative state.
  * The three conditions are the yardstick used to model-check every backend in Part V (see, e.g., the InvNoMissedConflict invariant of Part X).

CHAPTER: Hardware Concepts for Transactional Memory
============================================================

== Multicore Architectures and Memory Hierarchies ==
  * Shared memory, caches (L1/L2/L3), cache coherence (MESI).
  * The coherence protocol as a natural conflict‑detection substrate.
  * MESI states and transitions: a cache line invalidated by another core is, from a TM viewpoint, a conflict signal.
  * Snooping vs. directory‑based coherence, and a first look at why coherence does not exist across GPU SMs (Part X).
  * Word vs. cache‑line granularity of conflict detection: where false conflicts come from (Part IX).

== Out-of-Order Execution and Speculation ==
  * Instruction pipelines, reorder buffers, branch prediction.
  * Speculative stores and why they can be squashed.
  * The reorder buffer holds register state, not data; hardware TM must own speculative data in the cache.
  * Capacity limits: the transaction working set is bounded by L1; larger transactions need software transactions or fallback.
  * The parallel between branch misprediction recovery and transactional abort.

== Store Buffers and Memory Ordering ==
  * Store buffer; memory consistency models defined via two-thread litmus tests.
  * Sequential consistency (Lamport): one global order, no anomalies, no commercial SC machine.
  * Total Store Order (x86-64, SPARC): the store buffer is the only reordering source (store-then-load pair only); the store-buffering (Dekker) litmus anomaly; torn multi-word views; mfence fix.
  * Relaxed models of ARM and POWER: all four pairs reorderable; barriers (dmb, sync/lwsync/isync), ldar/stlr, dependencies; message-passing litmus anomaly; IRIW; POWER8 HTM backend tie-in (backends/tm_impl/power8_htm).
  * Other models: RISC-V RVWMO cousin; GPU coherence scopes (Ch.17); C11/C++11 atomics as the portable contract.
  * Litmus summary table: SB/MP/IRIW outcomes under SC, TSO, ARM/POWER.
  * The commit-publish fence: a transaction's write‑back must become visible in one atomic step to other cores.
  * Compiler fences (atomic_signal_fence) vs. hardware fences (mfence, dmb): eliminating the CPU barrier on the read path (Part VII).
  * Fence placement as a correctness issue, not a tweak: wrong placement reopens the commit-visibility window.

== C/C++ Memory Model and ABI Hazards: volatile, Inline Assembly, and Atomics ==
  * volatile only prevents compile‑time reordering, not CPU reordering.
  * C11/C++11 atomics and memory ordering (relaxed, acquire, release, seq_cst).
  * How compiler barriers can replace costly full fences inside a TM.
  * The per-operation cost model in STM backends: which ordering each read/write actually needs, and how backends downgrade seq_cst to compiler_fence(SeqCst) on the read path.
  * Comparing the TM read path to lock-free readers/`-writer patterns: same atomics, different workload.
  * ABI hazards specific to C/C++ TM integration: calling-convention mismatches between instrumented and non-instrumented functions, and the DATA-vs-TEXT symbol traps that arise when a runtime exposes hooks as function pointers rather than functions (see the pitfalls chapter).

== Language Integration Case Studies ==

-- Rust: The Borrow Checker and TM --
  * The borrow checker eliminates data races at compile time.
  * UnsafeCell and interior mutability: what remains unprotected.
  * How Rust’s safety guarantees can reduce (but not eliminate) the need for TM instrumentation.
  * Rust's guarantees eliminate data races but not deadlocks or lost atomicity - the very guarantees TM adds on top of the language.
  * Sync/Send traits as a way to reason about which values can be shared across threads; TM reifies "shared mutable" safety at runtime instead of compile time.
  * The C++ and Rust stories are different in kind, not just degree: C++ gives the programmer control over orderings; Rust removes whole classes of hazard at compile time. A TM layer must therefore integrate with each differently - one C++ ABI, one Rust trait boundary.
  * Safe Rust bank transfer with the companion tm crate (TmCell/transaction): no unsafe in client code; the type system proves access safety, the runtime owes atomicity.

-- Language‑Integrated Annotations for TM --
  * GCC’s __transaction_atomic and transaction_safe / transaction_pure attributes.
  * The (abandoned) C++ TM Technical Specification: transaction-safe functions, atomic blocks, and why the committee ultimately dropped it.
  * Research proposals like @atomic blocks.
  * This book's instrumentation plugin: a [[tm::shared]] annotation on globals, and the LLVM_TM_ADDR_CHECK threshold deciding when instrumentation is actually needed.
  * The three case studies (GCC, the C++ TS, this book's plugin) are a spectrum of how much the language commits to: the less the compiler enforces, the more the runtime must prove.

== Parser Generators: From Yacc to Modern Tools ==

CHAPTER: Compiler Optimizations and Their Impact on TM
============================================================

== Common Optimizations ==
  * Dead‑store elimination (DSE), loop‑invariant code motion (LICM), common subexpression elimination (CSE).
  * Each can silently break transactional semantics by eliminating or reordering instrumented accesses.
  * The root problem: most optimizers assume a single-threaded execution model and treat memory accesses as opaque only when told to.
  * Optimizations inside a transaction must be rerun after instrumentation, not before, or the pass rediscovers and undoes TM calls.
  * Stack versus shared memory: it is safe to optimize stack accesses aggressively; shared/global accesses inside a transaction are the only dangerous ones.

== Worked Example: Two Optimizations That Break TM ==

  * Both are correct under single-threaded semantics and both are wrong for TM: the write must reach the write-set, and the read must see fresh data each iteration.
  * The fix is the contract of the next section: tm_clobber and the rule that instrumentation runs after optimization.
  * These are exactly the "mismatch bugs seen in the wild" of the next section - pass reordering and dead-store elimination of speculative writes.

== The Instrumentation Contract ==
The precise, mechanical rules a compiler pass and a TM runtime agree on.
This section turns the previous section's warnings into a checkable list.
  * Which accesses are instrumented. Heap and shared-global memory operands inside a transaction are rewritten to tm_read_*/tm_write_* calls; stack-locals bypass via LLVM_TM_ADDR_CHECK. The [[tm::shared]] annotation (Chapter 4) is the source-level way to put a global on the instrumented side.
  * Which are exempt. Accesses that provably target the current thread's stack, addresses registered in the runtime's TM-global registry, and operations in uninstrumented (e.g. transaction_pure) callees are left untouched.
  * What metadata is preserved. The pass must not lose the address-space classification or the width of each access - the call name itself (i4 vs. i8) encodes both, so type-preserving rewrites are mandatory.
  * Pass ordering. Instrumentation is the last memory-affecting pass: anything that eliminates or reorders memory operations must run before it. Running DSE or LICM after instrumentation silently discards read-set/write-set side effects (Section sec:optim-example).
  * Barriers for the optimizer. Calls to tm_read_*/tm_write_* are opaque side-effecting calls - they must be marked tm_clobber-equivalent so the optimizer never treats them as pure loads/stores.

== Contract Between Programmer and Compiler ==
  * What the programmer must protect (via transaction_safetransaction_pure annotations).
  * Compiler intrinsics like tm_clobber that inform the optimizer of transactional side effects.
  * The annotation contract is the C++ TM TS's central lesson: without a language-level notion of "transaction", the compiler cannot keep its promises.

== Summary ==

  * A TM‑aware compiler must disable or constrain certain optimizations within transactional regions.

  * Shared memory and stack memory must be classified before rewriting; optimizing both under the same rules is either slow or wrong.

== Language‑Integrated Keywords ==
  * GCC’s __transaction_atomic and its implicit instrumentation.
  * How keywords can simplify the programmer’s view.

== Asynchronous and Future‑Based APIs ==
  * Pushing transactions into work queues.
  * Transactional futures: submitting a transaction as a future, awaiting results.
  * Batching and potential for optimisation.
  * The executor model: worker threads consume transaction closures from a queue; transactions become units of work, not thread-stack entities.
  * Pipeline implications: with async execution, stack-address checks and thread-entry initialization become per-task concerns, not per-thread.
  * Composing futures preserves the composability argument of Chapter 1: an atomic closure is just another value.

== Single Global Lock TM ==
  * Implementation sketch: acquire global lock at tm_begin, release at tm_commit.
  * Properties: correct, no rollbacks, trivially opaque.
  * Performance analysis: serialisation bottleneck, Amdahl’s law.
  * The `correct-by-construction' yardstick: every more powerful STM must degrade gracefully toward SGL under contention.
  * The stub-vs-real-hooks subtlety: during single-threaded init a TM must still route tm_malloc/tm_read through the real backend, or validation is silently disabled (a real bug fixed in the companion repo).
  * The PlusCal/SGL model of Part V as the reference execution - one process, one lock, no surprises.
  * Thread-serializer / queue-based TM (below) is SGL with the lock replaced by a work queue; it eliminates lock contention but adds submission overhead.
Amdahl's law gives the first-order bound.
S_ = 1 f + 1-f N
where (f ) is the non-parallel fraction and (N ) is the number of cores.

== Thread‑Serializer / Queue‑Based TM ==
  * A single worker thread executes transactions sequentially from a lock‑free queue.
  * How this design eliminates contention on the lock but introduces submission overhead.
  * Loss of thread-locality: transaction descriptors must be per-task, since work migrates across threads.
  * The moral for later chapters: SGL is the baseline; every speculative design's job is to beat it without losing its guarantees.
A serializer is not merely an optimization of SGL.

== NOrec: Value‑Based Validation ==
  * Read‑set tracking via timestamps, write‑set buffering.
  * Validation on every read and at commit time.
  * PlusCal model and key invariants.
  * Why `no ownership records': NOrec's write-set holds raw values, validated against a global sequence clock instead of per-location locks.
  * The read-validate discipline: capture the clock, read the value, re-check the clock - the same capture read recheck pattern that prevents partially-visible writes (Part IX hardware echo).
  * The invisible-it-committed trap: without value re-reading in validation, a concurrent commit between last read and commit sneaks a stale snapshot through (a real bug class fixed in the companion repo).
  * Comparison layout: NOrec has the smallest metadata footprint of the in-memory STMs; validation cost grows with read-set size.
  * Bloom-filter variant (NOrec-BF): a write-set bloom filter lets most reads skip read-set admission entirely - read-mostly speedup at the cost of rare false positives.

== TL2: The Textbook Global-Clock STM ==
  * Global version clock read at begin; snapshot = transaction's start time.
  * Write-set of (address, value) with per-location version metadata; read-set of (address, observed-value).
  * Commit: acquire commit lock, re-validate read-set against the clock, write back under lock, advance clock, release.
  * Timeline visualization (figure): two concurrent TL2 transactions and the clock values they observe.
  * Validation semantics: every read-set entry must still match its recorded version, proving no writer committed during the transaction - this is what makes invisible reads safe.
  * Why TL2 is the standard baseline: minimal algorithm, clear invariants, easy to model-check (PlusCal model in the companion repo).
  * The stored-value trap: without value-based re-validation, clock-only validation misfires on OCC write-back races - the read-validate pattern recurs (see ROMULUS/MVLog case studies).

== TinySTM Design Variants ==
  * Write‑through vs. write‑back (lazy version management).
  * Eager locking vs. commit‑time locking.
  * Comparison of strategies under different workloads.
  * WBCTL (write-back, commit-time locking) vs. WT (write-through): the observable difference is where the data lives before commit.
  * Rollback mechanics: undo log for write-through, discard of write-set for write-back.
  * Optimizations for the cache: versioned write-set entries, `read-set bypass' when a value matches the write-set, and when each pays off.

== Multiversion STMs: JVSTM and MVLog ==
  * JVSTM: versioned boxes (VBox) store a history of (version, value) pairs; readers walk the newest body with version read-version.
  * Read-only transactions never abort: a consistent snapshot is read from history rather than validated.
  * Commit: global clock increments under a lock; writer appends a new VBox body; validation compares VBox heads.
  * MVLog: commit-slot negotiated at begin (a single fetch_add), an ever-growing commit log of write-sets, and per-address newest-writer tracking.
  * MVLog's `no-false-negative' bloom filter lets reads skip the log when the address is provably clean.
  * The cost of history: memory grows with transaction count; reclamation (epochs, hazardous pointers) becomes a first-order concern.
  * Why multiversion dominates GPU TM: read-only transactions never abort, and commit slots are cheap atomics (Part X, CSMV and GUST).

== Comparing the Family ==
  * A single table mapping design axes - conflict detection (eager vs. lazy), version management (write-through vs. write-back), metadata (per-location locks vs. global clock), read set (invisible vs. validation-driven).
  * NOrec bread-and-butter simplicity; TL2 clock-heavy but robust; TinySTM tuning knobs; multiversion for read-heavy and GPU workloads.
  * The recurring invariant: every design must prevent a snapshot from becoming inconsistent mid-flight; the read-validate pattern is how software enforces it.
  * Per-runtime performance signatures (the expected bottleneck of each row in Table tab:family-matrix): SGL serializes everything (throughput cap =1/tx time ); NOrec validates whole read-sets (cost grows with read-set size); TL2 pays commit-lock serialization plus clock reads; TinySTM pays per-location metadata traffic; multiversion pays memory reclamation.
  * Exercise 6 turns Table tab:family-matrix into numbers: the memory-overhead row is measurable on the repository's benchmarks.

== Signal Safety and sigsetjmp/longjmp ==
  * The stack‑corruption hazard: begin inside a function, function returns, abort jumps to corrupted frame.
  * Alternate signal stacks and safe checkpointing strategies.
  * The DATA-symbol subtlety: the runtime exports tm_sigsetjmp/tm_longjmp as function pointers, not functions - a DATA/TEXT symbol collision with a compiler-generated direct call is a classic segfault (fixed in the companion repo, and instructive).
  * TLS vs. stack jmp buffers: keeping the retry buffer in thread-local storage so it outlives any single frame.

-- The Conservative Signal-Safety Policy --
Because the frame-lifetime hazard is ubiquitous (it is hidden inside
tm_begin/tm_end), the book adopts a single, conservative
policy instead of a list of exceptions:
  * Allowed inside a transaction: transactional reads and writes, transactional allocation (tm_malloc), and the retry loop itself - everything that stays within the runtime's metadata.
  * Forbidden: any sigsetjmp whose frame may outlive the transaction; blocking signals that the runtime's tm_sigsetjmp wraps; and hand-written siglongjmp to a stack buffer.
  * Must abort or become irrevocable: operations with externally visible side effects (I/O, syscalls) that cannot be undone; these force a fallback to a serializing path (Ch. 11) before the operation runs.
  * The policy is a property the TLA+ models do not check: the models abstract the retry mechanism away entirely (Part V), so frame validity is enforced by convention plus TLS re-arming - not by the checker.

== Verifying GPU Protocols with TLA+ ==
Because GPU protocols replace hardware guarantees with software discipline,
they are prime candidates for the model-checking workflow of Part V.
models accompanying this book - GPU_PR_STM.tla,
GPU_SIMT.tla, GPU_JVSTM.tla, GPU_GUST.tla -
make the warp the unit of concurrency and encode the SIMT lock step as a
shared warp phase with per-thread arrays and an activeMask
to express divergence:
  * Warp-as-process. One TLA+ process per warp manages all of
its lanes' transactions; a single transition steps the whole warp,
matching the shared program counter.
  * Divergence as masking. Lanes that finish early are removed
from the active mask; the warp continues with the survivors, exactly
as a real divergence point does.
  * Bounded phases. Reads, writes, and validation are explicit
phases (L_read L_write
L_validate), bounding the state space by
ReadsPerThread instead of an unbounded either.
  * Opacity is an invariant. The GUST model's
InvNoMissedConflict states that no committed transaction
may be followed by another committed transaction that wrote an
address the first one read - serialisable/opaque semantics, not
just absence of lost updates.
TLC has checked tens of millions of states across these models with no
violations: the GUST model ran 1.9M states on the small configuration (0
errors) and over 25M on the large one without violations before timing out.
The models caught real bugs - the startTS vs.
startTS+1 snapshot hole of Section sec:gust (found first in
the model, then confirmed in the kernel) and, more fundamentally, the
__ballot_sync divergence class of Section sec:ballot.
two tools worked as a pair: TLA+ says what must be true; the ballot
contract says how the hardware will let you express it.

== Summary ==
  * GPUs have no cache coherence, no speculative hardware, and no vendor
TM: GPU TM is software TM, run at a scale and under constraints the
CPU design space never anticipated.
  * Lock-step warp execution turns spinning into self-abort and conflict
detection into predicate voting via __ballot_sync.
  * Read/write sets that do not fit on chip, coalescing that works
against scattered accesses, and thousands of concurrent transactions
all push designs toward multi-versioning and batch commit.
  * The recurring winners - CSMV's client-server commit and GUST's
AtomicINC commit log - trade a serial CAS for an increment, and a
read abort for a consistent snapshot.
  * Hardware proposals (KILO TM, WarpTM, snapshot-isolation HTM) show the
design space is real but simulated; the software systems show it is
live silicon reality.
  * Formal models at warp granularity are a practical, not academic,
tool: they caught the very bugs (the ballot contract, the snapshot
threshold) that the GPU community has repeatedly tripped over.

CHAPTER: Open Questions and Emerging Directions
============================================================

== Current Research Directions ==
  * Hardware/software hybrid TM.
  * Non-blocking algorithms vs. TM.
  * Persistent memory TM.
  * Distributed TM.
  * GPU TM (see Chapter chap:gpu-tm): no vendor hardware,
software conflict detection, and the search for scalable commit
protocols at thousands of concurrent transactions.
  * Persistent TM: durable commit with volatile metadata; crash-consistency without a database's write-ahead log.
  * Distributed TM: exporting the TM API over replicated or geo-distributed storage (the companion repo wraps a TiKV cluster).
  * Hybrid systems: HTM fast path, STM (or serialized) fallback, and the theory of `phased' and `shipwreck' hybrids.
  * Verified/certified STMs: mechanically checked backends, and the growing standard of TLA+-verified designs.
  * Energy-aware TM: correlation between abort rate and power on mobile/embedded cores.
The implementation boundary is now part of the research question.
repo has working CPU backends from SGL through SwissTM, TinySTM variants,
NOrec-BF, TL2, TSC-TM, MVLog, persistent and distributed SGL, and a TiKV
Percolator-style backend; it also contains GPU designs such as PR-STM, CSMV,
GPUTX, GAccO, GPU-JVSTM, and GUST.
and data-structure suites, and the core protocols have TLA+ models.
the open questions unusually concrete: the same bank invariant should survive
hardware aborts, validation filters, crash recovery, remote prepare/commit, and
GPU commit logs.

== Challenges ==
  * Fairness, progress guarantees (starvation freedom, obstruction freedom).
  * Programming model adoption.
  * Legacy code integration.
  * Performance predictability: HTM's capacity aborts and STM's validation costs make best/worst-case analysis hard.
  * The missing standard: no widely adopted language integration after the C++ TS; education must bridge this gap.
  * Tooling: debuggers, profilers, and race detectors are lock-oriented; TM tools are nascent by comparison.

== Summary ==
  * TM is a rich research field with many unsolved problems.
  * The student should leave with a critical understanding of where TM stands and where it might go.
  * Directions worth watching divide into three families: hardware (hybrid HTM, GPU), systems (persistent, distributed), and methods (verification, education).
  * Read this chapter as a synthesis organised around where the book's own codebase stops working, not as a disconnected wish-list. The limits that surface in each family are the same limits the earlier parts hit: HTM's capacity aborts (Ch. 16), STM's validation and reclamation costs (Ch. 12, 14), the missing compiler/language contract (Ch. 7), and the absence of coherence on GPUs (Ch. 17). Each open direction in this chapter is one of those known limits restated as a research target.
