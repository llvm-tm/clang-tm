\chapter{Testing, Debugging, and Scheduling}
\index{testing, debugging, scheduling, fuzzing, deterministic replay, invariant testing, TLA+ model checking}

Transactional memory implementations fail in ways that ordinary unit tests rarely expose. A transaction may read a value that was valid for only a few instructions, validate too early, forget to roll back one write-set entry, or publish a partially committed state. The failure often appears later, after the schedule that caused it has disappeared.

This chapter treats testing as a layered engineering discipline. At the bottom are cheap invariant tests: the bank still conserves money, a counter still has the expected value, a set still agrees with a sequential oracle. Above them are abort fuzzers, deterministic schedulers, replay tools, and abstract model checkers. The goal is not to prove every line of code correct from tests alone. The goal is to make rare transactional bugs reproducible, local, and small enough to fix.

\section{Unit Testing and Fuzzing}

The first test for a transactional backend should not assert that a particular interleaving occurred. It should assert that no interleaving can violate an invariant. For transactional data structures, the most useful invariants are usually conservation properties: a sum, a count, a membership relation, or equality with a sequential reference implementation.

The running bank benchmark has two accounts or a vector of accounts. Transactions transfer money between accounts, optionally respecting an account floor. The main invariant is money conservation: a committed transfer may move value, but it must not create or destroy value. In a shared-counter suite, the corresponding invariant is equality between the final counter value and the number of committed increments. In a set or map benchmark, the invariant is agreement with a single-threaded oracle that applies the same logical operations in a known serial order.

The best invariants are sums because they are insensitive to schedule. A correct TM may serialize two transfers in either order, but the total balance must remain fixed. A race-free TM preserves the accumulator; a defective TM allows it to drift. Lost updates, torn write-back, duplicate redo-log replay, failed undo, and non-atomic commit all tend to surface as changes in a sum.

Fuzzing changes the distribution of executions. Real workloads may rarely hit capacity aborts, explicit aborts, or conflict windows at just the wrong point. A fuzzer should hit them constantly. Abort fuzzing injects failures after reads, after the first write, after validation, during write-back, and immediately before commit. The resulting workload is artificial, but that is the point: rollback paths must be exercised far more often than production executes them.

The oracle question is central: what is the ground truth for a concurrent data structure? For many tests the answer is a sequential reference implementation run in one thread. The test records operations, applies them to the TM-backed object and to the oracle under the same logical order, and compares the results. For the bank benchmark, the oracle can be even simpler: the initial sum is the expected final sum.

These layers are complementary. The companion implementation runs concrete tests across the backends in the codebase, including lock-based, versioned, persistent, distributed, and GPU designs. The important testing pattern is backend independence: the same logical workload and the same invariant should apply to SGL, TL2, NOrec, TinySTM variants, SwissTM, persistent backends, distributed backends, and GPU designs. Backend-specific tests are still needed, but they should come after the generic invariants.

\section{Worked Example: An Invariant Test for Lost Updates}
\index{invariant test}\index{money conservation}
\label{sec:test-example}

The money-conservation assertion that Chapter~1's running example demands:

\begin{lstlisting}[language=C, caption={An invariant test for the transfer benchmark.}]
TEST(bank, money_is_conserved) {
    int initial = balance_sum();
    spawn(8, worker);            /* 8 threads each doing transfers */
    join_all();
    ASSERT_EQ(initial, balance_sum());   /* sum is invariant */
}
\end{lstlisting}

This is intentionally small. It does not inspect the internal read set, write set, commit counter, undo log, or lock table. It treats the TM as a black box and checks the property that all correct implementations must preserve.

The test catches a classic lost update. Suppose two transfers read the same destination balance, compute two different increments, and then one write overwrites the other. No account may become corrupted in isolation; each stored value may still look plausible. The sum exposes the defect because one credit vanished.

\begin{itemize}
    \item A race-free TM preserves the accumulator; a defect (lost update, torn write-back) surfaces as a drift in the sum --- Exercise~1 of this chapter.
    \item The same binary runs against every backend in Part~IV with one flag, so one test suite validates the whole family.
    \item Exercise~1 asks for the abort-fuzzing extension; \S\ref{sec:test-example} feeds the oracle question of this section: what is ground truth?
    \item Combine with \S\ref{sec:math-example}: at abort probability
    $$
    p = 0.9
    $$
    eight threads completing ten successful transactions each require the expected number of attempts
    $$
    8 \times 10 \div (1-p) = 800 .
    $$
    The test still passes only if undo logging is correct.
\end{itemize}

The formula is useful because it separates test intensity from logical work. The workload still commits only eighty transfers, but the implementation attempts about eight hundred transactions. A backend with a bad abort path may fail quickly even when the normal, low-abort workload passes.

\section{Worked Example: Abort Fuzzing for the Bank Invariant}
\index{abort fuzzing}\index{undo log}
\label{sec:abort-fuzz-bank}

The following standalone C++ test uses a single global lock to make the transaction body serial, then injects explicit aborts after partial updates. The point is not performance. The point is coverage of rollback paths that normal executions rarely hit.

\begin{lstlisting}[language=C++, caption={A compilable abort-fuzzing harness for the bank benchmark.}]
#include <cassert>
#include <cstdint>
#include <exception>
#include <iostream>
#include <mutex>
#include <numeric>
#include <random>
#include <thread>
#include <utility>
#include <vector>

struct Abort : std::exception {};

struct Account {
    int balance;
};

static int balance_sum(const std::vector<Account>& bank) {
    return std::accumulate(bank.begin(), bank.end(), 0,
        [](int acc, const Account& a) { return acc + a.balance; });
}

static bool transfer_with_fuzzed_abort(std::vector<Account>& bank,
                                       std::mutex& global_lock,
                                       int from,
                                       int to,
                                       int amount,
                                       std::mt19937& rng,
                                       double abort_probability) {
    std::bernoulli_distribution abort_now(abort_probability);
    std::vector<std::pair<int, int> > undo;  // (index, old_balance)

    auto write_balance = [&](int index, int value) {
        undo.push_back(std::make_pair(index, bank[index].balance));
        bank[index].balance = value;
    };

    global_lock.lock();
    try {
        write_balance(from, bank[from].balance - amount);

        if (abort_now(rng)) {
            throw Abort();
        }

        write_balance(to, bank[to].balance + amount);

        if (abort_now(rng)) {
            throw Abort();
        }

        global_lock.unlock();       // commit
        return true;
    } catch (const Abort&) {
        for (auto it = undo.rbegin(); it != undo.rend(); ++it) {
            bank[it->first].balance = it->second;
        }
        global_lock.unlock();       // abort
        return false;
    }
}

static void worker(std::vector<Account>& bank,
                   std::mutex& global_lock,
                   int id,
                   int successful_transactions) {
    std::mt19937 rng(0xC0FFEEu + static_cast<unsigned>(id));
    std::uniform_int_distribution<int> account(0,
        static_cast<int>(bank.size()) - 1);
    std::uniform_int_distribution<int> amount(1, 7);

    int committed = 0;
    while (committed < successful_transactions) {
        int from = account(rng);
        int to = account(rng);
        if (from == to) {
            continue;
        }

        if (transfer_with_fuzzed_abort(bank, global_lock, from, to,
                                       amount(rng), rng, 0.90)) {
            ++committed;
        }
    }
}

int main() {
    std::vector<Account> bank(64, Account{1000});
    std::mutex global_lock;

    const int initial = balance_sum(bank);

    std::vector<std::thread> threads;
    for (int i = 0; i != 8; ++i) {
        threads.emplace_back(worker, std::ref(bank), std::ref(global_lock),
                             i, 10);
    }

    for (std::thread& t : threads) {
        t.join();
    }

    assert(initial == balance_sum(bank));
    std::cout << "money conserved\n";
    return 0;
}
\end{lstlisting}

\begin{itemize}
    \item The injected abort after the debit catches a missing undo entry for the source account.
    \item The injected abort after the credit catches a rollback loop that restores only the first write.
    \item A global lock is acceptable in the harness: the test is aimed at rollback correctness, not scalability.
    \item The same shape appears in production TM tests: run the normal workload, raise the abort rate, assert the invariant after all threads join.
\end{itemize}

A useful extension is to randomize the abort site rather than only the abort decision. For write-back TMs this means injecting aborts before validation, after validation, before acquiring write locks, after acquiring a prefix of write locks, before publishing, and after publishing a prefix of locations in a private test build. For undo-log TMs this means aborting after every undo-log append and after every in-place write. Each abort site should have a name in the failure report; otherwise a failing seed only says that rollback is wrong, not which rollback path is wrong.

\section{Worked Example: A Sequential Oracle for a Counter Suite}
\label{sec:oracle-counter-example}

A conservation invariant is not always enough. A set, map, queue, or counter suite often needs a reference object. The following C++ program uses a mutex-protected sequential oracle beside an intentionally simple transactional interface. In a real backend test, \texttt{tm_increment} would be replaced by the backend under test.

\begin{lstlisting}[language=C++, caption={A compilable sequential-oracle test for committed increments.}]
#include <cassert>
#include <atomic>
#include <mutex>
#include <thread>
#include <vector>

struct Oracle {
    std::mutex mu;
    int value = 0;

    void increment() {
        std::lock_guard<std::mutex> g(mu);
        ++value;
    }

    int read() const {
        return value;
    }
};

struct TMCounter {
    std::atomic<int> value{0};

    void tm_increment() {
        int old = value.load(std::memory_order_relaxed);
        while (!value.compare_exchange_weak(old, old + 1,
               std::memory_order_release,
               std::memory_order_relaxed)) {
        }
    }

    int read() const {
        return value.load(std::memory_order_acquire);
    }
};

int main() {
    Oracle oracle;
    TMCounter counter;

    const int threads = 8;
    const int operations = 1000;

    std::vector<std::thread> workers;
    for (int tid = 0; tid < threads; ++tid) {
        workers.emplace_back([&] {
            for (int i = 0; i < operations; ++i) {
                counter.tm_increment();
                oracle.increment();
            }
        });
    }

    for (std::thread& t : workers) {
        t.join();
    }

    assert(counter.read() == oracle.read());
    assert(counter.read() == threads * operations);
}
\end{lstlisting}

\begin{itemize}
    \item The oracle is deliberately boring: one mutex, one integer, one serial meaning.
    \item The implementation may be concurrent; the expected result is not.
    \item A lost update appears as inequality between \texttt{counter.read()} and \texttt{oracle.read()}.
    \item The same pattern scales to maps and sets by recording logical operations and comparing final contents.
\end{itemize}

\section{Record-and-Replay and Deterministic Scheduling}

Record-and-replay tools and deterministic schedulers address the same pain point: a concurrent failure is useless if it cannot be reproduced. A TM bug may manifest at commit even though the causal mistake was an earlier read, a missed version check, or an overwritten metadata bit. Reverse debugging lets the developer start from the bad final state and walk backward to the first invalid transition.

Tools such as \texttt{rr} record a concrete execution and replay it with stable timing and stable thread behavior. This is valuable for ordinary C and C++ debugging: set a watchpoint on the corrupted account, replay, and step backward or forward around the write that changed it. Deterministic schedulers, in the style of CHESS, are more systematic. They control where threads may preempt and explore schedules up to a bound.

The bound on preemptions is what makes the search usable. Full interleaving exploration grows too quickly: every shared-memory access may interleave with every access in every other thread. Bounded-preemption testing assumes that many bugs require only a small number of unlucky context switches. That assumption is often good for TM implementations because many defects live in short windows: after validation but before write-back, after acquiring one lock but before acquiring the next, or after appending to an undo log but before installing the write.

Record-and-replay and model checking are not substitutes. TLA+ explores an abstract protocol state space and can find missing validation cases before code exists. Replay explores the concrete executable and can expose allocator behavior, memory-ordering mistakes, padding assumptions, and integration bugs that the abstract model intentionally omitted.

\section{Worked Example: Replay of a Lost-Update}
\index{deterministic scheduling}\index{replay}
\label{sec:replay-lost-update}

The next program is deliberately not a correct TM implementation. It is a minimal deterministic scheduler that reproduces a money-conservation failure by forcing a particular interleaving. Each account is atomic to avoid undefined behavior in the C++ memory model; the bug is logical non-atomicity, not a data race.

\begin{lstlisting}[language=C++, caption={A deterministic replay schedule that exposes a non-atomic transfer.}]
#include <atomic>
#include <cassert>
#include <condition_variable>
#include <iostream>
#include <mutex>
#include <thread>
#include <utility>
#include <vector>

class Replay {
public:
    explicit Replay(std::vector<std::pair<int, int> > script)
        : script_(std::move(script)), pos_(0) {}

    void checkpoint(int tid, int step) {
        std::unique_lock<std::mutex> lk(mu_);
        cv_.wait(lk, [&] {
            return pos_ < script_.size()
                && script_[pos_] == std::make_pair(tid, step);
        });
        ++pos_;
        cv_.notify_all();
    }

private:
    std::vector<std::pair<int, int> > script_;
    std::size_t pos_;
    std::mutex mu_;
    std::condition_variable cv_;
};

struct Bank {
    std::atomic<int> a{100};
    std::atomic<int> b{100};
};

static void nonatomic_transfer(Bank& bank, Replay& replay,
                               int tid, int amount) {
    replay.checkpoint(tid, 0);
    int old_a = bank.a.load();

    replay.checkpoint(tid, 1);
    int old_b = bank.b.load();

    replay.checkpoint(tid, 2);
    bank.a.store(old_a - amount);

    replay.checkpoint(tid, 3);
    bank.b.store(old_b + amount);
}

int main() {
    Bank bank;

    /*
       T0 debits A, T1 observes that debit, T1 credits B,
       then T0 overwrites B with an older value.
    */
    Replay replay({
        {0, 0}, {0, 1}, {0, 2},
        {1, 0}, {1, 1}, {1, 2}, {1, 3},
        {0, 3}
    });

    std::thread t0(nonatomic_transfer, std::ref(bank),
                   std::ref(replay), 0, 10);
    std::thread t1(nonatomic_transfer, std::ref(bank),
                   std::ref(replay), 1, 20);

    t0.join();
    t1.join();

    const int final_sum = bank.a.load() + bank.b.load();

    assert(bank.a.load() == 70);
    assert(bank.b.load() == 110);
    assert(final_sum == 180);

    std::cout << "replayed invariant failure: sum = "
              << final_sum << "\n";
    return 0;
}
\end{lstlisting}

\begin{itemize}
    \item The schedule is the test case. Once recorded, the failure is no longer a Heisenbug.
    \item Atomics remove undefined behavior from the demonstration; they do not provide transaction atomicity.
    \item A watchpoint on \texttt{bank.b} identifies the overwrite: thread 0 writes a value computed before thread 1's credit.
    \item A real TM backend prevents this execution by locking, validating, versioning, or aborting one transaction.
\end{itemize}

The replay script is also a specification of the bug. It says which thread reached which logical point and in what order. That is more useful than a sleep-based test because sleeps encode timing, not causality. Deterministic checkpoints encode the causal edges directly.

\section{Worked Example: A TLA+ Money-Conservation Check}
\label{sec:tla-bank-conservation}

The following TLA+ model abstracts a single transfer from account \texttt{A} to account \texttt{B}. It includes an abort action that restores both balances from the saved old values. If the restoration of \texttt{a} is removed, the invariant can fail after an abort following the debit.

\begin{lstlisting}[caption={A small TLA+ model for transfer rollback and money conservation.}]
--------------------------- MODULE BankAbort ---------------------------
EXTENDS Naturals

CONSTANTS InitA, InitB, Amount

VARIABLES a, b, phase, oldA, oldB

Init ==
    /\ a = InitA
    /\ b = InitB
    /\ phase = "start"
    /\ oldA = InitA
    /\ oldB = InitB

Read ==
    /\ phase = "start"
    /\ oldA' = a
    /\ oldB' = b
    /\ phase' = "read"
    /\ UNCHANGED <<a, b>>

Debit ==
    /\ phase = "read"
    /\ a >= Amount
    /\ a' = a - Amount
    /\ phase' = "debited"
    /\ UNCHANGED <<b, oldA, oldB>>

Credit ==
    /\ phase = "debited"
    /\ b' = b + Amount
    /\ phase' = "credited"
    /\ UNCHANGED <<a, oldA, oldB>>

Commit ==
    /\ phase = "credited"
    /\ phase' = "done"
    /\ UNCHANGED <<a, b, oldA, oldB>>

Abort ==
    /\ phase \in {"read", "debited", "credited"}
    /\ a' = oldA
    /\ b' = oldB
    /\ phase' = "done"
    /\ UNCHANGED <<oldA, oldB>>

Next == Read \/ Debit \/ Credit \/ Commit \/ Abort

MoneyConserved == a + b = InitA + InitB

Spec == Init /\ [][Next]_<<a, b, phase, oldA, oldB>>
=============================================================================
\end{lstlisting}

\begin{itemize}
    \item The model is small because it checks one idea: rollback must restore every in-place update.
    \item \texttt{MoneyConserved} is the same invariant used by the C++ bank tests.
    \item Omitting \texttt{a' = oldA} in \texttt{Abort} models a missing undo-log entry for the debit.
    \item The abstraction ignores performance, allocation, and cache behavior; that is why it can exhaustively explore protocol states.
\end{itemize}

A useful workflow is to keep the TLA+ model close to the implementation test. When the implementation adds account floors, the model should add the same precondition. When the implementation distinguishes explicit aborts from conflict aborts, the model can keep one abstract abort action unless the distinction affects safety.

\section{Summary}

Testing transactional memory requires a stack of techniques. Invariant tests are cheap and backend-independent; they should run everywhere. Abort fuzzing makes rare rollback paths common. Deterministic scheduling turns timing-sensitive failures into ordinary test cases. Record-and-replay makes concrete executions debuggable. TLA+ model checking explores the abstract protocol and catches missing transitions before they become code.

The most useful tests are small, repeatable, and invariant-driven. A bank sum, a counter value, or agreement with a sequential oracle is often enough to expose a deep atomicity bug. Once a failure is found, the engineering task is to preserve it: keep the seed, keep the schedule, keep the model counterexample, and add the cheapest regression test that still fails without the fix.

\section{Exercises}
\begin{enumerate}
    \item Design a fuzzing strategy that randomly injects aborts to stress-test a TM's undo-log correctness.
    \item Given a recorded \texttt{rr} trace where a transaction T commits but its writes never appear, hypothesise where to set a watchpoint and how to step backwards to find the bug.
    \item A deterministic scheduler explores interleavings with a bounded number of preemptions. Explain how this bound trades off completeness for tractability.
    \item \emph{[implementation]} Extend Listing~\ref{sec:abort-fuzz-bank}'s harness with account floors: no committed transaction may leave an account below zero. Keep money conservation as a separate invariant, and report which invariant fails first.
    \item \emph{[verification]} Write a two-account TLA+ model of transfer with actions \textsc{Read}, \textsc{Debit}, \textsc{Credit}, \textsc{Commit}, and \textsc{Abort}. Add the money-conservation invariant and then intentionally omit rollback for \textsc{Debit}; confirm that the model checker finds a counterexample.
    \item \emph{[theory]} Bounded-preemption testing often finds bugs with a small bound. Give one reason this empirical fact is plausible for TM implementations, and one class of TM bug that may require a larger bound or a different exploration strategy.
    \item \emph{[implementation]} Add named abort sites to the abort-fuzzing harness and print the seed, thread id, source account, destination account, amount, and abort-site name on failure.
    \item \emph{[verification]} Modify the TLA+ model in Listing~\ref{sec:tla-bank-conservation} to include an account floor. State the invariant that distinguishes money conservation from floor preservation.
    \item \emph{[theory]} Explain why a sequential oracle is easy for a counter but harder for a concurrent queue whose operations return values during the execution, not only at the end.
\end{enumerate}
