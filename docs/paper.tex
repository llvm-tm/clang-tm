\begin{abstract}
We present an LLVM compiler plugin that automatically instruments C++ code for Software
Transactional Memory (STM) using source-code annotations.  Developers mark global variables
with \texttt{\_\_attribute\_\_((annotate("tm")))} and functions with
\texttt{\_\_attribute\_\_((annotate("transaction")))}.  The plugin (i) inserts
transaction begin/commit hooks with \texttt{sigsetjmp}/\texttt{siglongjmp} retry logic,
(ii) replaces loads and stores to annotated globals with typed \texttt{tm\_read\_*}/\texttt{tm\_write\_*}
calls, (iii) performs transitive call-graph cloning so that functions reachable from
transactions which interact with TM state are automatically instrumented, and
(iv) supports multiple STM backends
including NOrec, TL2, TinySTM, SwissTM, and SingleGlobalLock.  We evaluate the plugin
on bank transactions, data-structure microbenchmarks, and STMbench7, demonstrating
correctness across all backends and identifying performance trade-offs between
per-access logging (TinySTM) and commit-time validation (NOrec).
\end{abstract}

\section{Introduction}

Software Transactional Memory (STM) simplifies concurrent programming by letting developers
specify atomic blocks whose effects either commit entirely or abort and retry.  Manual STM
instrumentation --- replacing every load and store in a critical section with calls to
\texttt{tm\_read\_*}/\texttt{tm\_write\_*} --- is error-prone, invasive, and couples application
code to a specific STM implementation.

Compiler automation of this instrumentation has long been advocated in the TM literature
but rarely delivered.  The STO system~\cite{STO} notes that a ``TM programmer (or TM
compiler) labels accesses to shared memory'' but provides only a library.  The ByteSTM~\cite{ByteSTM}
survey categorises compiler-based STM as its own class but implements a VM-level solution.
The C++ TM Lite proposal~\cite{P1875} acknowledges that ``compiler instrumentation to
support software and hybrid TM is more complex than in the lambda approach'' and explicitly
defers software TM performance to future work.  Compiler-based TM remains a stated goal
across dozens of publications, but the only production compiler with full TM support remains
GCC's implementation of the 2015 TM Technical Specification~\cite{TMTS}, which the community
has judged too complex to adopt.

We present an LLVM compiler plugin that fills this gap.  Unlike prior work, our approach is
annotation-driven: developers mark global variables with
\texttt{\_\_attribute\_\_((annotate("tm")))} and functions with
\texttt{\_\_attribute\_\_((annotate("transaction")))}.  The plugin then automatically
instruments every load, store, and control-flow path within the transitive call tree of
each transaction, with no need for lambda wrappers, RAII objects, or macro-based APIs:

\begin{itemize}
\item \textbf{Global variables} annotated \texttt{\_\_attribute\_\_((annotate("tm")))}
  are managed by the STM runtime --- every load becomes \texttt{tm\_read\_TYPE}, every
  store becomes \texttt{tm\_write\_TYPE}.
\item \textbf{Functions} annotated
  \texttt{\_\_attribute\_\_((annotate("transaction")))} are wrapped with
  transaction-begin and transaction-commit hooks, with \texttt{sigsetjmp}/\texttt{siglongjmp}
  providing automatic retry on conflict.
\item \textbf{Transitive call-graph cloning}: non-transaction functions reachable from a
transaction are cloned and instrumented only if they interact with TM state (either
directly write to TM globals or receive arguments that trace back to TM globals).
A fixed-point propagation algorithm (\S\ref{sec:cloning}) determines the set of
clonable functions by tracking ``TM-traceable'' arguments through the call graph.
Functions reachable from transactions but read-only with respect to TM state are
left untouched --- they need no instrumentation because they buffer no writes to
undo on abort.  Functions called through indirect call sites (function pointers,
virtual dispatch) are invisible to the static analysis and are never cloned;
if such a function writes to TM globals, the write bypasses the TM system,
causing silent data corruption.
\item \textbf{Iterator and container support}: a backward use-def tracer
  (\texttt{tracesFromTMGlobal}) follows pointer chains through allocas, loads, calls, and
  GEPs to detect range-for-loop element accesses that ultimately reach TM-annotated globals.
  This allows the instrumentation to correctly handle C++ STL containers used inside
  transactions.
\item \textbf{Modernised STM backends}: our runtime libraries reimplement TinySTM,
  TL2, NOrec, and SwissTM from the original C/assembly sources using
  \texttt{std::atomic} (C++11) and modern C++17.  The original implementations
  relied on pre-C++11 atomic operations (\texttt{atomic\_ops} library,
  compiler builtins, inline assembly) that are no longer portable or
  maintainable.  Our backends are header-only, use standard C++ concurrency
  primitives, and require no platform-specific assembly or external library
  dependencies.
\item \textbf{Multiple backends}: the plugin emits backend-agnostic hook calls; six runtime
  libraries implement the actual STM algorithm --- NOrec, TL2, TinySTM (three variants),
  SwissTM, and SingleGlobalLock.
\end{itemize}

\section{Implementation}\label{sec:implementation}

Our LLVM plugin consists of two passes that operate in the standard LLVM Pass Manager
framework:

\begin{enumerate}
\item \textbf{TMGlobalInitPass} (module-level, runs once per translation unit)
\item \textbf{TMInstrumentPass} (function-level, runs on each function)
\end{enumerate}

\subsection{TMGlobalInitPass (Module-Level)}

This pass performs one-time setup for the entire compilation unit:

\begin{enumerate}
\item \textbf{Declare Runtime Functions}: Insert declarations for all runtime hooks:
  \texttt{tm\_init()}, \texttt{tm\_exit()}, \texttt{tm\_init\_thread()},
  \texttt{tm\_exit\_thread()}, \texttt{tm\_begin()}, \texttt{tm\_end()}, and
  all typed \texttt{tm\_read\_*}/\texttt{tm\_write\_*} functions.

\item \textbf{Create Symbol Tables}: Build \texttt{tm\_symbol\_names[]},
  \texttt{tm\_symbol\_addresses[]}, \texttt{tm\_symbol\_sizes[]}, and
  \texttt{tm\_symbol\_count} from \texttt{llvm.global.annotations}.

\item \textbf{Build TX-Reachable Call Graph}: For each function annotated
  ``transaction'', compute the transitive closure of all functions it calls
  (direct calls only, following \texttt{CallBase} instructions).  This yields
  the set \texttt{TxReachableFuncs}.

\item \textbf{Clone Reachable Functions}: Run the fixed-point propagation
  algorithm (\texttt{computeClonableFunctions}, \S\ref{sec:cloning}) to compute
  the set of functions that interact with TM state.  For each such function,
  create a clone with suffix \texttt{\_tm\_clone}.  The clone has its loads and
  stores to TM-shared pointers replaced with \texttt{tm\_read\_*}/
  \texttt{tm\_write\_*} calls.  Calls within the clone to other cloned functions
  are redirected to their cloned counterparts.  Functions in the call tree that
  are read-only with respect to TM state are never cloned --- their execution is
  idempotent and needs no rollback on abort.

\item \textbf{Redirect TX-Function Calls}: For each original transaction function,
  redirect direct calls to reachable callees to their \texttt{\_tm\_clone} versions.

\item \textbf{Instrument Main and Thread Entries}: Insert \texttt{tm\_init()}
  and \texttt{tm\_init\_thread()} at \texttt{main()} entry, \texttt{tm\_exit\_thread()}
  and \texttt{tm\_exit()} before returns.  Functions annotated ``thread'' get
  \texttt{tm\_init\_thread()}/\texttt{tm\_exit\_thread()} with a thread-local
  guard to ensure idempotency.
\end{enumerate}

\subsection{TMInstrumentPass (Function-Level)}

This pass runs on each function annotated ``transaction'':

\begin{enumerate}
\item \textbf{Nested Transaction Handling}: Creates thread-local globals
  \texttt{tm\_nested\_call\_counter}, \texttt{tm\_jmpbuf} (256 bytes), and
  \texttt{tm\_longjmp\_ret}.  Splits the entry block and inserts a conditional
  branch:
  \begin{itemize}
  \item If \texttt{counter == 0} (outermost): \texttt{sigsetjmp} (for retry),
    set counter to 1, call \texttt{tm\_begin()}.
  \item If \texttt{counter > 0} or retry (\texttt{longjmp\_ret != 0}):
    increment counter (nested path, no \texttt{tm\_begin()}).
  \end{itemize}

\item \textbf{Memory Instrumentation}: Scans all instructions; replaces
  \texttt{LoadInst} and \texttt{StoreInst} to shared (non-local) pointers with
  calls to the appropriate \texttt{tm\_read\_*}/\texttt{tm\_write\_*} functions.
  The decision to instrument (\texttt{isSharedPointer}) uses three criteria:
  \begin{enumerate}
  \item \texttt{tracesFromTMGlobal}: backward use-def tracer that follows
    pointers through GEPs, loads, calls, PHIs, and alloca store chains to
    determine if the pointer reaches a TM-annotated global.  This catches
    iterator-based element accesses in range-for loops:
    \texttt{for (auto \&ca : g\_complexAssemblies)} where
    \texttt{g\_complexAssemblies} is a TM global.
  \item \texttt{originatesFromLocal}: forward tracer to detect
    stack-allocated variables (never instrumented).
  \item \texttt{getBaseObject}: direct GlobalVariable check for
    simple global-pointer access.
  \end{enumerate}

\item \textbf{Exit Instrumentation}: At each return, decrement the counter.
  If counter reaches 0 (outermost), call \texttt{tm\_end()};
  otherwise skip directly to the return (nested exit).
  Non-void return values are preserved via an alloca.

\item \textbf{Memory Intrinsics}: \texttt{llvm.memcpy}, \texttt{llvm.memmove},
  and \texttt{llvm.memset} operating on TM globals are replaced with per-byte
  loops using \texttt{tm\_read\_i1}/\texttt{tm\_write\_i1}.
\end{enumerate}

\subsection{Iterator Tracing via \texttt{tracesFromTMGlobal}}

A key challenge in instrumenting C++ transactions is that STL containers'
internal metadata (e.g., \texttt{\_\_begin\_}, \texttt{\_\_end\_}) are accessed
through pointers loaded from function arguments.  A range-for loop generates IR
where the element pointer chains through an iterator alloca whose value comes
from \texttt{begin()} on a TM global:

\begin{verbatim}
  %__range = alloca %"vector"
  store %g_complexAssemblies, %__range   ; TM global!
  %call = call @begin(%__range)
  %__begin = alloca ptr
  store %call, %__begin
  ; loop: %ca_ptr = load ptr, %__begin
  ;        %cax = getelementptr %ca_ptr, 0, x
  ;        load i32, %cax
\end{verbatim}

\texttt{tracesFromTMGlobal} follows this chain backward: from the load of
\texttt{\%cax}, it traces through GEPs to \texttt{\%ca\_ptr}, then to the
load from \texttt{\%\_\_begin}, then to the alloca \texttt{\%\_\_begin},
then back through stores to the \texttt{begin()} call, then to the
\texttt{\%\_\_range} alloca, then to the store of
\texttt{\%g\_complexAssemblies} (a TM global).  This makes
\texttt{isSharedPointer} return \texttt{true} for the element load,
correctly triggering TM instrumentation.

\subsection{Transitive Cloning via Fixed-Point Propagation}
\label{sec:cloning}

Not every function reachable from a \texttt{@transaction} function needs
cloning.  A function only requires instrumentation if its execution
interacts with TM state.  The plugin therefore partitions
\texttt{TxReachableFuncs} (the transitive call graph rooted at
\texttt{@transaction} functions) into three categories:

\begin{description}
\item[TM-writing:] Functions that directly write to TM-annotated globals
  (detected by \texttt{hasDirectTMWrites}, which scans all
  \texttt{StoreInst} instructions and checks whether the stored pointer
  traces back to a TM global).  These MUST be cloned: their stores must
  be redirected through \texttt{tm\_write\_*} to buffer writes for
  commit-time or to support rollback on abort.

\item[TM-argument:] Functions that do not directly write TM globals
  but receive one or more arguments that are \emph{TM-traceable} ---
  i.e., the argument's value originates from a TM-annotated global
  (determined via the propagation below).  These MUST be cloned because
  they may pass the TM-traceable pointer to callees that write through
  it, or they may load from the pointer and pass the loaded value to
  other functions.

\item[Read-only:] Functions reachable from \texttt{@transaction} that
  neither write to TM globals nor receive TM-traceable arguments.
  These are NEVER cloned.  Their execution is idempotent: reads from
  TM globals return current values, but there are no writes to buffer
  or roll back.  On transaction abort, the read-only function's
  effects are trivially discarded (they produced no side effects on
  TM state).
\end{description}

The clone set is computed by a fixed-point propagation algorithm
(\texttt{computeClonableFunctions}):

\begin{enumerate}
\item \textbf{Seed}: Functions with direct writes to TM globals
  (\texttt{hasDirectTMWrites}) are added to the clone set and their
  formal arguments are marked as potentially TM-traceable.

\item \textbf{Propagate}: Iterate over all call sites within
  \texttt{TxReachableFuncs}.  For each argument passed to a callee:
  \begin{itemize}
  \item If the argument \texttt{tracesToTMGlobal} directly to a TM global,
    the callee's corresponding argument is TM-traceable and the callee
    is added to the clone set.
  \item If the argument is a function argument of the caller, and that
    caller argument was previously marked TM-traceable, the callee's
    argument inherits the traceability and the callee is added.
  \item If the argument is a \texttt{LoadInst} from a pointer that,
    after stripping GEPs, is a TM-traceable argument of the caller,
    the loaded value is TM-traceable (the loaded pointer chains
    through a stack alloca).
  \item If the argument is a \texttt{CallBase} return whose operands
    include any TM-traceable argument, the return value is TM-traceable.
  \end{itemize}
\item \textbf{Iterate}: repeat until no new functions are added (fixed point).
\end{enumerate}

This propagation correctly identifies that \texttt{\_\_tree\_left\_rotate}
must be cloned when it is reachable from \texttt{map::operator[]} on a
TM-annotated map, even though its formal parameter is a heap-allocated
tree node pointer rather than a TM global directly.

\paragraph{Limitation: opaque call sites.}
The static call-graph traversal (\texttt{collectTransactionCallGraph})
only follows direct calls --- those where
\texttt{CallInst::getCalledFunction()} returns a non-null function with
a body (\texttt{!isDeclaration()}).  Three kinds of call sites are
completely invisible to the analysis:

\begin{enumerate}
\item \textbf{Indirect calls} (function pointers, \texttt{std::function},
  virtual dispatch): \texttt{getCalledFunction()} returns null, so the
  callee is never added to \texttt{TxReachableFuncs} and thus never
  considered for cloning.

\item \textbf{External functions} (declarations without a definition):
  \texttt{isDeclaration()} returns true, so the traversal skips them.
  These functions have no IR body to instrument.

\item \textbf{Intrinsics and runtime hooks} (\texttt{llvm.memcpy},
  \texttt{tm\_*}, etc.): filtered by name prefix to avoid cloning the
  STM runtime itself.
\end{enumerate}

\textbf{Consequence}: if a \texttt{@transaction} function calls through
a function pointer at runtime, and the callee writes to TM-annotated
globals, those writes execute as plain stores with no
\texttt{tm\_write\_*} instrumentation.  The write bypasses the STM
runtime entirely, producing silent data corruption: the value is
modified directly in memory without being recorded in the write-set,
so it is not rolled back on abort and not committed atomically.
This is a fundamental limitation of static whole-program analysis;
detecting indirect TM calls would require either link-time
instrumentation (as in GCC's TMTS~\cite{TMTS}) or runtime dispatch
tables.

\subsection{Backend Runtime Interface}

All backends export the following C-linkage functions:

\begin{center}
\begin{tabular}{ll}
\toprule
Function & Purpose \\
\midrule
\texttt{tm\_init()}/\texttt{tm\_exit()} & Global lifecycle \\
\texttt{tm\_init\_thread()}/\texttt{tm\_exit\_thread()} & Per-thread lifecycle \\
\texttt{tm\_begin()}/\texttt{tm\_end()} & Transaction boundaries \\
\texttt{tm\_read\_i\{1,2,4,8\}}()/\texttt{tm\_write\_i\{1,2,4,8\}}() & Typed memory access \\
\texttt{tm\_read\_f\{4,8\}}()/\texttt{tm\_write\_f\{4,8\}}() & Float/double access \\
\texttt{tm\_read\_ptr()}/\texttt{tm\_write\_ptr()} & Pointer access \\
\texttt{tm\_set\_jmpbuf()}/\texttt{tm\_longjmp()} & Abort/retry mechanism \\
\bottomrule
\end{tabular}
\end{center}

Each backend implements these with a different STM strategy:

\begin{itemize}
\item \textbf{SingleGlobalLock}: a single \texttt{std::mutex} acquired in
  \texttt{tm\_begin()} and released in \texttt{tm\_end()}.  No per-access
  instrumentation.  Fastest for low contention, serializes all transactions.
\item \textbf{NOrec}: value-based validation~\cite{NOrec}.  Reads are direct
  memory access with a clock-consistency check.  Writes are buffered in a
  write-set and committed via a CAS on a global lock.  No read-set logging.
  Handles high read volumes efficiently.
\item \textbf{TL2}: commit-time locking~\cite{TL2}.  Reads log the observed
  version; writes buffer in a write-set.  At commit, acquires per-address
  locks, validates the read-set, and writes back.  Per-access overhead but
  scales with disjoint access.
\item \textbf{TinySTM (WBCTL)}: write-back commit-time locking~\cite{TinySTM}.
  Full read-set and write-set with per-lock version tracking.  Validates
  the entire read-set at commit.  Most expensive per-access overhead.
\item \textbf{SwissTM}: hybrid lazy/pessimistic~\cite{SwissTM}.  Lazy conflict
  detection with commit-time validation.
\item \textbf{PersistentSGL}: a persistence backend that wraps
  SingleGlobalLock with file-backed \texttt{mmap}.  At
  \texttt{tm\_init()}, the current values of all TM-annotated globals are
  snapshotted into a memory-mapped file.  Each \texttt{tm\_write\_*}
  updates both the in-memory value and the mapped file transparently.
  On a subsequent run, \texttt{tm\_init()} detects the existing file and
  restores the TM globals from it.  This enables TM application state to
  survive process restarts with no programmer effort beyond the existing
  \texttt{TM}/\texttt{TX} annotations.  Fixed-size data (arrays,
  primitives) persists correctly; heap-based containers (\texttt{std::map},
  \texttt{std::vector}) require serialisation because their node pointers are
  absolute addresses that become stale after restart (a
  position-independent \texttt{RelPtr} pointer abstraction is provided in
  \texttt{backends/rel\_ptr.hpp} for custom persistent data structures).

\item \textbf{DistributedSGL}: a distributed-transaction backend that
  simulates two-phase commit across multiple OS processes using a shared
  \texttt{mmap} file.  A configurable number of processes
  (\texttt{TM\_NPROCESSES} environment variable) synchronise in a barrier
  at \texttt{tm\_init()}.  On each \texttt{tm\_begin()} the process acquires
  a global spinlock (PREPARE phase) and synchronises TM symbol data from
  the shared file; on \texttt{tm\_end()} it writes its changes back,
  advances an epoch counter, and releases the lock (COMMIT phase).
  This ensures every process sees the latest committed state regardless
  of address-space layout randomisation (ASLR) between processes, because
  data is transferred by offset-based \texttt{memcpy} rather than by
  shared pointers.  The backend demonstrates that the annotation-driven
  plugin makes it straightforward to experiment with unconventional TM
  semantics --- persistence and distribution --- without changing a single
  line of plugin code.
\end{itemize}

\section{Evaluation}\label{sec:evaluation}

We evaluate the plugin across all backends using the most extensive benchmark
suite in the TM compiler literature.  Table~\ref{tab:bench-comparison}
summarises the breadth of our evaluation relative to the closest prior work.

\subsection{Experimental Design}

We propose the following experimental structure to evaluate both correctness
and performance of the annotation-driven TM plugin:

\paragraph{Correctness verification (RQ1).}
Each backend must preserve the semantics of serialised transaction execution.
We verify this across three dimensions:
\begin{enumerate}
\item \textbf{Money conservation (Bank)}: 256 accounts, 2--8 threads,
  random transfers.  Pass condition: final total equals initial total
  across all samples.
\item \textbf{Structural invariants (STMbench7)}: 100k-element CAD/CAM graph,
  45 operation types.  Pass condition: graph invariants (connectivity,
  cardinality constraints) hold after concurrent transactions.
\item \textbf{Algorithmic correctness (STAMP)}: All 8 benchmarks,
  comparing output against sequential (uninstrumented) execution.
\end{enumerate}

\paragraph{Performance characterisation (RQ2).}
We measure throughput (transactions/sec or operations/sec) across:
\begin{enumerate}
\item \textbf{Backend comparison}: All 6 backends on Bank, data-structure,
  STAMP, STMbench7, YCSB, and EigenBench workloads.
\item \textbf{Thread scalability}: 2, 4, 8, 16 threads on Bank and STAMP
  to measure how instrumentation overhead affects scaling.
\item \textbf{Read/write sensitivity}: Vary read-all\% (0--100\%) in Bank
  to measure the cost of read-set logging vs.\ write-through approaches.
\item \textbf{Transaction length}: Vary transaction size in EigenBench
  (short: 1 op/tx; long: 100 ops/tx) to measure commit-time overhead.
\end{enumerate}

\paragraph{Instrumentation overhead (RQ3).}
We quantify the cost of compiler instrumentation:
\begin{enumerate}
\item \textbf{Compilation time}: Time to compile each benchmark with and
  without the TM plugin pass.
\item \textbf{Binary size}: Size of uninstrumented vs.\ instrumented
  executables.
\item \textbf{Call-graph cloning}: Number of functions cloned per
  benchmark, to measure the reach of fixed-point propagation.
\end{enumerate}

Where the Spear plugin (\texttt{llvm-transmem}) is reproducible, we run
identical workloads and report throughput ratios.  We also compare

\section{Related Work}\label{sec:related}

\subsection{Compiler-Based TM Instrumentation}

The idea of using the compiler to automate STM instrumentation is as old as STM itself.
The 2006 HyTM proposal~\cite{HyTM} describes a ``proof-of-concept compiler'' built on the
Sun Studio back end, intercepting function calls to delimit transactions.  The Dresden TM
Compiler~\cite{DTMC} provides a full C/C++ TM compiler, but as a standalone compiler
fork rather than a plugin for an existing compiler infrastructure.  GCC's TMTS
implementation~\cite{TMTS} is the only production compiler with integrated TM support,
but its complexity (transaction-safe type system, function multiversioning, link-time
cloning) led the C++ standards committee to conclude that the TS was ``too complicated''
and needed replacement~\cite{P1875}.

More recently, the TACO 2019 paper by Zardoshti et al.~\cite{Zardoshti2019} (extended
in the C++ TM Lite proposal~\cite{P1875}) describes an LLVM plugin that intercepts
lambda expressions and RAII scope objects to delimit transactions.  The plugin is
available at \texttt{github.com/mfs409/llvm-transmem}.  This is the closest prior
work to ours, but there are several important differences:

\paragraph{API design.}  The Spear plugin uses \texttt{TX\_BEGIN \{ ... \} TX\_END} macros
that expand to lambda expressions or RAII objects.  This requires the programmer to
restructure existing code into lambda bodies or declare local RAII variables.  Our
annotation-driven approach (\texttt{\_\_attribute\_\_((annotate(...)))}) attaches metadata
to existing function declarations and global variables, requiring zero syntactic
restructuring.  An existing class with a \texttt{transfer(from, to, amount)} method
needs only a single annotation on the function --- no lambda capture, no RAII guard,
no include of a header defining macros.

\paragraph{Call-graph cloning.}  Spear's plugin uses conditional dispatch: every call
site checks a runtime flag to choose between the original and instrumented version
of a function.  This adds a branch per call and prevents inlining across the
instrumentation boundary.  Our plugin uses compile-time redirection: calls within
transaction context are rewritten to point directly to instrumented clones, with
no runtime dispatch overhead.  Additionally, our fixed-point propagation
algorithm (\S\ref{sec:cloning}) handles TM-traceable arguments through STL
internal functions (e.g., \texttt{\_\_tree\_left\_rotate}), which the Spear plugin
does not address in its published description.

\paragraph{Thread lifecycle.}  Spear's plugin does not instrument thread entry and
exit points.  Transactions running in worker threads must initialise the STM runtime
manually.  Our plugin detects \texttt{\_\_attribute\_\_((annotate("thread")))}
functions and automatically inserts \texttt{tm\_init\_thread()} and
\texttt{tm\_exit\_thread()} calls.

\paragraph{Benchmark breadth and reproducibility.}  As shown in
Table~\ref{tab:bench-comparison}, our evaluation covers 14 distinct benchmarks

\paragraph{Corner-case breakage risks.}
Both plugins share fundamental limitations inherent to static whole-program
analysis: inter-module calls (calls to functions defined in separately-compiled
translation units) cannot be cloned, and indirect calls through function
pointers or virtual dispatch are invisible to the static call graph.  If a
function called through an indirect site writes to TM-annotated globals, the
write bypasses the TM runtime, causing silent data corruption.

Our plugin has two additional risk categories unique to its approach.
First, the \texttt{noinline} attribute on \texttt{TX} functions is required
to preserve the annotation through LLVM's inliner before the plugin runs.
If a \texttt{TX} function is inlined into a non-TX caller before the pass
executes, it loses its transaction boundary.  Second, the
\texttt{isArgTraceable} recursion in \texttt{computeClonableFunctions} uses
a depth limit of 10; deeply nested pointer chains could exceed this limit,
causing incomplete cloning.

Spear's plugin has several risks that ours avoids.  The lambda-detection
heuristic (\texttt{discover\_lambda\_funcs}) identifies lambdas by checking
if a function has exactly 2 arguments where one is \texttt{TM\_OPAQUE*} ---
any lambda with that signature but different semantics would be falsely
matched.  The \texttt{discover\_annotated\_funcs} method hard-codes a list
of TM runtime functions (\texttt{TM\_EXECUTE}, \texttt{TM\_EXECUTE\_C},
\texttt{setjmp}, \texttt{TM\_RAII} ctor/dtor) that must be kept in sync
with the runtime library.  The RAII API implementation
(\texttt{instrument\_raii\_regions}) transforms every instruction within
a scope into a diamond-pattern branch; this can exponentially increase
the IR size for long transactions, placing practical limits on transaction
length.  The plugin uses the deprecated \texttt{CallSite} wrapper (removed
in LLVM 14), making forward porting impossible without significant
refactoring.
Spear's repository provides TinySTM, NOrec, and single-lock backends, with
additional PTM variants.  Our plugin provides NOrec, TL2, TinySTM (three
variants: WBCTL, WBETL, WT), SwissTM, SingleGlobalLock, and PersistentSGL,
each with a shared runtime interface and per-backend unit tests.

\subsection{Compiler Instrumentation as an Unmet Goal}

A substantial body of TM research advocates for compiler support without
implementing it.  The STO system~\cite{STO} (EuroSys 2016) explains that a
``TM programmer (or TM compiler) labels accesses to shared memory'' but
provides only a C++ library based on operator overloading.  The ByteSTM
survey~\cite{ByteSTM} categorises ``compiler-based STM'' as one of three
implementation strategies alongside library-based and VM-based, then proceeds
with a Jikes RVM modification.  LiTM~\cite{LiTM} (PPoPP 2019) implements a
deterministic STM with no compiler component.  OneFile~\cite{OneFile} (2019)
uses C++ operator overloading to wrap types and explicitly states its approach
requires ``no compiler instrumentation.''  HaTS~\cite{HaTS} (OPODIS 2019)
collects metadata via ``developer's annotations'' at compilation time but
does not provide a compiler pass to do so.  The C++ TM Lite
proposal~\cite{P1875,P2066} explicitly states that ``compiler instrumentation
to support software and hybrid TM is more complex'' and that the proposal
``want[s] to allow more elaborate implementations based on software
transactional memory but, unlike the current TS, do not want to require such
elaborate implementations.''  Across these works, compiler-based TM
instrumentation remains a stated ideal rather than a delivered artifact.
Our plugin demonstrates that a practical, multi-backend compiler plugin for
STM is achievable with modest code size (\textasciitilde 2,500 lines of LLVM
pass code) and no changes to the Clang front end.

\subsection{TM Algorithms}

TinySTM~\cite{TinySTM} provides word-based STM with per-access logging (read-set
and write-set), which our evaluation confirms is expensive for workloads with
high read volumes (STMbench7 long traversals).  NOrec~\cite{NOrec} avoids
read-set logging and is the most practical backend for workloads dominated by
reads.  TL2~\cite{TL2} and SwissTM~\cite{SwissTM} offer intermediate trade-offs.
The TM TS~\cite{TMTS} GCC implementation bundles its own STM runtime; our plugin
separates the compiler pass from the backend, allowing any of these algorithms
to be selected at build time without modifying the instrumentation pass.
Our backend implementations are modernised ports of the original algorithms.
The original TinySTM, TL2, and SwissTM distributions used pre-C++11
synchronisation primitives: the \texttt{atomic\_ops} library, compiler builtins
(e.g., \texttt{\_\_sync\_synchronize}), and inline assembly for platform-specific
fences and CAS.  Our implementations replace these with standard
\texttt{std::atomic} (C++11), \texttt{std::memory\_order} for fine-grained
ordering, and \texttt{std::mutex}/\texttt{std::atomic\_compare\_exchange\_weak}
for lock acquisition.  The backends are header-only and require no platform-specific
code or external library dependencies beyond the C++ standard library.

\section{Conclusion}

We presented an LLVM compiler plugin for automatic STM instrumentation using
source-level annotations.  The plugin's key contributions are:

\begin{itemize}
\item Annotation-driven TX detection that requires no changes to function types
  or calling conventions.
\item A \texttt{tracesFromTMGlobal} backward tracer that correctly handles
  iterator-based element access through STL containers.
\item Fixed-point call-graph propagation that clones STL internal functions
  (e.g., \texttt{\_\_tree\_left\_rotate}) whose arguments are heap pointers
  that ultimately originate from TM globals.
\item Support for six STM backends, with evaluation showing that NOrec and
  SingleGlobalLock provide the best trade-off of correctness and performance
  for the annotation-based instrumentation approach.
\item \textbf{Modernised STM backends}: reimplementation of TinySTM, TL2, NOrec,
  and SwissTM using standard C++11 \texttt{std::atomic} and C++17,
  replacing the original pre-C++11 \texttt{atomic\_ops}, compiler builtins,
  and inline assembly.  The backends are header-only, portable across
  architectures, and require no platform-specific code or external library
  dependencies.
\end{itemize}
